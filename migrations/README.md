# Миграции владельцев

Отдельная операторская команда; runtime сервисов её не вызывает. Нужны Python 3.9+
(стандартная библиотека), Docker Compose и запущенный [PostgreSQL](../infra/postgres/README.md).
Локальный `psql` и Go-зависимости не нужны: используется клиент закреплённого образа.

Из корня проекта:

```sh
docker compose -f infra/postgres/compose.yaml up -d --wait
python3 scripts/migrate.py --owner api
python3 scripts/migrate.py --owner market_data
python3 scripts/migrate.py --owner matcher
python3 scripts/migrate.py --owner notifications
```

Каждая команда работает только с одной БД под её `<owner>_migration`, через TCP/SCRAM
внутри контейнера. Пароль берётся из уже настроенного окружения контейнера; он не
передаётся в аргументах процесса. `--project` выбирает существующий Compose-проект
(по умолчанию `binance-storage`); команда не запускает контейнеры сама.
`--directory /path/to/sql` заменяет каталог `migrations/<owner>` для проверки fixture.
В `api/001_users.sql` находится схема аккаунтов IAM-001, в `api/002_sessions.sql` — сессии IAM-004, в `api/003_telegram_link_codes.sql` — хеши кодов привязки IAM-006; `market_data/001_quotes_outbox.sql` — котировка, состояние потока и outbox MKT-017;
`api/005_subscriptions.sql` — каноническая подписка SUB-001 ([контракт](../internal/api/subscription/README.md));
matcher/notifications пока пусты. Контракт market-data —
[storage/README](../internal/marketdata/storage/README.md). Контракт хранилища — в [account/README](../internal/api/account/README.md).

Файлы — UTF-8 `001_description.sql`, `002_next_step.sql` и далее: положительный
уникальный bigint в начале, описание из строчных латинских букв, цифр и `_`,
начиная с буквы. Порядок числовой. Файлы с расширением `.sql` проверяются строго;
другие файлы игнорируются. Пустой каталог допустим, отсутствующий — ошибка.
Применённые файлы сохраняются неизменными; исправления добавляются новой версией,
больше всех применённых. Изменение байтов (включая переносы строк), имени или удаление
применённого файла приводит к ошибке до применения новых файлов. Историю не очищать.

В каждой БД своя закрытая схема `migration`, таблица `history` с версией,
именем, SHA-256 исходных байтов и временем применения. Runtime не имеет доступа
к этой схеме/таблице. Транзакционная advisory-блокировка `(180006, 4)` резервируется
runner в каждой БД: исполнители одного владельца ждут друг друга, разные БД не
блокируют друг друга. Блокировка берётся до создания истории и автоматически
освобождается при commit, rollback или разрыве соединения.

Весь набор ожидающих файлов и история применяются **одной транзакцией** с
`synchronous_commit=on`. Повтор пропускает применённые версии. Ошибка SQL откатывает
весь набор этого запуска; прежние успешные запуски сохраняются. `psql ON_ERROR_STOP`
возвращает ненулевой код; сообщения ошибок и имя применяемого файла видны в stderr.

SQL выполняется как доверенный операторский код через `EXECUTE` в `DO`, с
`search_path=app,pg_catalog`. Используйте квалифицированные имена `app.<table>`.
Разрешён транзакционный SQL, включая функции с dollar quoting; psql-команды
(`\i`, `\copy`), параметры `$1`, собственные BEGIN/COMMIT/ROLLBACK и операции вне
транзакции (например, CREATE INDEX CONCURRENTLY, VACUUM) не поддерживаются.
Для неатомарных операций нужен отдельный согласованный план по DEC-006.
Runner не является песочницей для недоверенного SQL.

Проверка на отдельном функциональном проекте и четырёх БД с теми же ролями:

```sh
bash infra/postgres/verify-migrations.sh
# При конфликте порта:
MIGRATION_CHECK_PORT=55435 bash infra/postgres/verify-migrations.sh
```

Проверка использует `binance-migrations-check`, порт 55434 и отдельный volume.
Тесты сбрасывают только историю и fixture `app.migration_probe` **в тестовом проекте**;
не задавайте `MIGRATION_TEST_PROJECT` рабочим проектом. Проверяются повтор для
четырёх владельцев, закрытая история, checksum/удаление файла, откат DDL и истории,
повтор после исправления, две реально ожидающие lock команды, независимость
другого владельца, запрет COMMIT и неправильные версии. После успеха контейнер
останавливается, volume сохраняется; при ошибке стенд остаётся для разбора.
Обычный `unittest discover` пропускает эти тесты без `MIGRATION_TEST_PROJECT`.
