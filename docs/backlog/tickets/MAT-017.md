# MAT-017 — Защитить SQL-записи matcher fencing token

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MAT-005](MAT-005.md), [MAT-014](MAT-014.md), [SET-010](SET-010.md), [DEC-007](DEC-007.md)

Выделенная предпосылка [MAT-010](MAT-010.md) после сессионной проверки 29 октября 2026.

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Транзакционная сериализация назначения и commit защищает от запоздалых записей без нового механизма locks.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Условная SQL-запись назначения с durable монотонным token и защита изменяемого состояния matcher в той же транзакции. Это SQL-часть MAT-010; Kafka group здесь не реализуется.

## Критерии приёмки

- Durable назначение идентифицируется средой/группой/topic/фиксированной ценовой партицией; повтор одного запроса назначения не создаёт неоднозначный новый token при потере ответа. Новое назначение повышает token без сброса после restart; исчерпание диапазона отклоняется явно.
- Контракт явно связывает назначение с pricework scope и используемой projection ID. Pricework scope не меняется при смене владельца, иначе Pending/результаты будут потеряны. C, subscription-changes offset, prices offset и token остаются независимыми шкалами.
- Accept/Record/Complete (включая terminal повтор и Prefix) и изменяющие операции projection Initialize/ApplyReplay/Handle на защищённом пути проверяют полномочия внутри той же SQL-транзакции. Повышение token и проверка полномочий сериализованы так, чтобы после commit нового token старая запись не могла commit-иться. Проверка только в Go до Begin недостаточна.
- При общем replica-local полном after-image/index не шардировать C по ценовым партициям: явно определить, какие назначения защищают запись поколения и как отзыв любого из них запрещает прежнему writer продолжение. Изолированная неактивная загрузка immutable snapshot не получает фиктивный ценовой offset.
- Защищённую идентичность нельзя записать через старый конструктор без token; неверная партиция/scope/projection и устаревший token дают явную ошибку без изменения данных и без ack. Нужные миграции и права matcher_runtime включены в результат.
- Документирован интерфейс выдачи/проверки/отзыва полномочий для MAT-018/010. Durable token не выдаётся за доказательство Kafka-владения: Kafka-назначение проверяет caller. TTL/distributed lock не добавляются.
- Выполнены проверки и [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

На disposable PostgreSQL через два независимых pool: назначение/идемпотентный повтор и рост token, конкуренция старой SQL-записи и нового назначения, rollback/неоднозначный commit, запрет старого Record/Complete/Prefix и projection replay, отсутствие ack при отказе, невозможность обхода защищённого scope/id через прежний конструктор. Подтвердить неизменность Pending и canonical исходов при смене token. Использовать `GOCACHE=/tmp/binance-go-build python3 scripts/check_postgres.py` с race detector; существующий harness не заменять новым.

## Не входит

Kafka consumer group, consumer loop, восстановление после отказа процесса (MAT-011), внешние API/RPC, runtime в cmd и нагрузка.

  MAT-010 затем связывает подтверждённое Kafka-назначение с Assign: стабильные
  scope и RequestID, ExpectedToken из Current, полный набор Grants до запуска
  projection writer, восстановление Latest/Pending до readiness. Для потери
  ответа повторять исходный Request, не выдавать новый token вслепую.
- SQL Grant не доказывает Kafka-владение. После SQL commit до callback
  назначение может измениться; транспорт обязан ещё раз проверить своё
  актуальное назначение при broker commit. Внешний поздний RPC остаётся
  безопасным через каноническую идемпотентность API.
- Gate общий для БД: изменение назначения ждёт текущие изменяющие транзакции,
  включая Initialize. Производительность не измерена. Меньший набор
  назначений использует новую ProjectionID: историческое членство сохраняется.
  Все партиции реплики регистрируются до начала обработки полной проекции.
