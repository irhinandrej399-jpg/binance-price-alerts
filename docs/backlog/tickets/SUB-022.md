# SUB-022 — Открыть защищённый SQL-replay подписок

Статус: `planned`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-021](SUB-021.md), [SUB-015](SUB-015.md), [SUB-016](SUB-016.md), [DEC-007](DEC-007.md)

Выделен при принятии [DEC-007](../../decisions/DEC-007.md); реализация не входит в DEC.

## Модель для сессии

- Модель: `gpt-6-astra`.
- Уровень размышления: `high` (High).
- Обоснование: Согласование replay-pin, целых транзакций C и durable прогресса не должно оставлять окно очистки.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора](../MODELS.md).

## Один результат

Один защищённый протокол страниц SQL-replay с подтверждением durable прогресса.

## Критерии приёмки

- Используются готовые append/read SUB-021 и pin/progress storage SUB-015; новый счётчик, snapshot-builder и cleaner не добавляются.
- Начало replay продолжает pin снимка без окна; ответ содержит cursor после C, объявленную целую head-границу H и срок ресурса. Пустая страница отличима от истёкшего/неизвестного pin.
- Прогресс подтверждается по authenticated consumer ID монотонно и только до выданной целой границы транзакции. Запрос повторяем; подтверждение не доверяет Kafka offset. Consumer подтверждает лишь свой SQL-commit.
- Истечение/отказ ресурса явно освобождает pin; остановленный consumer не исчезает только из-за отсутствия heartbeat. После потери ресурса клиент обязан начать новый snapshot.
- Пагинация ограничена; публичный/чужой consumer не читает и не меняет pins. Доступ к БД только у API.
- Выполнены проверки ниже и [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Contract/integration: конкурентный create/cancel после C, целые транзакции между страницами, повтор подтверждения и откат прогресса, неверный consumer, истечение ресурса, отсутствие окна при передаче pin snapshot→replay. Проверить реальные PostgreSQL storage-инварианты через готовые adapters.

## Не входит

Загрузка проекции matcher, брокер, новый storage pin-адаптер и создание snapshot.

## Размер сессии

Кандидат на одну сессию после готовности зависимостей и соответствующего test harness. Перед ready проверить фактические интерфейсы по workflow. Отсутствующие adapters, экспорт прогресса или harness сначала выделить отдельными предпосылками; не реализовывать скрытно.
