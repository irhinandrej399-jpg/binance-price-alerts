# OPS-067 — Исследовать нестабильную metadata после recreate в changefeed fixture

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-060](OPS-060.md), [SET-009](SET-009.md)

## Уточнение объёма — 8 ноября 2026

По [DEC-011](../../decisions/DEC-011.md) задача остаётся: это конкретный дефект
прав, поведения или обычной интеграционной проверки. Проверить причину и
узкое исправление на существующем fixture, выполнить относящиеся regression
тесты и штатный CI. Нагрузочные/длительные стресс-повторы, новый общий harness
и многократные полные suite не нужны. Защитные assertions и production guards
сохраняются; неизвестную причину не выдавать за «просто flaky».

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high` (High).
- Обоснование: Нужно различить transient readiness disposable topic и отказ source identity, сохранив проверку старого reader до dispatch.

Это рекомендация, а не смена модели; см. [MODELS](../MODELS.md).

## Один результат

Воспроизводимая диагностика и узкое исправление нестабильности changefeed source-generation integration fixture без ослабления production source guards.

## Критерии приёмки

- Воспроизвести сбой `TestIntegrationSourceGeneration` и установить причину по управляемой Kafka границе/ответам без секретов. Eventual metadata после CreateTopics — гипотеза, а не установленный факт.
- Исправить только подтверждённую причину; если это readiness fixture, использовать bounded ожидание нового ненулевого ID и готовых partitions, без sleep как доказательства и без retry старого consumer после mismatch.
- Сохранить запрет выдачи/подтверждения нового source старым reader/resume и отказ relabel старой позиции.
- Выполнить Red/Green, имеющийся disposable Kafka runner с race и проверкой cleanup; выполнить общие критерии готовности. Новый общий harness не создавать.

## Не входит

Source-bound notifications, изменение production Kafka identity/SQL contracts, новый harness и нагрузка.

## Размер сессии

Кандидат после проверки причины и готовых test adapters по [workflow](../workflow.md).

## Ход работы

- 8 ноября 2026: выбран `backlog.py next`, рекомендация Sol/High сообщена.
  OPS-060 и SET-009 подтверждены source guards, wire fixture и disposable
  Kafka runner. После сессионной проверки planned → ready → in-progress.
  Входное дерево содержало только посторонние untracked исследования;
  они сохранены и не включаются в commit.
- Подтверждена ошибка условия готовности fixture: CreateTopics success не
  гарантирует готовую broker metadata. Управляемая существующая generationWire
  отвечает успешным create, затем Metadata error 3 без partitions; прежний
  одношаговый Metadata даёт нулевую Identity/ErrMetadata, следующий ответ с
  новым ID готов. Официальный Kafka Admin API подтверждает допустимость
  задержки. Точная причина исторического ответа OPS-065 не доказана:
  ErrMetadata объединяет несколько причин, raw response не сохранился.
- Короткая диагностика реального брокера: первый исходный тест PASS; ещё 9
  повторов одного имени дали CreateTopics error 36, а не исходный сбой.
  После уникализации topic: 10 и 30 последовательных и 10 конкурентных
  сценариев PASS. Нагрузочные исследования не проводились. Временная
  production-диагностика и конкурентный тест удалены.
- Исправление только тестов: bounded newGeneration ждёт новый ненулевой ID,
  прежний ClusterID при recreate, partition 0 без ошибки и leader в ISR;
  общий бюджет 5 s, интервал опроса 20 ms. Старый reader после mismatch не
  повторяется. Все assertions Next/Confirm/resume/relabel/unbound сохранены.
- Red: `GOCACHE=/tmp/binance-go-build GOTOOLCHAIN=local go test -count=1

  целевых readiness/fetch/metadata сценариев — PASS. После добавления
  CreateTopics wire-проверки замечен собственный controller metadata lookup;
  счётчик сбрасывается после create, чтобы не поглощать управляемый ответ
