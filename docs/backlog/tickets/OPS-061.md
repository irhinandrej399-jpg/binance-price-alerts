# OPS-061 — Сохранить source binding Kafka checkpoints matcher в SQL

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-060](OPS-060.md), [MAT-017](MAT-017.md), [MAT-016](MAT-016.md), [MAT-009](MAT-009.md)

Разделённый исходный тикет: [OPS-059](OPS-059.md).

## Модель для сессии

- Модель: `gpt-6-astra` (GPT-6 Astra).
- Уровень размышления: `high` (High).
- Обоснование: Атомарные binding/checkpoint и SQL-защита от прежних writers должны сохранить fencing, Pending и происхождение снимка.

Это рекомендация, а не смена модели; см. [MODELS](../MODELS.md).

## Один результат

Один SQL-протокол source binding для обоих transport checkpoints matcher с проверяемым чтением и запретом обхода старым writer.

## Критерии приёмки

- Применить тип identity OPS-060 к projection transport checkpoint и prices
  scope/partition. Логический consumer, SQL projection/snapshot и Kafka source
  различаются по контракту OPS-059. До ready описать границы транзакций и API.
- Binding и соответствующая позиция фиксируются атомарно вместе с эффектами
  Handle/Complete; mismatch/unbound не продвигают checkpoint и не вызывают ack.
  Нельзя подставить config как provenance старого offset. Recover/Checkpoint
  дают read-only проверяемое чтение binding и позиции из согласованной SQL-view
  для OPS-056/062. Не выводить Kafka offset из C или snapshot_id.
- Сохранить стабильный prices scope, Pending/исходы и CAS Prefix при takeover.
  Проверять происхождение transport Input при Accept/возобновлении/Complete;
  не разрешать старой Pending-позиции обновить prefix нового источника.
  Смена snapshot не меняет происхождение старой Kafka позиции. C/replay работают
  независимо, до Kafka cursor нет синтетического подтверждённого offset.
- Миграция сохраняет старые строки и Pending без backfill identity. Legacy
  неподтверждён и явно отклоняется bound API; безопасный запуск документирован,
  перенос старого состояния автоматически не выполняется. Старый writer с
  прежним SQL и matcher_runtime не может продвинуть bound checkpoint, снять
  binding или переобозначить источник. Проверка только в новом Go-коде
  недостаточна; защита должна действовать в самой БД.
- Сохранить существующий fencing и атомарность projection/кандидатов. Дать
  команды PostgreSQL проверки, описание миграции/прав и API для runtime.
  Если требуется промежуточная совместимость, явно ограничить её unbound
  состоянием, никогда не выдаваемым cleaner как подтверждённое.
- Выполнены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальный disposable PostgreSQL: binding+offset commit/rollback, согласованное
чтение, повтор/конфликт; два source ID с одинаковыми topic/offset; новый snapshot;
Legacy/Pending до миграции; takeover и запоздалый token. Выполнить буквальный
старый INSERT/UPDATE через matcher_runtime одновременно с bound writer и
проверить отказ без продвижения/ack, сохранность Pending/исходов. SQL fault
не оставляет отдельно binding или отдельно offset. Использовать готовый matcher
PostgreSQL harness; Kafka transport уже проверен OPS-060.

## Не входит

Runtime wiring/process lifecycle, exporter, cleaner, автоматический перенос/удаление старого состояния и нагрузка.

## Размер сессии

Кандидат после сессионной проверки готовых интерфейсов и средств проверки.
Использовать существующие disposable runners; новый harness и независимое
поведение не добавлять скрытно. Контракт источника — в OPS-059; изменяющие
гарантии продуктовые решения сначала выделять в DEC.

## Сессионный контракт — 7 ноября 2026

- Зависимости подтверждены stores/fencing/transport и готовым PostgreSQL runner.
  Один результат: source-bound SQL checkpoint, без runtime/exporter.
- Logical projection ID и стабильный prices scope не являются Kafka identity;
  Source = ClusterID/TopicID/Topic, partition отдельно. Snapshot/C не создают offset.
- Новые NewSourceBound stores требуют ожидаемый Source, а Batch/Position/Prefix
  несут собственное происхождение; конфигурация не заполняет legacy позиции.
- Handle берёт fencing gate/row lock и атомарно связывает только ещё не имеющую
  transport projection, применяет after-images/C и offset; rollback отменяет всё.
  Recover/Checkpoint читают Source и позицию одним SELECT; Walk — одной MVCC view.
- Prices scope связывается при первом Accept под transaction advisory lock;
  существующий unbound scope с work/checkpoint отвергается. Binding без cursor
  не является подтверждённым offset. Accept/Record/Complete проверяют Input.Source;
  Complete атомарно фиксирует состояние и CAS Prefix. Takeover сохраняет scope.
- SECURITY DEFINER функции с фиксированным search_path изменяют transport bound
  строк; triggers отвергают прежние INSERT/UPDATE и снятие binding от runtime.
  Legacy совместимость ограничена unbound строками; без backfill/удаления Pending.
