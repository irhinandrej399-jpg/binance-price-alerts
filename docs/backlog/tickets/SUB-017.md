# SUB-017 — Сохранить допуск одной попытки доставки

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-013](SUB-013.md), [DOM-004](DOM-004.md), [DEC-004](DEC-004.md), [IAM-008](IAM-008.md), [DEC-005](DEC-005.md), [SUB-021](SUB-021.md)

Выделен при уточнении [DEC-004](DEC-004.md); не реализуется внутри задачи решения.

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Конкурентный допуск, отмена и истечение полномочий должны быть проверены транзакционно по одной канонической записи.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Одна storage-операция допуска попытки по готовой проверенной котировке.

## Критерии приёмки

- По [DEC-006](../../decisions/DEC-006.md): изменение видимого в снимке состояния и неизменяемое событие с номером C записываются через готовый SUB-021 в той же SQL-транзакции. Порядок блокировок: пользователь/привязка → подписка → workflow/attempt → журнал; сетевых вызовов под блокировкой нет. Ошибка outbox откатывает весь переход и слот, где он меняется.

- По DEC-004 ложное условие возвращает active/wait_condition, слот остаётся занят; истинное атомарно сохраняет sending и ограниченное разрешение attempt ID.
- Одновременно одна действующая попытка; повтор команды идемпотентен. Cancelled/delivered и blocked без исправленного канала не дают новых разрешений; fencing не позволяет старой попытке менять новую.
- Хранилище получает котировку от доверенного application-слоя; сетевое чтение цены не входит в транзакцию.
- По [DEC-005](../../decisions/DEC-005.md) допуск транзакционно проверяет актуальную привязку; сохраняет chat/версию попытки. При отсутствии канала — blocked с причиной/версией, без отдельной цены блокировки. Blocked из-за канала допускает возобновление только при новой версии: по проверенной котировке true → sending, false → active; прежние порог/workflow/слот сохраняются, версия подписки и outbox изменения обновляются атомарно. Другая причина blocked не снимается.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальная БД: два допуска, повтор request ID, ложная цена, отмена до/после допуска, истечение разрешения, rollback; слот неизменен.

Дополнительно: отсутствие/смена канала до и после допуска, blocked старой версии с новой привязкой при true/false, неизменный порог, повтор восстановления, cancel/delivered и rollback. Запоздалый отказ прежней версии не блокирует новую работу.
