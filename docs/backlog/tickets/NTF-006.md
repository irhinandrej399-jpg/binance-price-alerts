# NTF-006 — Назначить повтор по retry_after и временной ошибке

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [NTF-003](NTF-003.md), [NTF-001](NTF-001.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `medium` (Medium).
- Обоснование: Расчёт next_attempt_at ограничен правилом backoff, retry_after и пределом попыток; fake clock делает его проверяемым.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Расчёт next_attempt_at для повторяемых ошибок.

## Критерии приёмки

- По [ADR DEC-004](../../decisions/DEC-004.md): wait_condition использует отдельный ограниченный интервал проверки и не расходует счётчик ошибок Telegram; каждый HTTP-повтор требует нового допуска API.
- Учитываются retry_after, ограниченный backoff с jitter и предел попыток; worker не спит, удерживая задание.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Fake clock: 429, 5xx, повтор нескольких попыток и достижение предела.

## Не входит

Неоднозначный timeout и ручной replay.

## Размер сессии

Сессионная проверка 2 ноября 2026 пройдена: NTF-001/003 готовы; один результат — чистый расчёт расписания по классификации telegram.Error. Unit harness готов; worker, SQL-сохранение и API-допуск остаются последующим задачам. planned → ready → in-progress → done.
Для старта нужны только эта карточка, применимые ADR, готовые интерфейсы из зависимостей и относящийся к поведению код. Если требуется выбрать протокол, реализовать недостающую зависимость или менять независимое поведение, карточка сначала уточняется либо делится по [сессионной проверке](../workflow.md#сессионная-проверка-перед-ready).

Рекомендация GPT-6.1 Sol / Medium сообщена, настройки модели не менялись.
- Сессионная граница уточнена по «Один результат»: чистый расчёт расписания в `internal/notifications/retry/`, без скрытого создания worker/storage. Конкретные интервалы и бюджет — обязательные параметры, production defaults не выбраны. Контракт интеграции и пример описаны в README пакета.
- `Retry` принимает текущий clock, сохранённый счётчик до исхода, wrapped telegram.Error и случайный uint64. 429/5xx увеличивают счётчик; exponential backoff с equal jitter ограничен MaxDelay, положительный retry_after может превысить локальный максимум. На MaxFailures автоматическое расписание отсутствует, exhausted не сбрасывается. `WaitCondition` использует независимый ConditionInterval без изменения счётчика. Нет сна/захвата задания/HTTP; новый API-допуск и оба лимитера обязательны для каждого будущего Send.
- Red: `GOTOOLCHAIN=local GOCACHE=/tmp/binance-go-build go test ./internal/notifications/retry` — FAIL: `no non-test Go files`, сценарии написаны до политики.
- Green: `GOTOOLCHAIN=local GOCACHE=/tmp/binance-go-build go test -race ./internal/notifications/retry -count=1` — PASS для первоначальных чистых сценариев. Проверены fake clock, 429/5xx и несколько ошибок до предела, 20 wait_condition между ошибками, границы jitter/ceiling, retry_after=90s выше cap, отсутствие/отрицательное значение, неподдерживаемые ошибки, переполнение duration/uint32 и некорректная конфигурация. Refactor: immutable Config/Policy, отдельный метод ожидания без невозможной ошибки, saturating doubling ограничен разрядностью duration.
- Дополнены проверки реального sender на loopback fake HTTP 429/503 (одна отправка → deadline), exhausted wait и saturating doubling. Первый запуск в sandbox — FAIL `bind: operation not permitted`, успехом не считался. После разрешённого запуска вне sandbox общий `GOTOOLCHAIN=local GOCACHE=/tmp/binance-go-build go test -race ./...` — PASS, включая новый retry и оба HTTP-сценария. Неизменённые пакеты могли использовать cache; SQL/Kafka opt-in без стенда пропущены и не заявляются проверенными в этой сессии.

- Критерии расчёта выполнены. Unknown/timeout, permanent errors, NotSent и nil возвращают явную ошибку без расписания; недопустимо большой retry_after тоже не сокращается молча. Это не terminal-исход API и не повод терять задание.
