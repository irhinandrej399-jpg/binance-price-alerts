# MAT-009 — Возобновить проекцию с сохранённого cursor

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MAT-008](MAT-008.md)

Разделённый исходный тикет: [MAT-003](MAT-003.md).

## Модель для сессии

- Модель: `gpt-6-astra` (GPT-6 Astra).
- Уровень размышления: `high` (High).
- Обоснование: Cursor должен соответствовать durable проекции при сбое в любой точке; нужны безопасные replay и fallback на bootstrap.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Один restart-путь согласованной проекции и cursor.

## Критерии приёмки

- По [DEC-007](../../decisions/DEC-007.md): SQL-checkpoint авторитетен после рестарта; потеря Kafka offset commit вызывает безопасный повтор. Потеря SQL-pin/ресурса требует нового bootstrap, не silent reset на latest. Cursor C и ценовая позиция разделены; в Kafka подтверждается только непрерывно durable обработанный префикс.

- По [DEC-006](../../decisions/DEC-006.md): cursor восстанавливается вместе с durable поколением проекции из БД matcher; индекс в памяти перестраивается. Сбой до/после commit не создаёт cursor впереди применённых данных; используется готовый storage-контракт MAT-001/MAT-007.

- По [ADR DEC-004](../../decisions/DEC-004.md): после восстановления последняя цена проверяется заново; durable workflow не теряется, но прошлые исчезнувшие условия не восстанавливаются.
- Cursor не опережает сохранённое состояние; при невалидном cursor используется определённый bootstrap; replay дублей безопасен.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сессионная проверка

- 29 октября 2026: MAT-008 и её storage/replay/price зависимости подтверждены по коду и артефактам. Имеющийся совместный disposable PostgreSQL/Kafka/mTLS runner пригоден для restart-сценариев.
- Один результат: восстановить явно заданный стабильный projection ID. Origin snapshot, C и Kafka identity/NextOffset читаются из matcher SQL; индекс и ценовые подключения создаются заново. До первого Kafka commit регистрация начинается с LSO перед SQL H. При сохранённой позиции читается именно она, без reset. Потерянный pin/невалидная проекция дают явный запрос нового bootstrap; новый snapshot создаёт внешний владелец в отдельном поколении.
- Выбор активного ID в runtime, группы/fencing, durable обработка цен и кандидатов остаются отдельными задачами.

## Ход работы

- 29 октября 2026: результат завершён в одной сессии; исходное рабочее дерево чистое. Новые решения, миграции и зависимости не потребовались.
- `projection/recovery.go`: Recover читает одной SQL-view origin/C/transport выбранного поколения. Отсутствующий/неполный origin, C ниже snapshot boundary и неверная транспортная идентичность требуют bootstrap. Срок загрузки snapshot отделён от срока API replay-pin.
- `changefeed/feed.go`: RegisterAt начинает с SQL topic/partition/NextOffset, проверяет log-start/LSO, не читает broker commits и не делает reset. Прежний Register сохранён.
- `live/resume.go`, `coordinator.go`: NewResume читает SnapshotID из SQL до регистрации, не вызывает Initialize, повторяет SQL страницы до durable ack, перестраивает индекс через Walk и заново подключает MAT-012 до readiness. Невалидный checkpoint, позиция и потерянный/истёкший pin возвращают ErrBootstrap с исходной причиной. Новый snapshot/request ID и отдельный projection ID создаёт внешний владелец через MAT-007/008; прежнее поколение не удаляется.
