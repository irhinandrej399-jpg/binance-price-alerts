# MAT-013 — Подготовить источник ценовых обновлений matcher

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SET-009](SET-009.md), [CON-003](CON-003.md), [MKT-014](MKT-014.md), [DEC-007](DEC-007.md)

Выделен при сессионной проверке [MAT-012](MAT-012.md): готов producer, но отсутствует входной адаптер регистрации ценовых обновлений.

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Регистрация Kafka-чтения, ограниченная буферизация и явная потеря непрерывности требуют конкурентных и брокерных проверок по готовому контракту.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Источник read_committed ценовых обновлений с интерфейсом регистрации для MAT-012, использующий закреплённый Kafka-клиент и существующий disposable стенд.

## Критерии приёмки

- Caller передаёт уже назначенные ему prices-партиции; адаптер не реализует consumer group/rebalance. Регистрация для пары возвращается только после установки позиции чтения: последующие committed обновления остаются доступной работой до снятия регистрации. MAT-012 сможет сначала зарегистрироваться, затем вызвать Latest; создание клиента без установленного cursor не считается регистрацией.
- Чтение только read_committed, с исходными pair, generation/sequence, event_id и транспортной позицией. Автоматический commit offsets отключён; получение события и регистрация не подтверждают durable обработку цены. Цена не смешивается с C журнала подписок.
- Есть явные снятие регистрации, отмена и сигнал потери непрерывности: недоступная позиция, потеря назначения или переполнение ограниченного буфера запрещают считать регистрацию действующей. События не отбрасываются молча; MAT-012 получает необходимость нового bootstrap. Лимиты и поведение при backpressure документированы.
- Неизвестная версия, повреждённый payload и несовпадение Kafka key с pair останавливают соответствующее чтение с ошибкой без ack/skip. Дубли сохраняют исходную идентичность; арбитраж ревизий и ценовая готовность принадлежат MAT-012.
- На существующем disposable Kafka стенде проверены регистрация и последующее обновление, невидимость aborted/open transaction, исходные ключ/ревизия/позиция, отключённый auto-commit, отмена/закрытие, недоступный broker/cursor и ограничение буфера. Opt-in ошибка не подменяется SKIP; ресурсы стенда удалены.
- Интерфейс и команда воспроизведения описаны; выполнены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Регистрация до публикации, публикация одновременно с регистрацией и затем Latest в будущем MAT-012; committed/aborted транзакции; повтор сообщения; ошибка контракта; отмена во время ожидания; потеря позиции и заполнение буфера с явным отказом регистрации. Использовать готовые producer, Kafka runner и fault proxy, без нового независимого стенда.

## Не входит

## Уточнение сессионного контракта

`internal/matcher/pricefeed`: New(ctx, Config) получает LSO и устанавливает абсолютные позиции caller-assigned партиций; Register(ctx, pair, partition) под барьером диспетчеризации подтверждает LSO пары до возврата. Registration предоставляет Start/Next/Done/Err/Close; Source — Close/Revoke. Одна регистрация пары, до 1 024 регистраций; общий буфер по умолчанию 256, максимум 512 событий ≤4 KiB. Fetch/decompressed batch target 64 KiB, один concurrent fetch, broker response ≤1 MiB. Ошибка/переполнение инвалидирует весь источник, требуется новый Latest-bootstrap. Полный интерфейс и границы — в README пакета.
