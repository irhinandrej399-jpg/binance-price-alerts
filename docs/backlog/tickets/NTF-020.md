# NTF-020 — Исследовать состояние bootstrap после отмены SQL

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-064](OPS-064.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Отмена SQL, блокировка legacy writer и наблюдение commit/rollback требуют анализа конкурентности на готовом fixture.

## Один результат

Устранить подтверждённую причину сбоя проверки bootstrap/cancellation без
ослабления запрета bootstrap при незавершённом legacy writer.

## Воспроизведение

8 ноября 2026 при NTF-017 команда
`GOCACHE=/tmp/binance-go-build python3 scripts/check_postgres.py` с новой
миграцией 012 завершилась exit 1 в `TestBinding`:
`internal/notifications/intake/testdata/binding/binding_test.go:196`,
`canceled bootstrap changed state`. Полные локальные логи двух последовательных отказов:
`/tmp/NTF-017-green.log`, `/tmp/NTF-017-green-retry.log`. Миграции применились, первый прогон до 012 прошёл
TestBinding; связь сбоя с миграцией не установлена.

Сценарий: открытый tx вставляет legacy checkpoint, Bootstrap с deadline
100 ms возвращает ошибку; после rollback legacy tx обнаружена строка в
intake source либо checkpoints (текущий assertion не различает их).
Это наблюдение, не установленная причина и не доказательство flaky-теста.

## Критерии приёмки

- На существующем disposable fixture уточнить оставшиеся строки и исход SQL
  после отмены; различить дефект реализации и гонку наблюдения теста.
- Сохранить assertions отказа bootstrap при legacy writer и отсутствия
  незавершённого/частичного bootstrap после подтверждённой отмены.
- Подтверждённая причина, Red → Green, целевой PostgreSQL/race и обычный CI.

## Не входит

SQL-права NTF-017, новый harness, нагрузочные исследования и другие дефекты.

## Ход работы

- 8 ноября 2026: выбран через next/show. OPS-064 проверен по карточке,
  `binding.go`, migration 011, README и существующему disposable fixture.
  Контракты/runner готовы, один результат; planned → ready → in-progress → done.
  Рекомендация GPT-6.1 Sol / High сообщена. Существующие untracked исследования
  OPS-030/034/043/044 и infra/postgres/measure сохранены вне результата.
- Red: `GOCACHE=/tmp/binance-go-build python3 scripts/check_postgres.py
  --binding-only` с уточнённым assertion — exit 1: source=1, checkpoints=2,
  jobs=0 после `timeout: context deadline exceeded`. Локальный лог:
  `/tmp/NTF-020-red.log`. Это полный атомарный bootstrap, не частичная запись.
  Disposable контейнер/volume/network удалены.
- Причина подтверждена: Bootstrap исполняет один autocommit SELECT. В pgx
  v5.11.0 ошибка чтения по context запускает `pgconn.asyncClose`: CancelRequest
  и cleanup идут асинхронно. Тест отпускал advisory lock legacy transaction
  немедленно после клиентской ошибки. Сервер мог получить lock и завершить
  bootstrap раньше CancelRequest. Отсутствие legacy после его rollback
  законно разрешает bootstrap; клиентский timeout не обещает SQL rollback.
  Наблюдение совпадает с уже описанной неопределённостью commit в OPS-064
  и с соседним cancellation/retry тестом AcceptBound. Связь с миграцией 012
  не подтверждена; production-дефекта bootstrap не обнаружено.
- Исправлен только fixture `intake/testdata/binding/binding_test.go`:
  отдельный pool с одним соединением и известным backend PID; фактическое
  ожидание legacy writer проверяется через pg_stat_activity/pg_blocking_pids.
  Пока lock удерживается, durable source/checkpoints отсутствуют. Затем
  context явно отменяется, проверяется context.Canceled, а lock освобождается
  только после исчезновения backend PID. После подтверждённой отмены отдельные
  counts source/checkpoints/jobs равны 0. Все ожидания ограничены context.
  Никаких дополнительных SQL прав, sleeps для угадывания отмены или нового
  harness нет. Сохранены обратная гонка legacy writer после binding,
  rollback/deferred commit, legacy rejection и AcceptBound recovery.
- Green: та же команда — exit 0, TestBinding PASS (0.58 s), source=0,
  checkpoints=0, jobs=0. После refactor helper с явными SQL args финальная
  проверка той же командой — exit 0. Логи `/tmp/NTF-020-green.log` и
  `/tmp/NTF-020-final-binding.log`. Оба disposable cleanup подтверждены.
  README intake объясняет различие клиентской ошибки и серверной отмены.
- Обычный CI: `GOCACHE=/tmp/binance-go-build GOTOOLCHAIN=local go test -race
  ./...`, `go vet ./...`, `go build ./...` — exit 0;
  `python3 scripts/generate_proto.py --check` — exit 0, generated code current.
  Обычный Go suite не включает opt-in SQL/Kafka; SQL проверен целевым runner.
  Первые sandbox попытки Docker/Protobuf были недоступны (socket/DNS);
  успешные проверки выполнены с разрешённым доступом, пропуски не выданы за PASS.
- `git diff --check`, gofmt и `python3 scripts/backlog.py check` — PASS.
  Все критерии приёмки выполнены. Production Go/SQL не менялись.
