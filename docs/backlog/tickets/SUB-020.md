# SUB-020 — Открыть фиксацию исхода доставки

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-019](SUB-019.md), [DEC-009](DEC-009.md)

Выделен при уточнении [DEC-004](DEC-004.md); не реализуется внутри задачи решения.

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Защищённый интерфейс должен позволять повтор фиксации после timeout без повторного внешнего сообщения.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Один защищённый интерфейс API для готовой операции результата.

## Критерии приёмки

- По [DEC-009](../../decisions/DEC-009.md): внутренний интерфейс реализуется как unary gRPC с Protocol Buffers, сервисными полномочиями и конечным deadline; изменяющие операции сохраняют идемпотентность. Контрактные проверки включают сетевой адаптер, deadline и недоступность зависимости. Перед ready проверить готовность генерации и test harness; отсутствующие общие предпосылки выделить отдельно.

- Полномочия notifications, workflow/attempt ID и допустимый результат проверяются.
- Повтор после потерянного ответа возвращает сохранённый результат; ошибка API не требует повторной отправки Telegram.
- Поздний подтверждённый успех передаётся storage-операции, а не отбрасывается только из-за локального lease отправителя.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Авторизация, неизвестный attempt, повтор success, timeout после commit, постоянный отказ, поздний успех после отмены.

## Не входит

Изменение storage-протокола и worker reconciliation.

## Размер сессии

Кандидат на одну сессию после закрытия зависимостей. Перед ready проверить готовность адаптеров, транзакций и test harness по [workflow](../workflow.md). Недостающие предпосылки не реализовывать скрытно.
