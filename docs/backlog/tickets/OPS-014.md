# OPS-014 — Удалить безопасный префикс журнала Kafka

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SET-005](SET-005.md), [SUB-022](SUB-022.md), [MAT-011](MAT-011.md), [NTF-001](NTF-001.md), [DEC-007](DEC-007.md), [OPS-056](OPS-056.md), [OPS-057](OPS-057.md), [OPS-058](OPS-058.md)

Выделен при принятии [DEC-007](../../decisions/DEC-007.md); реализация не входит в DEC.

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high` (High).
- Обоснование: Удаление необратимо; граница должна учитывать durable прогресс всех зарегистрированных потребителей и гонки.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора](../MODELS.md).

## Один результат

Один cleaner безопасного префикса партиции Kafka по подтверждённым durable checkpoints.

## Критерии приёмки

- Cleanup по возрасту/объёму и compaction остаются выключенными. Cleaner не сбрасывает consumer на latest и не снимает SQL replay-pins.
- Реестр обязательных потребителей и их авторитетные durable checkpoints заданы явно; Kafka committed offset без проверки происхождения не считается доказательством. До ready проверить наличие интерфейсов экспорта прогресса владельцами, при отсутствии выделить prerequisite.
- Удаляется только префикс строго до минимального next-offset подтверждённых SQL-checkpoints; неизвестный потребитель/поколение, неподтверждённый прогресс или ошибка запрещают удаление.
- Регистрация нового потребителя и вывод старого из эксплуатации согласованы с очисткой; новый consumer не может требовать уже удалённую историю без явного bootstrap. Рестарт не равен выводу из эксплуатации.
- Команда повторяема, ограничена по объёму, показывает проверенную границу и результат DeleteRecords. Не удаляет целый topic и не обещает немедленного освобождения всех байтов.
- Выполнены проверки ниже и [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальные Kafka и PostgreSQL: два потребителя с разным прогрессом, отстающий/неизвестный потребитель, потерянный ответ commit offset, конкурентная регистрация/вывод, отказ DeleteRecords и повтор. Необработанное сообщение остаётся читаемым после очистки; durable задания notifications сохраняются.

## Не входит

SQL cleaner журнала API, сброс/пересоздание topics, экспорт checkpoints всех сервисов и подбор размеров нагрузочного стенда.

## Размер сессии

Кандидат на одну сессию после готовности зависимостей и соответствующего test harness. Перед ready проверить фактические интерфейсы по workflow. Отсутствующие adapters, экспорт прогресса или harness сначала выделить отдельными предпосылками; не реализовывать скрытно.

### Подготовленный вариант A — локальная maintenance-команда (предложение)

- Один доверенный локальный durable каталог реестра на среду; все экземпляры
  init/register/retire/clean обязаны использовать его и один постоянный lock
  file. Межпроцессная блокировка удерживается от чтения состава до завершения
  bounded DeleteRecords. Параллельные хосты/shared network filesystem не входят.
  Исчезновение/повреждение существующего state запрещает clean; автоматического
  создания пустого реестра при запуске нет. Init — отдельная явная операция.
- State связывает source ClusterID/TopicID/Topic/partition, полный явно заданный
  набор обязательных exact consumers (matcher kind+scope/projection ID либо
  notifications ID+generation), retired tombstones и монотонную границу уже
  разрешённого удаления. Offline/unknown не исчезают по TTL или restart.
- До отправки DeleteRecords возможная граница сохраняется atomic replace +
  fsync файла/каталога. Любая ошибка сохранения запрещает отправку. После потери
  broker response или смерти процесса эта граница остаётся обязательной даже
  если результат удаления неизвестен; повтор не откатывает её.
- Register под той же блокировкой проверяет источник, broker log-start и
  сохранённую границу возможного удаления. Новый consumer требует exact SQL
  proof не ниже этой границы; необходимый новый bootstrap выполняется владельцем
  явно до регистрации. Retire — явная операция с exact identity/generation,
  не следствие недоступности, рестарта или нового member. Неполный/пустой
  обязательный набор запрещает clean.
- Clean читает каждый зарегистрированный SQL proof через mTLS без чужих DSN,
  проверяет полный ответ/source/partition/generation и минимум next; одна команда
  обрабатывает одну partition и не более заданного диапазона offsets. Ошибка
  любого proof запрещает DeleteRecords. Возвращает проверенную границу и
  фактический broker result/неизвестный исход; SQL replay-pins не меняет.
- Операционные предусловия: один авторитетный state path и доверенный durable
  storage без восстановления устаревшей копии; provisioning не пересоздаёт topic
  во время cleanup. DeleteRecords текущего kmsg использует имя topic, поэтому
  metadata/source check не является атомарной блокировкой административного
  delete/recreate. Topic lifecycle/migration не входят в автоматическую команду.
