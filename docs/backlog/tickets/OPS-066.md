# OPS-066 — Подключить source binding к runtime notifications

Статус: `planned`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-064](OPS-064.md), [OPS-065](OPS-065.md), [OPS-055](OPS-055.md), [OPS-011](OPS-011.md), [OPS-054](OPS-054.md)

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high` (High).
- Обоснование: Runtime recovery должен сохранить pending jobs и запретить старый source при рестарте и смене topic.

Это рекомендация, а не смена модели; см. [MODELS](../MODELS.md).

## Один результат

cmd/notifications и существующая process fixture восстанавливают intake по проверяемым consumer/generation/source без изменения durable jobs.

## Критерии приёмки

- Явная обязательная конфигурация logical consumer, SQL bootstrap generation и ClusterID/TopicID delivery-requests; нет нулевого отключения/автоприсвоения текущей metadata legacy данным. Использовать OPS-064/065; задокументировать provisioning нового пустого intake и безопасный отказ legacy/source mismatch.
- Подключить bound store/consumer, сохранить API mTLS, worker/reporter, health и существующий bounded shutdown/join до pool.Close. Startup/terminal ошибки identity явно завершают процесс без ложной readiness.
- Дополнить готовую notificationsprocess fixture только source/bootstrap конфигурацией и наблюдением; использовать её disposable lifecycle/runner без нового harness. Родительские SQL assertions читают реальное binding.
- Проверить настоящий executable/race: SIGKILL/restart с прежними IDs, pending job/report/attempt/bytes и SQL/broker prefix; новый member не создаёт consumer/generation. Legacy и delete/recreate своего topic с перекрывающимися offsets дают отказ без reset/смены scope/новых job или отправок, исходы сохраняются.
- Проверить новый пустой SQL bootstrap с новой generation и отказ старого ожидания; смена source/перенос legacy требует отдельного операторского плана. Сохранить SIGTERM/SIGINT и cleanup fault exit. Документировать интерфейс для OPS-057 и выполнить общие критерии готовности.

## Сценарии TDD (Red → Green → Refactor)

Готовый scripts/check_notifications_process.py с PostgreSQL/Kafka/race, config/startup/terminal tests и применимая общая Go-регрессия. Подтвердить cleanup собственных containers/volumes/networks. Не подменять process recovery unit mocks.

## Не входит

Экспорт progress/RPC, реестр/cleaner, автоматическая миграция legacy или источника, новые Telegram/retry политики и нагрузка.
