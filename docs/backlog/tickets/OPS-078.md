# OPS-078 — Подготовить явный source provisioning постоянного стенда

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-062](OPS-062.md), [OPS-066](OPS-066.md), [E2E-005](E2E-005.md)

Выделен при сессионной проверке [OPS-074](OPS-074.md) 8 ноября 2026.

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high`.
- Обоснование: Сохранение source identity и безопасный повтор явного SQL bootstrap.

Рекомендация, не переключение модели. [Условия выбора](../MODELS.md).

## Один результат

Операторская команда первоначального provisioning источников готовых matcher и
notifications с сохраняемым inventory, пригодным для рестарта постоянного стенда.

## Критерии приёмки

- Использовать готовые kafkasource.Metadata, intake.Binding/Bootstrap/ReadProgress
  и контракты runtime. Команда выполняется явно после migrations/topics init при
  остановленных producers/consumers; runtime не делает автоматический bootstrap.
- Для нового dataset подтвердить один ClusterID, ненулевые TopicID, точный набор
  partitions prices/subscription-changes/delivery-requests (16/1/16), полные нулевые
  earliest/latest read_committed vectors до создания нулевого bootstrap. Неполный
  ответ, недоступность, непустая история или legacy SQL — отказ без выдуманных IDs.
- Сохранить вне SQL несекретный inventory: source IDs, имена topics, полный
  PRICES_BOOTSTRAP, notifications ConsumerID/Generation и стабильные runtime IDs,
  необходимые OPS-074. Формат и передачу в runtime env документировать.
- Явно bootstrap-ить новый notifications intake через готовый Store.Bootstrap;
  режим проверки существующего inventory сверяет metadata и persisted provenance
  всех partitions, не обнуляет прогресс и не требует пустоты уже рабочего broker.
  Повтор/прерывание provisioning не меняет ранее выбранные IDs и не маскирует
  несовпадение или частичный результат; дать точный безопасный порядок продолжения.
- DB credential передаётся через secret file/окружение, не argv, inventory или
  диагностический вывод. Использовать notifications runtime роль для готового
  SQL-интерфейса, не migration owner; доступ к чужим БД не добавлять.

## Проверка

TDD для нового поведения команды и один малый integration сценарий на существующем
runner E2E-005: fresh provisioning → сохранённый inventory → повторная проверка
после ненулевого durable прогресса; mismatch/отсутствующий bootstrap отклоняются.
Проверить ошибочные входы и отсутствие секретов в выводе. Целевые race и штатный CI,
без нового runner, нагрузки и расширения fault proxy.
