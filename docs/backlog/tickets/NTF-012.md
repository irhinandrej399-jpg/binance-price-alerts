## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Application-handler соединяет готовые компоненты, но обязан согласовать rate limit, lease и исход единственной HTTP-попытки.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Один application-handler соединяет готовые claim, limiter, HTTP adapter и переход результата.

## Критерии приёмки

- По [ADR DEC-004](../../decisions/DEC-004.md): после claim/лимитеров вызывается готовый SUB-018: ложное условие паркует тот же job и возвращает подписку к ожиданию. По разрешению одна немедленная попытка, текст по проверенной цене. Результат сохраняется/сообщается через NTF-014; нет нового HTTP из-за потерянного ответа API.
- За вызов не более одной HTTP-попытки; отказ лимитера не удерживает lease в ожидании; результат записывается по текущему lease.
- По [DEC-005](../../decisions/DEC-005.md) blocked из-за канала передаётся NTF-015 для durable проверки восстановления; при новой привязке используется прежний job и актуальный chat. Лимитер должен соответствовать chat допуска; при смене адресата требуется новый проход лимитеров и свежий допуск, отложенное разрешение не используется.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Одна готовая задача: success, ещё нельзя отправлять, 429 и постоянный отказ приводят к согласованным состояниям.

## Не входит

Бесконечный worker loop, параллелизм и graceful shutdown процесса.

## Размер сессии

Оценка: **кандидат на одну сессию после закрытия зависимостей**, не подтверждённый `ready`.
Для старта нужны только эта карточка, применимые ADR, готовые интерфейсы из зависимостей и относящийся к поведению код. Если требуется выбрать протокол, реализовать недостающую зависимость или менять независимое поведение, карточка сначала уточняется либо делится по [сессионной проверке](../workflow.md#сессионная-проверка-перед-ready).

## Готовый интерфейс из NTF-007

NTF-007: `Claim` может вернуть `*jobs.UnresolvedAttempt` с историческими Lease/AttemptID; сначала сохранить uncertain с будущим сроком проверки, не переиспользовать HTTP-разрешение. После Unknown использовать интервал `retry.Policy.WaitCondition` без сброса бюджета ошибок. При исчерпанном бюджете сохранять свидетельство и блокировку, не передавать нулевой срок SaveUncertain и не возобновлять HTTP. Проверить интеграционно: сервер принял запрос/оборвал ответ → durable uncertain/report → новая цена ложна → wait_condition без HTTP; затем новая цена истинна → оба лимитера/новый допуск/новый attempt, тот же trigger_id. Поздний success запрещает дальнейшие попытки.

## Готовый интерфейс из NTF-016

После 429/5xx использовать `jobs.SaveRetryable(ctx, lease, attemptID, cause,
policy, entropy, permissionBindingVersion)`: расчёт готовой retry.Policy, durable
бюджет, первый план, pending report и блокировка при Exhausted атомарны.
`Lease.Failures` переживает wait_condition/лимитеры/unknown, restart и дубль intake.
Не выполнять отдельную операцию блокировки после последней временной ошибки.
При SQL-ошибке повторять SaveRetryable, не Send; перед следующим HTTP нужны оба
лимитера и новый API-допуск/attempt по текущей цене. Конфигурация Policy задаётся
явно. Reporter подключается NTF-014. Полный контракт — jobs/README.md.
