# SUB-004 — Вернуть активные подписки владельца

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-001](SUB-001.md), [IAM-005](IAM-005.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `medium` (Medium).
- Обоснование: Список прост по объёму, но фильтр владельца и состояния должен проверяться на двух пользователях.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Один endpoint списка активных подписок текущего пользователя.

## Критерии приёмки

- По [ADR DEC-004](../../decisions/DEC-004.md): активный список включает все занимающие слот состояния DEC-004, workflow и видимую причину delivery_blocked.
- Возвращаются только собственные активные записи, не более 15; порядок стабилен.
- По [DEC-005](../../decisions/DEC-005.md) blocked виден владельцу с причиной канала; после автоматического восстановления отображается фактическое состояние прежней подписки и прежний порог.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Тесты пустого списка, нескольких собственных записей и изоляции двух пользователей.

## Не входит

## Ход работы

- Добавлены `internal/api/subscription/list.go` и `list_test.go`: защищённый GET /v1/subscriptions, владелец из context, четыре занимающих слот состояния, стабильный порядок UUID и лимит 15. Явный DTO включает точный порог/процент, версии, workflow и blocked; нет owner_id и внутренних полей. Пустой массив не null. Ответ буферизуется до проверки rows.Err/context; ошибки безопасные, частичного успеха нет.
- Refactor в `repository.go`: общие recordColumns/scanRecord для списка и ByID; публичный persistence-интерфейс SUB-001 сохранён. Миграции и другие операции не менялись. README описывает JSON, подключение обоих HTTP-обработчиков под auth и границы чтения.
- Red: `GOTOOLCHAIN=local GOCACHE=/tmp/binance-go-build go test ./internal/api/subscription` — exit 1, undefined NewListHandler. С компилируемой заглушкой `GOCACHE=/tmp/binance-go-build python3 scripts/check_postgres.py` — exit 1: TestListHTTP получил 404 вместо 200. Первый sandbox-запуск runner не имел доступа к Docker socket; поведенческий Red выполнен с разрешённым доступом вне sandbox на disposable binance-go-check. Рабочая БД не затрагивалась.
- Green: тот же PostgreSQL runner после реализации — exit 0. После уточнения процентного fixture (100 +5% = 105) и границы ровно 15 выполнен итоговый повтор — exit 0: TestListHTTP и TestListStorageFailure PASS, весь Go-набор с -race -count=1 успешно, disposable volume удалён.
- Проверены пустой список, обратный порядок вставки/повторное чтение, все шесть состояний (четыре включены, два terminal исключены), оба владельца с подменой query/header, отсутствие и подделка credentials. Blocked показывает channel_unavailable/версию канала и workflow. Fixture сохранённого восстановления отражает active/version=4, тот же ID/workflow и порог 105/+5%, без blocked. Проверены 15 и 16 незавершённых записей (ответ не больше 15). Инъекции отказа Query и поздней ошибки поверх реальных rows дают одинаковый 500 без частичного списка/деталей БД.
- `GOTOOLCHAIN=local GOCACHE=/tmp/binance-go-build go vet ./...` — exit 0; `go build ./...` с теми же env — exit 0. Сборка в sandbox сообщила отказ записи stat cache; повтор с доступом к существующему module cache завершился без предупреждения. `gofmt -l internal/api/subscription`, `git diff --check`, `python3 scripts/backlog.py check` — успешно.
