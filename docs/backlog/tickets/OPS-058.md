# OPS-058 — Подготовить disposable окружение проверки Kafka cleaner

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-056](OPS-056.md), [OPS-057](OPS-057.md), [OPS-052](OPS-052.md), [OPS-054](OPS-054.md), [SET-009](SET-009.md), [OPS-068](OPS-068.md)

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high` (High).
- Обоснование: Нужны реальные PostgreSQL/Kafka, изоляция credentials и управляемые границы отказов для проверки необратимого удаления.

Это рекомендация, а не смена модели; см. [MODELS](../MODELS.md).

## Один результат

Воспроизводимая fixture/runner для OPS-014 с двумя владельцами SQL-прогресса и настоящей Kafka.

## Критерии приёмки

- Переиспользовать готовые Compose/init/migrate, apiprocess lifecycle и Kafka fault proxy. Уникальные disposable проекты/порты/topics, конечные deadlines, cleanup после успеха/ошибки и аварийного owner exit; рабочие стенды не затрагиваются.
- Поднять владельцев matcher/notifications и их реальные защищённые export adapters OPS-056/057; cleaner caller получает только Kafka/RPC credentials и будущую конфигурацию реестра, без чужих DSN. Родительские независимые SQL observers остаются средствами проверки.
- Дать сценарии разного durable прогресса, неизвестного/отстающего consumer, потери ответа broker offset commit; управляемые границы RPC и Kafka позволяют воспроизводить ошибку/потерю ответа DeleteRecords и повтор без production fault hooks. Kafka-границы переиспользуют проверенный fault adapter OPS-068; его протокольную реализацию не включать в сборку совместной fixture.
- Fixture позволяет OPS-014 координировать конкурентную регистрацию/вывод consumer на управляемых барьерах, но не реализует и не имитирует доказанную безопасность отсутствующего продуктового реестра.
- Дать независимое чтение log-start/оставшихся read_committed записей и canonical SQL jobs/Prefix. Проверить исходные bytes, наличие необработанного сообщения и сохранность durable notifications job в квалификации fixture; сам алгоритм safe boundary проверяет OPS-014.
- Runner: без opt-in явный SKIP; с opt-in отсутствие зависимости — FAIL. README содержит команду, интерфейсы управления и ограничения. Изоляция и cleanup подтверждены реальным race-прогоном.
- Выполнены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальные PostgreSQL/Kafka/mTLS: два exporter endpoints с независимыми SQL результатами, управление задержкой/отказом и восстановлением, наблюдение log-start/read_committed bytes и pending job; startup failure и аварийный owner exit cleanup.

## Не входит

Продуктовый cleaner и его реестр, новый общий lifecycle, полный E2E и квалификация ёмкости.

## Размер сессии

Кандидат на одну сессию после проверки контрактов и средств проверки по [workflow](../workflow.md). Недостающие adapters/lifecycle выделять до ready, не выполнять несколько результатов скрытно.

  unit и integration tests, README; `scripts/check_cleaner_process.py` расширяет
  прежний runner режимом API+matcher+notifications. Нового process lifecycle нет:
  запуск/TERM/KILL/Wait/PID registry — apiprocess, инфраструктура — прежние

- Два отдельных test exporter owners выполняют реальные SQL/mTLS adapters

  CA-signed outsider отвергается обоими. Production cmd/worker здесь не запущены.
- RPC forwarding gates удерживают вызов до owner или настоящий успешный ответ

  конкурентными тестовыми действиями, не реализует registry/retirement policy.

  независимо прочитаны read_committed. Реальный AcceptBound создаёт первый job

  Реальные PriceObserved соответствуют разным durable Prefix двух matcher
  consumers одного topic; третий остаётся Pending без cursor. RPC сверены с SQL,
  unknown/Pending не дают proof; отстающая notifications partition отдаёт 0.
