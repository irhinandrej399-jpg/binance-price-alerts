# SUB-023 — Создать снимок идемпотентно по request ID

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-015](SUB-015.md), [DEC-009](DEC-009.md)

Выделен при сессионной проверке [SUB-016](SUB-016.md): сетевой повтор после потерянного commit-ответа требует durable восстановления того же ресурса.

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Durable дедупликация builder должна сохранять один S/C/pin при конкуренции, rollback и потере commit-ответа между репликами API.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора](../MODELS.md).

## Один результат

Один storage-интерфейс идемпотентного создания ресурса снимка по owner/request ID поверх готового SUB-015.

## Критерии приёмки

- При первом успешном запросе owner/request ID атомарно сохраняются соответствие ресурсу, материализованный S/C и pin; после commit повтор возвращает тот же snapshot_id/C/expires_at, в том числе после рестарта и через другую реплику API. Нет окна между commit снимка и durable дедупликацией.
- Конкурентные одинаковые запросы дают один ресурс; ключ изолирован по owner. Изменение параметров того же запроса явно отклоняется. Некорректный request ID отклоняется до создания ресурса.
- Повтор не продлевает срок. Истёкший/утраченный/отозванный ресурс явно требует нового request ID и bootstrap; прежний ключ не создаёт новый S/C. Документированы срок хранения ключа и обязанности будущего cleaner: удаление снимка не должно незаметно разрешать повторное использование ключа.
- Сохраняются retention-lock до REPEATABLE READ, согласованность S/C и атомарная публикация pin из SUB-015. Rollback не оставляет частичного ресурса/ключа; неоднозначный commit восстанавливается повтором.
- Миграция, минимальные runtime-права и storage-контракт документированы; проверки проходят на существующем disposable PostgreSQL harness и выполнены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальный PostgreSQL: одинаковый запрос последовательно и конкурентно через два экземпляра adapter; изменение подписок между повторами не меняет S/C; изоляция owner; конфликт параметров; rollback builder и потеря ответа после commit; expiry/abandon без нового ресурса; сохранение SUB-015 retention/страниц. Использовать существующие harness и fault fixtures, не вводить новый runner.

## Не входит

Сетевой endpoint/Protobuf, SQL-replay, cleaner, проекция matcher, runtime; новая реализация материализации S/C вместо SUB-015.
