# OPS-074 — Собрать постоянный запуск четырёх сервисов

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [DEC-011](DEC-011.md), [MKT-019](MKT-019.md), [E2E-002](E2E-002.md), [OPS-078](OPS-078.md), [E2E-009](E2E-009.md)

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `medium`.
- Обоснование: Один воспроизводимый deployment на готовых сервисах и хранилищах.

Рекомендация, не переключение модели. [Условия выбора](../MODELS.md).

## Один результат

Документированный запуск постоянного стенда одной командой из чистого checkout.

## Критерии приёмки

- Добавить сборку образов четырёх сервисов и Compose-профиль для одного хоста с PostgreSQL/Kafka, отдельным шагом миграций и init topics. Использовать постоянные volumes; restart не меняет ClusterID/TopicID или transactional IDs.
- Дать .env.example без секретов, проверку обязательных настроек и руководство start/status/stop/update. Стенд использует настоящие Binance/Telegram endpoints; тестовый режим явно отделён. Нужные сертификаты выдаются отдельной локальной командой для development; public ingress — OPS-075.
- Сохранять четыре отдельные БД/роли и mTLS identities. Runtime не запускается от migration owner; DSN, bot token и private keys не попадают в образ, Git, argv или вывод.
- Малый smoke через имеющиеся fake: старт, регистрация/подписка/цена/доставка, stop/start с теми же volumes и сохранённой подпиской. Не выполнять docker down -v для постоянного профиля. Проверить build/config/startup failure; без новых fault-proxy и capacity harness.

## Проверка

Только относящиеся к изменению unit/integration проверки, один небольшой smoke
на имеющихся средствах и обязательные проверки CI. Для поведения Red → Green;
для deployment/docs — проверка команд и фактического запуска, без искусственных
unit-тестов. Отсутствующую предпосылку не разрабатывать скрытно.

## Границы и сессионная проверка

Один хост, по одной реплике. Выдача публичного TLS, настройка домена и реальная доставка проверяются отдельно. Kubernetes, HA и benchmark не входят.

Перед ready сверить фактические интерфейсы и размер по [workflow](../workflow.md).
При независимых результатах разделить; новая рекомендация модели объём не заменяет.

### Реализация — 9 ноября 2026

- Добавлен `infra/deploy/`: четыре отдельных multi-stage образа и отдельный
  source-provision tool, Compose одного хоста, постоянные PostgreSQL/Kafka volumes.
  Использованы прежние init owners/topics и migration.program без изменений SQL.
  Миграции выполняются явным шагом под четырьмя migration ролями; приложения
  получают только собственную runtime DSN. Source init/verify/resume вызываются
  отдельной командой; inventory сохраняется вне checkout, runtime не bootstrap-ит SQL.
- `.env.example`, deploy.py: prepare/check/start/status/stop/update/resume и отдельный
  dev-pki. Обязательные настройки/inputs проверяются до старта хранилищ. Реальные
  Binance/Telegram endpoints заданы в обычном профиле; MODE=smoke обычная CLI
  отвергает. Секреты загружаются из приватных mounted файлов, без argv/interpolation
  или вывода; `.dockerignore` допускает только исходники сборки и entrypoint.
  У каждого сервиса свой PKI mount, различные client URI SAN; CA key не монтируется.
- Сервисы стартуют последовательно, healthcheck проверяет /healthz. Raw feed
  сохраняет unconfirmed и /readyz=503; SQL ради readiness не менялся. Только API
  HTTP публикуется на loopback; RPC/SQL/Kafka остаются внутри bridge. Ограничены
  контейнерные логи; restart policy сохраняет прежние IDs. README описывает
  остановку/обновление, dev certificate expiry, recovery и границы выпуска.
- Узкий smoke.py + Go test используют готовые binancefake/telegramfake через
  NewWithListener в отдельном контейнере. Test-only Compose override делит namespace
  notifications с fixture: существующий Telegram client разрешает HTTP только на
  literal loopback; guard и production runtime не менялись. Binance используется
  через bridge DNS. Link остаётся loopback-only, обычный test webhook отправляется
  отдельно по изолированному маршруту. Новые vendor handlers/control API не добавлены.
- Неуспешные попытки не считались проверкой: первый запуск выявил explicit EC
  parameters/SHA-1 системного LibreSSL — dev-pki теперь явно named curve/SHA-256.
  Следующий выявил запрет HTTP non-loopback у Telegram client — исправлена только
  тестовая топология. Compose config также потребовал явно активировать smoke
  profile; случайный tempfile suffix с underscore заменён отдельным hex project ID.
- Первый успешный journey выявил ошибку остановки: `compose stop` со списком
  останавливает всё одновременно, PostgreSQL завершался раньше durable gap write
  market-data. Теперь stop_apps ждёт каждый процесс в обратном порядке, и только
  затем останавливает Kafka/PostgreSQL. Финальный smoke подтвердил exit 0 всех
  четырёх приложений до выключения хранилищ. Все промежуточные disposable datasets
  очищены; одиночный каталог с невалидным project ID содержал только config и удалён.
