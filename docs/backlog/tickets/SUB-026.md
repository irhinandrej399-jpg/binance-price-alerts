# SUB-026 — Сохранить блокировку после промежуточного исхода той же попытки

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-020](SUB-020.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Канонический арбитраж нескольких исходов одной попытки, fencing, отмена/успех и однократный журнал требуют SQL/race проверки.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

API применяет доказанный blocked после retryable/uncertain той же актуальной попытки, независимо от порядка и повторов отчётов, без понижения успеха и без изменения чужой новой попытки.

## Воспроизведение

Найдено при проверке интеграционного контракта NTF-016 3 ноября 2026.
`internal/api/subscription/result.go`: mutate отрицательного исхода требует
current_attempt_id == attempt ID; любой применённый исход затем очищает
current_attempt_id. Поэтому последовательность для одного допуска:

1. Получить допуск (helpers в result_test.go), сохранить DeliveryRetryable.
2. Сохранить DeliveryFailed/AttemptsExhausted для того же attempt.
3. Прочитать canonical subscription: останется pending_delivery, хотя аудит
   содержит оба исхода; ожидается delivery_blocked/attempts_exhausted.

То же для uncertain → blocked. Это вывод по текущему коду; отдельный SQL Red
данной последовательности ещё не выполнялся. Имеющиеся тесты проверяют
отдельные отрицательные исходы и поздний success, но не эту последовательность.
У NTF-016 Exhausted атомарно создаёт retryable и blocked pending reports;
у NTF-008 blocked может прийти после восстановления uncertain. Reporter не может
обеспечить общий порядок отчётов, уже подтверждённых до позднего ответа HTTP.

## Критерии приёмки

- Реальный PostgreSQL Red подтверждает воспроизведение; один attempt принимает retryable/uncertain → blocked в обоих порядках и при concurrent replay.
- Канонический blocked не понижается retryable/uncertain; поздний success имеет приоритет, отмена не возрождается. Отрицательный исход старого fence не меняет новую попытку/канал.
- Audit, quota, journal/outbox и replay сохраняют существующие гарантии SUB-019/020; повтор не создаёт лишнюю версию/журнал и не освобождает слот.
- Готовый gRPC-контракт не расширяется без необходимости. Выполнены общие [критерии готовности](../workflow.md).

## Не входит

Notifications storage, reporter и worker/runtime.
