# NTF-018 — Исследовать сбой восстановления после потери ответа регистрации

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [NTF-012](NTF-012.md)

## Уточнение объёма — 8 ноября 2026

По [DEC-011](../../decisions/DEC-011.md) задача остаётся: это конкретный дефект
прав, поведения или обычной интеграционной проверки. Проверить причину и
узкое исправление на существующем fixture, выполнить относящиеся regression
тесты и штатный CI. Нагрузочные/длительные стресс-повторы, новый общий harness
и многократные полные suite не нужны. Защитные assertions и production guards
сохраняются; неизвестную причину не выдавать за «просто flaky».

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Lease, crash recovery и временные границы на реальном PostgreSQL.

## Один результат

Выяснить и устранить причину нестабильного TestHandlerRegisteredCrashRecovery
без ослабления проверки запрета HTTP по историческому permission.

## Критерии приёмки

- Причина подтверждена воспроизведением; различены ошибка реализации и timing теста.
- После потери ответа регистрации recovery приводит к wait_condition/active,
  не отправляя HTTP по историческому permission.
- Исправление проверено через Red → Green и на disposable PostgreSQL с race detector.

## Проверка и воспроизведение

`python3 scripts/check_postgres.py`: 6 ноября 2026 при проверке OPS-001

ожидался wait_condition, наблюдался sending (revision 3, latest_price).
В тесте используется lease 50 ms; влияние параллельной нагрузки — гипотеза.

Для узкого повтора на таком же migrated disposable стенде:
`go test -race -count=1 -run '^TestHandlerRegisteredCrashRecovery$' ./internal/api/admissionrpc`.

исходного сбоя. Проверить и самостоятельный повтор, и конкурентную нагрузку.

## Ход работы — 8 ноября 2026

- Выбран через `backlog.py next`; зависимость NTF-012 подтверждена существующими
  handler/jobs/report и SQL/mTLS/HTTP fixture. Сессионная проверка пройдена,
  planned → ready → in-progress. На входе только посторонние untracked измерения;
  они не изменялись и не включены в commit.
- Установлена ошибка timing/предусловия теста, а не ошибка crash recovery.
  Lease 50 ms начинался до PrepareRecipient, SQL-лимитеров и AdmitDelivery.
  API мог уже сохранить sending, но локальный lease истекал до RegisterAttempt:
  handler возвращал invalid/expired permission либо ErrStale. Тест принимал
  любую ошибку как потерю ответа committed регистрации, не проверяя сам commit.
  Без локальной регистрации recovery не создаёт uncertain/report; очередной
  admission получает attempt_busy по ещё действующей минутной API-попытке,
  локально паркует wait_condition, а канонический sending остаётся. Это объясняет
  исходное сочетание состояний без ослабления production guards.
- Red: добавлены проверка `lostRegistration.lost`, ровно одна SQL-регистрация,
  канонический sending и вариант с задержкой ответа admission 75 ms после
  настоящего RPC/commit. На чистом migrated PostgreSQL с runtime-ролями:
  `go test -race -count=1 -v -run '^TestHandlerRegisteredCrashRecovery$'
  ./internal/api/admissionrpc` — FAIL именно в delayed варианте:
  `crash fixture never committed registration: invalid or expired delivery permission`;
  обычный вариант PASS. Лог локально `/tmp/NTF-018-red.log`.
- Green: только fixture lease увеличен до 1 s; проверка фактического commit
  обязательна в обоих вариантах. После expiry/restart дополнительно проверяются
  PendingDelivery, ровно одно durable uncertain и отсутствие pending report;
  итоговые wait_condition/Active и ноль HTTP сохранены. Production handler,
  сроки разрешений, guards и SQL-права не менялись.
- Узкий Green на новом чистом PostgreSQL/race — оба варианта PASS.
  Финальная регрессия `go test -race -count=1 -v -run .
  ./internal/api/admissionrpc` — весь пакет PASS (22.398 s), включая обычный
  и задержанный crash recovery, HTTP outcomes, limiter и admission guards.
  Финальный SQL-прогон пересекался с общей `go test -race ./...`: PASS при
  конкурентной нагрузке. Логи локально `/tmp/NTF-018-green.log`,
  `/tmp/NTF-018-postgres-final.log`, `/tmp/NTF-018-race.log`.
- Для трёх SQL-прогонов использован setup/migrations/runtime DSN/cleanup
  существующего `scripts/check_postgres.py`; временный `/tmp/ntf018-postgres.py`
  через импорт заменял только subprocess Go-test фазу на указанный admissionrpc
  scope. Репозиторный runner не менялся; все три disposable контейнера/volume
  удалены. Для воспроизведения подходят команды выше с owner DSN и POSTGRES_TEST=1
  на штатном migrated disposable fixture; общий `check_postgres.py` тоже включает
  эти тесты, но его независимый TestBinding defect остаётся NTF-020.
- Штатные проверки с `GOCACHE=/tmp/binance-go-cache`, `GOTOOLCHAIN=local`:
  `go test -race ./...`, `go vet ./...`, `go build ./...` — exit 0.
  `python3 scripts/generate_proto.py --check` — generated code current, exit 0.
  Docker/loopback и загрузка protoc выполнялись с разрешённым расширением sandbox;
  первые ограниченные попытки Docker/DNS не считались успехом.
- `gofmt -l internal/api/admissionrpc/handler_test.go`, `git diff --check`
  и `python3 scripts/backlog.py check` — PASS. Все критерии выполнены.
