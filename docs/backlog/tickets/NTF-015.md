# NTF-015 — Возобновить задание после восстановления Telegram

Статус: `planned`. Приоритет определяется зависимостями, а не номером.

Зависимости: [NTF-008](NTF-008.md), [NTF-009](NTF-009.md), [SUB-018](SUB-018.md), [DEC-005](DEC-005.md)

Выделен при уточнении DEC-005; не реализуется внутри решения.

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Durable проверка должна пережить рестарт и гонку с перепривязкой/запоздалым отказом, сохраняя одно задание.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Одна storage/scheduler-операция назначения проверки восстановления канала для прежнего задания.

## Критерии приёмки

- По [DEC-006](../../decisions/DEC-006.md): next_check_at, причина и версия канала хранятся в БД notifications; claim и перепланирование используют готовые lease/fencing-операции. Перезапуск восстанавливает проверку того же задания.

- По [DEC-005](../../decisions/DEC-005.md) blocked из-за канала сохраняет job, причину и версию привязки без отдельной цены блокировки. Назначенная проверка durable, доступна claim и восстанавливается после рестарта.
- Настраиваемый ограниченный интервал/backoff без busy loop, удержания lease/лимитера и расхода счётчика HTTP-ошибок. Без новых ценовых событий задание всё равно попадает на проверку SUB-018 через обычный handler NTF-012.
- Результат той же версии/нет канала вновь паркует job без sendMessage. Новая версия и wait_condition возвращают тот же job к ожиданию цены; допуск возвращает к обычной доставке. Порог, workflow и слот не меняются.
- Повтор назначения не создаёт второго job; отмена/успех не возрождаются, чужая причина blocked не снимается. Запоздалый отрицательный результат старой версии не затирает восстановление.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальная БД notifications + fake clock готового harness: durable назначение/рестарт, повтор парковки, backoff, claim срока проверки, новая версия при true/false через готовые результаты API, отмена/успех, запоздалый отказ и один job. Нет Telegram-вызовов в самой операции назначения.

## Не входит

Новый API допуска, изменение привязки, Telegram adapter и worker loop. Соединение компонентов — NTF-012.

## Размер сессии

Кандидат на одну сессию после готовности зависимостей и test harness; перед ready проверить по [workflow](../workflow.md). Недостающие предпосылки не реализовывать скрытно.
