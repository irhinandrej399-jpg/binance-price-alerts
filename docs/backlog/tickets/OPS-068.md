# OPS-068 — Управлять отказами OffsetCommit и DeleteRecords в Kafka fault proxy

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SET-009](SET-009.md)

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high` (High).
- Обоснование: Нужны correlation/version-aware Kafka frames, различение отказа до запроса и потери ответа после broker commit, конечные ожидания и race-safe cleanup.

Это рекомендация, а не смена модели; см. [MODELS](../MODELS.md).

## Один результат

Переиспользуемые управляемые границы OffsetCommit/DeleteRecords в существующем
`internal/testutil/kafkafault.Proxy`, квалифицированные на настоящей disposable Kafka
для совместной fixture OPS-058.

## Критерии приёмки

- Расширить существующий framed TCP proxy SET-009, сохранив New/Arm/Observed,
  EndTxn lost-response сценарий и ограничения single-broker plaintext.
  Не создавать новый broker/lifecycle, не добавлять production fault hooks.
- Управление выбирает нужный API и различает две границы: до пересылки
  DeleteRecords реальному broker и после получения его настоящего ответа,
  перед доставкой caller. Барьер наблюдаем тестом, освобождение идемпотентно;
  можно воспроизвести отказ до удаления и потерю успешного ответа после удаления.
  Не подменять сетевой отказ синтетическим успешным ответом.
- Дать потерю настоящего успешного OffsetCommit response: запрос доходит до
  broker, fault observer подтверждает декодированный результат, caller не
  получает подтверждения. Учитывать реальные версии/flexible headers,
  correlation ID и ошибки нужных topic/partition; соседние API не повреждаются.
- Fault охватывает автоматические повторы выбранной операции до явного
  снятия; после снятия доступен управляемый повтор с прежними параметрами.
  Документировать область действия и не приписывать потерю ответа простой
  остановке клиента перед отправкой запроса.
- Context/deadline и Close освобождают активные gates/connections/goroutines;
  проверены отмена, повторное освобождение, параллельные запросы и race.
  Сохранить bounded framing и отказ на некорректных frames без утечки секретов.
- Реальная Kafka-квалификация независимо читает committed group offset,
  log-start и оставшиеся read_committed bytes: отказ до DeleteRecords не
  удаляет prefix, потерянный успешный ответ уже изменяет log-start, повтор
  той же границы сохраняет необработанное сообщение и исходные bytes.
  Это квалификация сетевого adapter, без вычисления безопасной границы cleaner.
- Переиспользовать disposable Compose/init и runner SET-009 с уникальными
  topics/проектом, конечными deadlines и cleanup при успехе/ошибке. Без opt-in
  явный SKIP; с opt-in недоступный broker — FAIL. README описывает команды,
  управление границами, наблюдение фактического broker результата и ограничения.
- Выполнены [общие критерии готовности](../workflow.md), включая реальный
  race-прогон, сохранность прежнего EndTxn сценария и подтверждение cleanup.

## Сценарии TDD (Red → Green → Refactor)

Настоящая Kafka через существующий proxy: OffsetCommit выполнен, ответ потерян,
независимый observer видит commit; DeleteRecords заблокирован до broker и
отклонён без изменения log-start; успешное удаление с потерянным ответом и
повтором той же границы после снятия fault; исходные retained bytes;
параллельный соседний API, cancellation/Close и прежний EndTxn loss.

## Не входит

Совместная PostgreSQL/RPC fixture OPS-058, SQL jobs, реестр/retirement/cleaner
OPS-014, изменение production clients, Kafka TLS/multi-broker и нагрузка.
