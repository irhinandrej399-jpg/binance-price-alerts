# SET-009 — Подготовить Go-клиент и транзакционные проверки Kafka

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SET-001](SET-001.md), [SET-005](SET-005.md), [DEC-007](DEC-007.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Подготовка транзакционного клиента требует проверки fencing, неоднозначного commit timeout и управляемых сетевых сбоев.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Воспроизводимая основа разработки и проверки транзакционных Kafka producers в Go, без прикладных событий.

## Критерии приёмки

- Выбран и закреплён Go-клиент Kafka с транзакциями и fencing; описаны создание, инициализация, закрытие и обязательный стабильный transactional.id вызывающего relay-шарда. Проверены эквиваленты acks=all, idempotence, retries и max.in.flight<=5 по DEC-007; заданы конечные context/deadline без логирования credentials.
- Одна документированная команда использует отдельный disposable Compose-проект и префикс topics на основе SET-005; рабочие topics/volume не затрагиваются. Очистка выполняется при ошибке, ожидания ограничены; тестовые сообщения — неприкладной probe.
- Реальные Go-интеграционные тесты подтверждают commit/abort и read_committed, fencing прежнего producer новым с тем же transactional.id и отказ недоступного брокера. Ошибка не выдаётся за commit; неоднозначный timeout различим от fencing и подтверждённого commit.
- Переиспользуемое средство управления сетевыми сбоями позволяет воспроизводимо потерять ответ commit после обработки брокером и проверить повтор исходного probe-сообщения новым producer с тем же transactional.id. Неоднозначный результат не считается доказанным abort; допустимый дубль сохраняет исходную идентичность. Один mock последовательности методов не заменяет проверку протокола.
- Обычные Go-тесты явно пропускают opt-in реальные проверки без стенда; при явно включённом opt-in недоступный брокер вызывает ошибку. Документированы интерфейс использования в MKT-013 и пределы гарантии: нет exactly-once между PostgreSQL и Kafka.
- Выполнены применимые [общие критерии готовности](../workflow.md).

## Проверка / воспроизведение

Выполнить команду disposable-проверки и отказный сценарий с недоступным брокером; проверить освобождение ресурсов. Для поведения клиента/helper использовать Red → Green; для Compose/runner — соответствующую проверку без искусственных unit-тестов. Выполнить Go race/vet/build для затронутого кода.

## Не входит

PriceObserved producer (MKT-013), SQL-outbox relay, буфер, длительные прикладные повторы, consumers приложения, cleaner, нагрузка и runtime четырёх сервисов.

## Размер сессии

Кандидат на одну сессию после проверки SET-001/005 и доступности инструментов. Использовать существующий Kafka Compose и конфигурацию topics. Если выбранный клиент требует самостоятельного большого fault broker, сначала уточнить разделение основы, не уменьшать проверку неоднозначного commit.
