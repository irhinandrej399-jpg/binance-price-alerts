# IAM-004 — Реализовать вход с ограниченным сроком сессии

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [IAM-001](IAM-001.md), [IAM-002](IAM-002.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Выдача credentials, конечный TTL и одинаковые внешние ошибки входа требуют тщательной проверки безопасности и времени.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Один HTTP endpoint входа, выдающий проверяемые credentials с конечным TTL.

## Критерии приёмки

- Неверные email и пароль дают одинаковый внешний ответ; TTL и формат credentials записаны в контракте.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Тесты успешного входа, неверного пароля, неизвестного email и времени истечения.

## Не входит

Refresh-токены и восстановление пароля.

## Размер сессии

Оценка: **кандидат на одну сессию после закрытия зависимостей**, не подтверждённый `ready`.
Для старта нужны только эта карточка, применимые ADR, готовые интерфейсы из зависимостей и относящийся к поведению код. Если требуется выбрать протокол, реализовать недостающую зависимость или менять независимое поведение, карточка сначала уточняется либо делится по [сессионной проверке](../workflow.md#сессионная-проверка-перед-ready).

## Согласованный контракт и сессионная проверка

- 27 октября 2026 пользователь согласовал случайный Bearer-токен на 24 часа, только SHA-256/user_id/expiry в PostgreSQL. Решение: [IAM-004](../../decisions/IAM-004.md).
- IAM-001/002 готовы по миграции и коду account/password; тестовый PostgreSQL runner существует. Рабочее дерево чистое. Рекомендация Sol / High сообщена. planned → ready после согласования контракта.
- Один результат включает выдачу, необходимую схему/adapter сессии и проверку срока; middleware защищённого endpoint остаётся IAM-005.
- POST /v1/sessions, JSON email/password; 200 access_token/token_type/expires_in/expires_at, 401 invalid_credentials одинаково для неизвестного email/неверного пароля, 400 invalid_request для malformed/пустых полей, 415 unsupported_media_type, 500 internal_error. Cache-Control: no-store.

## Ход работы

- 27 октября 2026: после сессионной проверки и согласования контракта выполнены ready → in-progress → done. Новая миграция 002_sessions, session.Store и HTTP-handler login; контракты в README соответствующих пакетов. Принятое решение записано в docs/decisions/IAM-004.md, требования обновлены. Отдельная DEC-карточка не создавалась: требования делегируют конкретный формат соответствующей интерфейсной задаче IAM-004, пользователь явно согласовал вариант в этой сессии.

Затем с компилируемым session stub `python3 scripts/check_postgres.py` упал в TestSessionsWithPostgres/session_test.go:26 с session storage operation failed — Issue не реализован. Это фактический поведенческий Red на реальном PostgreSQL, не инфраструктурный сбой.
- Первый sandbox-запуск runner не имел доступа к Docker socket; повтор с разрешённым выходом из песочницы выполнил Red. Рабочая БД не адресовалась; использовался только disposable binance-go-check, удалённый runner вместе с volume после каждого запуска.
- Green: `GOTOOLCHAIN=local go test ./internal/api/login ./internal/api/session` — exit 0 (PostgreSQL opt-in пропущены). `python3 scripts/check_postgres.py` — exit 0, реальные PostgreSQL-сценарии всех пакетов с `go test -race -count=1 -v ./...`.
- Refactor: упрощён DTO ошибок login. Повтор `python3 scripts/check_postgres.py` на итоговом коде — exit 0; TestLoginWithPostgres и TestSessionsWithPostgres PASS, disposable volume удалён. Проверены неизвестный/неправильного формата email и неверный пароль с одинаковыми 401, сохранение байтов пароля и нормализация email, отсутствие сессии после отказа, 400/404/405/415, безопасные 500 обоих хранилищ, повреждённый password_hash, случайность/независимость токенов, digest в БД, FK, истечение до/на/после границы, поддельный/неканонический токен, каскадное удаление владельца.

## Передача следующей сессии

- Статус: `done`. Незавершённых действий IAM-004 нет. Результат — подключаемый handler `POST /v1/sessions` и хранилище/Verify с конечным TTL, не запущенный runtime.
- Следующий шаг по отдельному поручению: IAM-005, middleware защищённого endpoint. Использовать `session.Store.Verify(ctx, token)` для доверенного user_id; ErrInvalid отклоняет сессию, ErrStorage/отмена context не дают доступ. user_id клиента не заменяет владельца.
- Основные файлы: internal/api/login/{login.go,login_test.go,README.md}, internal/api/session/{session.go,session_test.go,README.md}, migrations/api/002_sessions.sql; ADR docs/decisions/IAM-004.md. Схему рабочей БД этой сессией не мигрировали.
- Ограничения: middleware, runtime wiring, refresh/logout, восстановление пароля, очистка истёкших строк, лимиты тела и частоты остаются вне задачи. Часы API-реплик должны быть согласованы; нагрузка не измерялась. При каждом входе создаётся независимая сессия, предыдущая не отзывается.
