# MAT-019 — Ограничить live-подключения назначенными ценовыми партициями

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MAT-009](MAT-009.md), [MAT-018](MAT-018.md), [DEC-007](DEC-007.md)

Выделено как предпосылка [MAT-010](MAT-010.md) после проверки фактических интерфейсов.

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Полная проекция и единый C должны сохраняться при ограничении ценовых подключений и readiness текущим назначением, включая replay и restart.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

`live.Coordinator` строит и восстанавливает полную проекцию подписок, но подключает цены и предоставляет кандидатов только для пар фиксированного ценового назначения. Это готовый интерфейс view для интеграции двух matcher в MAT-010.

## Критерии приёмки

- Caller задаёт неизменный набор назначенных ценовых партиций на один запуск New/NewResume; отображение пары использует `pricefeed.PairPartition`. Отсутствие ограничения сохраняет прежний режим. Явно пустое назначение не трактуется как владение всеми партициями; недопустимые номера/дубли отклоняются. Набор копируется, последующее изменение входных данных не меняет полномочия.
- Initialize, replay, Walk и durable C/transport cursor остаются полными и независимыми от ценовых offsets. Чужие after-images, workflow и tombstones не теряются и не мешают готовности собственной view.
- При bootstrap, SQL/Kafka update и NewResume подключаются только активные пары своего назначения. Для чужих пар не вызываются Register/Latest и не создаются ценовые readers; Current чужой пары возвращает ErrNotReady.
- Readiness зависит от необходимых собственных подключений. Отмена lifetime назначения отзывает Ready/Current и закрывает свои подключения; изменение набора требует нового координатора, а не мутации действующей view.
- Доступен согласованный с readiness перечень активных собственных пар для первоначальной оценки и повторного чтения после Changed в MAT-010. Перечень не выдаёт исторические candidate batches и не подтверждает цены.
- Проверены bootstrap/replay/restart с подписками как в своих, так и в чужих партициях, появление/отмена последней собственной пары и назначение без собственных активных подписок.

## Сценарии TDD (Red → Green → Refactor)

1. Полная проекция содержит две активные пары с разными `PairPartition`; назначена только одна. Connect чужой пары возвращает ErrConfig, как настоящий Assignment.Register. До изменения текущий Run ошибочно вызывает его и не достигает Ready; после изменения готова только собственная пара, durable проекция содержит обе.
2. Replay создаёт/обновляет/отменяет чужую подписку: C и after-image меняются, чужое подключение не появляется. Создание собственной пары выполняет Register → Latest, отмена последней освобождает подключение.
3. NewResume восстанавливает полный C и транспортный cursor, заново подключает только собственные цены; изменение caller slice после создания не расширяет назначение.
4. Отмена контекста назначения отзывает готовность/Current/перечень и завершает readers. Пустой набор и набор без собственных active подписок не подключают чужие цены.

Использовать существующие unit fixtures `internal/matcher/live/*_test.go` и совместный disposable runner `GOCACHE=/tmp/binance-go-build KAFKA_RUN_POSTGRES=1 bash infra/kafka/verify-go.sh` для полной SQL-проекции/replay. Harness и отдельные сервисы не создавать.
