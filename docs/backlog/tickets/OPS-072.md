# OPS-072 — Подключить Telegram-привязку к процессу API

Статус: `planned`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-004](OPS-004.md), [OPS-012](OPS-012.md), [IAM-006](IAM-006.md), [IAM-007](IAM-007.md), [IAM-008](IAM-008.md), [E2E-004](E2E-004.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `medium`.
- Обоснование: Монтаж готовых HTTP handlers и клиентов с готовым процессным harness.

Это рекомендация пользователю, настройки текущей сессии не меняются. [Условия выбора](../MODELS.md).

## Один результат

Настоящий API выдаёт link-code и принимает защищённый Telegram /start webhook.

## Критерии приёмки

- POST /v1/telegram/link-codes использует готовый session/auth и telegramcode; POST /v1/telegram/webhook соединяет telegramwebhook с telegramlink без Bearer.
- Webhook secret явно задаётся окружением и проверяется до startup; токен бота и setWebhook не нужны. Общий body limit и HTTP shutdown сохраняются; секреты/коды не попадают в ошибки/логи.
- Привязка сохраняется только в собственной API БД; повтор update/code и чужой секрет следуют существующим контрактам.

- Выполнены проверки ниже и [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

scripts/check_api_process.py --package ./cmd/api: executable с disposable PostgreSQL/Kafka; реальная регистрация/вход → выдача кода → telegramfake.Link → независимое чтение binding/version; 401/403, повтор кода, ошибочный secret startup, shutdown и cleanup.
Сначала получить падение по отсутствующему runtime wiring; затем подключить готовые adapters и повторить проверки с race. Unit-проверка конфигурации не заменяет процессный тест.

## Не входит

Сборка подписок/RPC, setWebhook у Telegram, реальная доставка, новое поведение привязки и полный E2E.

## Размер сессии

Кандидат на одну сессию, не ready. Перед реализацией проверить зависимости и достаточность существующего process harness. Если нужен независимый adapter/harness, выделить зависимость до кода.
