# OPS-045 — Подготовить наблюдения границ задержки цена → durable workflow

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MKT-014](MKT-014.md), [SUB-013](SUB-013.md), [SUB-014](SUB-014.md), [DEC-008](DEC-008.md), [DEC-010](DEC-010.md)

Выделена при сессионной проверке [OPS-002](OPS-002.md).

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Нужен один контракт измерительных наблюдений с корректными
  границами commit, сопоставимостью часов и восстановлением после повтора.

Это рекомендация, а не автоматическая смена модели. [Правила](../MODELS.md).

## Один результат

Готовый контракт и точки получения исходных наблюдений t0/t1 для OPS-002,
проверенные на готовых компонентах без запуска полного приложения.

## Критерии приёмки

- По DEC-008: t0 фиксируется при приёме контрольной цены до SQL commit
  market-data; t1 — после подтверждённого commit workflow/outbox API.
  Предоставить сопоставимую монотонную шкалу для процессов одного хоста,
  идентичность шкалы и явную ошибку при несопоставимости. Сериализация
  time.Time сама по себе монотонную часть Go не переносит.
- Наблюдения содержат идентичности для raw join с контрольным эталоном:
  первая сохраняющаяся подходящая цена каждой ожидаемой подписки остаётся
  началом при поздних ревизиях. Эталон задаёт вызывающий контрольный сценарий,
  а не новая история всех рыночных условий в production matcher.
- Успешный повтор существующего workflow не выдаётся за первый commit;
  rollback и неизвестный commit не выдаются за подтверждение. Потерянное
  наблюдение/ошибка sink видимы и не меняют бизнес-результат. Указать границы
  полноты при crash: OPS-002 обязан учитывать missing, а не обещать durable
  телеметрию без доказательства. Не добавлять распределённую транзакцию.
- Документировать подключение готовых точек наблюдения и формат для OPS-002.
  ID остаются в исходных наблюдениях, не становятся metric labels.
- Доступные реальные PostgreSQL и loopback harness используются через
  существующие интерфейсы. Подготовка нового стенда — отдельная предпосылка,
  если она фактически потребуется. После чтения кода подтвердить размер
  сессии; независимые результаты разделить до ready.

## Сценарии TDD (Red → Green → Refactor)

Известный интервал между приёмом и commit сохраняется в наблюдениях;
две подходящие ревизии не заменяют первый t0 контрольной подписки;
commit failure/rollback не дают t1, повтор workflow не даёт нового t1;
чужая шкала и потерянная отметка явно обнаруживаются.

## Не входит

Histogram, экспорт метрик, вычисление p99 и полноты (OPS-002),
полный runtime, нагрузочный runner, distributed tracing, доказательство SLA
и квалификация диска. По DEC-010 нагрузочный этап остаётся отложен.

## Передача следующей сессии

- Статус: done. Следующий по ORDER — OPS-002, только по отдельному поручению и после его сессионной проверки.
- Использовать `internal/platform/latency/README.md` и готовые opt-in hooks, не время повторного Latest/RPC. OPS-002 отвечает за oracle ожидаемых подписок, полноту/missing и агрегацию. ID остаются raw, не labels. При выборе первой контрольной цены один раз сохранить first_attempt_id; поздние ревизии его не заменяют.
- Sink не durable: crash после commit до наблюдения или потерянный commit-response оставляют missing; recovery не может доказать первое t1. Failures проверять с каждого процесса, flush/close sink отдельно. Поддержанные часы macOS проверены межпроцессно; Linux только скомпилирован. Не смешивать OS/VM/boots, не запускать опыт со sleep хоста.
- Полного runtime и производительности ещё нет; p99/SLA не измерены. OPS-002 и будущий runtime должны подключить recorder на непосредственном контрольном входе Accept. Рабочие БД и Kafka не изменялись, NTF-018 не реализовывался; текущий полный прогон прошёл, что не заменяет расследование его прежнего сбоя.
