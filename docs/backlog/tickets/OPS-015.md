# OPS-015 — Остановить новый приём API при исчерпании бюджета

Статус: `planned`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-003](SUB-003.md), [SUB-005](SUB-005.md), [SUB-020](SUB-020.md), [SUB-007](SUB-007.md), [SUB-009](SUB-009.md), [DEC-008](DEC-008.md)

Выделен при принятии [DEC-007](../../decisions/DEC-007.md); реализация не входит в DEC.

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high` (High).
- Обоснование: Ограничение нового приёма должно сохранять уже принятые переходы и резерв завершения под конкуренцией.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора](../MODELS.md).

## Один результат

Один ограничитель durable приёма новой работы API по согласованному бюджету.

## Критерии приёмки

- По [DEC-008](../../decisions/DEC-008.md), раздел «Диск и атомарное резервирование»: durable векторный ledger в БД API, атомарное списание с записью/outbox, идемпотентность/rollback/restart, резерв будущих шагов и отдельная оплата дублей publish. До ready квалифицировать верхние стоимости SQL/WAL/Kafka с запасом 2× и непересекающуюся квоту API в общих бюджетах SQL 80/24 GiB и Kafka 24/8 GiB. Неготовая таблица — явная предпосылка; независимый механизм сначала выделить в отдельный тикет. При отказе 503 capacity_exhausted до commit; отмена/исход принятой работы используют резерв. Проверить 200 конкурентов при квоте 100, затем завершение и повтор publish при закрытом обычном приёме. Возврат кредитов только после безопасного физического освобождения; нижние пороги SQL 72/Kafka 20 GiB.

- Используется точный контракт учёта ёмкости, лимитов и резерва из DEC-008; до ready он должен быть согласован. Мониторинг свободного места без атомарного ограничения параллельного приёма недостаточен.
- При достижении бюджета новые create/запросы новой работы отклоняются до commit с временной ошибкой, без подписки/workflow/outbox или занятого слота.
- Завершение/отмена/фиксация исхода уже принятой работы используют зарезервированный бюджет. Повтор запроса не расходует его повторно; ранее принятый SQL-outbox не удаляется.
- Состояние ограничителя и причина остановки предоставляются через интерфейс состояния для будущих health/readiness adapters; после безопасного освобождения ёмкости новый приём возобновляется без рестарта.
- Выполнены проверки ниже и [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальный PostgreSQL и управляемый бюджет: конкурентные запросы у границы, rollback, рестарт, временный отказ брокера, сохранность SQL-outbox и завершение/отмена принятой работы из резерва. После отказа нет новой подписки/слота/workflow.

## Не входит

Health endpoint, очистка Kafka/SQL, подбор бюджета и новый тип бизнес-перехода.

## Размер сессии

Кандидат на одну сессию после готовности зависимостей и соответствующего test harness. Перед ready проверить фактические интерфейсы по workflow. Отсутствующие adapters, экспорт прогресса или harness сначала выделить отдельными предпосылками; не реализовывать скрытно.
