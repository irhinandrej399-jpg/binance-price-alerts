## Один результат

Проверяемая durable привязка Kafka checkpoints matcher к поколению источника,
пригодная для чтения будущим exporter OPS-056 и сохраняемая при takeover.

## Критерии приёмки

- До ready описать точный контракт identity: логический consumer, поколение
  источника subscription-changes/prices и поколение SQL-проекции. Разделить
  рестарт/смену владельца, новый snapshot и замену Kafka-источника. Имена topic,
  endpoint, replica/member ID и fencing token не доказывают source incarnation.
  Выбрать проверяемый источник identity и способ его проверки. Если это требует
  несогласованного продуктового решения, выделить DEC до реализации.
- Собственная БД matcher хранит связь identity с соответствующим checkpoint;
  offset нельзя читать, записывать или продолжать как позицию другого источника.
  Сохранение/проверка не допускают окна между сменой binding и записью offset.
  Не подставлять текущую конфигурацию как происхождение исторической строки.
- Реальные Kafka входы и resume/bootstrap runtime используют эту привязку до
  обработки/подтверждения позиции. Пересозданный topic с прежним именем или иной
  источник с совпадающим диапазоном offsets не подтверждает старый checkpoint.
  Ошибка проверки/недоступность identity даёт явный отказ, без reset на latest.
- Рестарт/takeover в том же источнике сохраняют стабильный prices scope,
  Pending/canonical исходы и Prefix. Новый snapshot не переобозначает происхождение
  старой транспортной позиции. Replay C остаётся независимым от Kafka offset.
- Legacy/unbound checkpoint явно неподтверждён для cleaner; описать безопасную
  миграцию/запуск без автоматического присвоения старой строке нового источника.
  Старые writers не должны обходить binding. Старое состояние и Pending не
  удалять ради смены поколения; запрещённый переход должен давать явный отказ.
- Дать read-only интерфейс проверки identity вместе с Recover/Checkpoint для
  OPS-056 и документировать runtime конфигурацию, ограничения и воспроизведение.
- Выполнены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальные PostgreSQL/Kafka на готовом disposable runner: commit/rollback binding
и checkpoint; restart/takeover того же источника с Pending; неизвестная/неверная
identity и legacy строка; новый snapshot; замена источника при одинаковом имени
и диапазоне offsets; SQL/metadata fault; конкурентный старый writer без
продвижения позиции. Рабочие topics/БД не затрагивать.

## Не входит

RPC exporter, DeleteRecords, реестр обязательных consumers/retirement,
notifications, автоматическая миграция на другой Kafka-источник и нагрузка.

## Контракт для реализации дочерних задач

- Проверяемый кандидат identity: broker ClusterID + ненулевой TopicID + имя
  topic; partition задаётся отдельно. Получать metadata у Kafka без auto-create,
  сверять ожидаемые IDs и TopicID каждого fetch до dispatch (включая control
  records). Неподдерживаемая/нулевая identity и metadata fault — явный отказ.
  Точные публичные типы/ошибки закрепляет OPS-060. Проверка offsets или имени
  не заменяет доказательство источника. Клонирование broker storage с теми же
  IDs не различимо этим кандидатом; поддержку такого переноса не обещать.
- Логический prices consumer сохраняет нынешний environment/group/topic/partition
  и SQL scope при рестарте/takeover. ProjectionID и snapshot_id обозначают
  SQL-проекцию/её снимок; fencing token обозначает право записи. Эти значения
  не являются Kafka source generation и не заменяют её.
- Источник привязывается к transport checkpoint атомарно с первой доказанной
  позицией. SQL-replay C до Kafka позиции остаётся отдельной шкалой. Новый
  snapshot не переписывает provenance существующего offset; источник старого
  Pending также нельзя угадать по текущему config. Legacy/unbound состояние
  явно не подтверждено, не удаляется и автоматически не получает новые IDs.
- Смена источника вызывает отказ, а не новый scope/сброс offset/повторное
  использование старой Pending-позиции. Автоматическая миграция остаётся вне
  объёма. Если для безопасного продолжения понадобится изменить согласованные
  гарантии или разрешить перенос старых данных, сначала отдельный DEC.
