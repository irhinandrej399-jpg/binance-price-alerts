# OPS-002 — Измерять задержку от цены до trigger

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MAT-004](MAT-004.md), [SUB-013](SUB-013.md), [SUB-014](SUB-014.md), [OPS-045](OPS-045.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `medium` (Medium).
- Обоснование: Нужно корректно связать уже имеющиеся timestamps с метрикой и не вводить labels с неограниченной кардинальностью.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Метрика end-to-end latency с однозначными timestamps.

## Критерии приёмки

- По [ADR DEC-004](../../decisions/DEC-004.md): метрика ≤1 с заканчивается durable запросом работы при сохраняющемся условии. Подтверждённый успех, очередь и wait_condition измеряются отдельно.
- Можно проверить p99 ≤1 с на стенде; в labels нет user_id, subscription_id и chat_id.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Контрольный сценарий с известной задержкой попадает в ожидаемый bucket; задержки между сервисами не теряются.

## Не входит

Полный distributed tracing стек.

## Размер сессии

Оценка: **кандидат на одну сессию после закрытия зависимостей**, не подтверждённый `ready`.
Для старта нужны только эта карточка, применимые ADR, готовые интерфейсы из зависимостей и относящийся к поведению код. Если требуется выбрать протокол, реализовать недостающую зависимость или менять независимое поведение, карточка сначала уточняется либо делится по [сессионной проверке](../workflow.md#сессионная-проверка-перед-ready).
