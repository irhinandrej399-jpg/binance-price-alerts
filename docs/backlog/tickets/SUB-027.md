# SUB-027 — Подготовить адресата до лимитеров и проверить его при допуске

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-018](SUB-018.md), [NTF-005](NTF-005.md), [DEC-005](DEC-005.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Один защищённый протокол согласует адресата лимитера с финальным admission при конкурентной перепривязке, сохраняя идемпотентность и границы API.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

API-контракт позволяет notifications получить адресата для лимитеров без разрешения Telegram, а затем получить свежий допуск только для адресата, прошедшего лимитер. Это подготовка готового handler NTF-012, без реализации самого handler.

## Воспроизведение отсутствующей предпосылки

Обнаружено 4 ноября 2026 при сессионной проверке NTF-012. В `proto/api/v1/admission.proto` chat/version существуют только в AttemptPermission; запрос содержит лишь owner/subscription/workflow/request ID. `alerttriggered.Triggered` не передаёт адресата. Поэтому при первом claim нельзя пройти chat limiter до AdmitDelivery. Вызвать admission заранее и отложить его при отказе лимитера нельзя; replay исторического разрешения не перепроверяет цену/привязку.

## Критерии приёмки

- Защищённый интерфейс для notifications проверяет owner/subscription/workflow и возвращает текущие chat/version либо явное отсутствие канала без выдачи attempt/перехода sending. Подготовка не разрешает HTTP и не резервирует квоту; прямого доступа notifications к API БД нет.
- Финальный admission после обоих лимитеров сверяет подготовленный адресат/версию с текущими под теми же бизнес-блокировками, что SUB-017. При изменении не выдаёт разрешение на другой chat: caller заново готовит адресата, проходит оба лимитера и запрашивает свежий допуск. Новая цена читается готовым SUB-018.
- Поля подготовки являются только условием согласованности, не источником истины адресата. Исторический replay существующего request ID сохраняет прежнюю семантику; новый цикл/смена адресата использует новый request ID. Нельзя использовать replay как свежую проверку.
- Отсутствие канала, blocked прежней/новой версии, terminal, ошибочный workflow и unavailable не создают отправку и не теряют прежний workflow. Сохраняются DEC-004/005 и mTLS-изоляция SUB-018.
- TDD: реальный PostgreSQL и существующий mTLS harness проверяют подготовку без attempt, первый chat, перепривязку между подготовкой и финальным допуском (без permit на непролимитированный chat), повтор с новым адресатом, исчезновение канала, cancel, исторический replay после смены привязки, timeout/commit recovery. Fake HTTP не должен получать вызов по одному результату подготовки.
- Proto/generated code и README обновлены; `generate_proto.py --check`, профильные race-тесты, `check_postgres.py`, vet/build и `backlog.py check` проходят.

## Не входит

Handler/worker, новые лимитеры, изменение продуктовой политики канала, перенос адресата в событие, прямой доступ к чужой БД.

Кандидат на одну сессию: один протокол подготовки/проверки адресата поверх готового SUB-018 с существующими SQL/mTLS harness. До ready выбрать конкретную additive форму RPC/полей, сверить backward compatibility и сессионный объём; при необходимости разделить до реализации.
