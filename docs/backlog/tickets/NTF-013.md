# NTF-013 — Запустить ограниченный цикл notification worker

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [NTF-012](NTF-012.md)

Разделённый исходный тикет: [NTF-011](NTF-011.md).

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `medium` (Medium).
- Обоснование: Цикл использует готовый handler; задача ограничена параллелизмом, ожиданием пустой очереди и остановкой новых вызовов.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Один управляемый цикл вызывает готовый handler с заданным пределом параллелизма.

## Критерии приёмки

- Нет busy loop на пустой очереди; число вызовов ограничено; context запрещает начало новой работы.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Управляемый handler и часы проверяют пустую очередь, границу параллелизма и прекращение новых вызовов по context.

## Не входит

Новая логика попытки, backoff, leases и гарантии остановки HTTP-запроса.

## Размер сессии

Оценка: **кандидат на одну сессию после закрытия зависимостей**, не подтверждённый `ready`.
Для старта нужны только эта карточка, применимые ADR, готовые интерфейсы из зависимостей и относящийся к поведению код. Если требуется выбрать протокол, реализовать недостающую зависимость или менять независимое поведение, карточка сначала уточняется либо делится по [сессионной проверке](../workflow.md#сессионная-проверка-перед-ready).

## Готовый интерфейс из NTF-012

`handler.New(Config)` / `Handle(ctx, triggerID)` — один ограниченный проход.
Точный контракт: `internal/notifications/handler/README.md`. Выбирать due jobs,
pending reports также у stopped/terminal jobs и не назначенные channel blocks
текущего fence; discovery/условия — jobs/README.md. Handle сначала передаёт
ограниченную порцию reports, при непустой порции завершает проход без Claim.
Ошибка требует backoff; нет признака, разрешающего немедленный tight loop.

`*handler.PendingWrite` требует ограниченных повторов `Retry(freshContext)` с
backoff и сохранением объекта до записи известного исхода. Retry никогда не
вызывает Telegram/Claim/лимитеры. После потери процесса Claim восстанавливает
зарегистрированный исход как uncertain; внешний дубль остаётся возможным.
Перед остановкой процесса дать уже начатой записи результата отдельный
ограниченный context, даже если основной context отменён. Численные настройки
Policy/RecoveryInterval/ReportLimit и общего deadline задаются явно. Новую
логику HTTP/admission/retry-планов внутри worker не добавлять.
