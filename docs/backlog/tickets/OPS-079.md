# OPS-079 — Подключить метрики очереди к процессу notifications

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-003](OPS-003.md), [OPS-057](OPS-057.md), [OPS-074](OPS-074.md)

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `medium`.
- Обоснование: Узкое runtime wiring готового SQL exporter и admission decorator с существующими process fixtures.

Рекомендация, не переключение модели. [Условия выбора](../MODELS.md).

## Один результат

Работающий внутренний GET /metrics процесса notifications на существующем
HTTP listener с метриками OPS-003 и измерением реального admission client.

## Критерии приёмки

- Создать один metrics.New(store), обернуть им admission client до передачи
  handler.Config и смонтировать GET /metrics рядом с health/readiness.
  Сохранить существующие lifecycle, readiness withdrawal и shutdown joins.
- Ограничить время SQL collection через request context; отмена/timeout/ошибка
  дают 503 без частичных/старых метрик и текста SQL/credentials. Один лишь
  http.Server.WriteTimeout не заменяет deadline SQL операции.
- Endpoint доступен только во внутренней сети deployment; не публиковать
  новый порт и не открывать /metrics через Caddy. Labels остаются фиксированными,
  DB-wide gauges не суммировать по репликам. Описать команду внутреннего scrape.
- Готовая process/SQL fixture подтверждает HTTP metrics от runtime роли,
  pending/blocked и pending reports на контрольном наборе, histogram после
  admission; ошибка/отмена collection не зависает и не раскрывает секреты.
  Прежние health/readiness и shutdown проверки проходят.
