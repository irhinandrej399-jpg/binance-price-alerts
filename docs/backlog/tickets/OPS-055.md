# OPS-055 — Собрать минимальный процесс notifications

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [NTF-001](NTF-001.md), [NTF-012](NTF-012.md), [NTF-013](NTF-013.md), [OPS-008](OPS-008.md), [OPS-054](OPS-054.md), [DEC-010](DEC-010.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Intake, worker и reporter должны сохранять leases, SQL checkpoint и известный исход при ошибках и рестарте.

Это рекомендация, не смена модели; см. [MODELS](../MODELS.md).

## Один результат

Работающий cmd/notifications над готовыми intake/handler/worker с конфигурацией, mTLS и health, пригодный для отдельного OPS-011.

## Критерии приёмки

- Валидируются собственный DSN, HTTP_ADDR, Kafka/topic/group, API endpoints,
  mTLS identity/credentials, Telegram token/endpoint/timeout, явные retry policy,
  limiter и worker budgets. RecoveryInterval handler/worker согласован.
  Миграции отдельно; секреты и URL с токеном не попадают в ошибки/логи.
- Подключены готовые intake.New/Run/Close, jobs.Store, bot/chat limiters,
  telegram client, admissionrpc/resultrpc clients, reporter, handler и worker.
  SQL checkpoint остаётся источником intake resume; SQL job сохраняется до
  Kafka ack. Claim/CAS/новый admission/одна HTTP-попытка и PendingWrite
  не переизобретаются в cmd.
- OPS-008 подключён к listener, собственному pool.Ping, Worker.Running и
  инициализации. Readiness 503 до старта и после выхода компонента/ошибки SQL,
  200 после готовности; Telegram 429 не ломает liveness.
  Terminal intake/worker failure явно завершает владельца; startup/terminal
  cleanup отменяет и присоединяет компоненты до закрытия SQL/RPC ресурсов.
- Через OPS-054 запускается настоящий executable с race: canonical событие
  становится durable job, проходит оба лимитера/свежий admission/HTTP/result;
  проверяются success, 429/unknown, pending report и restart после SIGKILL
  с той же identity. Исходные IDs/bytes сохраняются, intake не дублирует job,
  recovery не повторяет уже подтверждённый успех. Возможность внешнего дубля
  после неизвестной отправки явно сохраняется.
- Config/startup failures и terminal intake error не дают ложной readiness;
  opt-in без конфигурации FAIL. Реальные PostgreSQL/Kafka/RPC/HTTP проверки,
  cleanup, README и общая применимая регрессия подтверждены.

## Сценарии TDD (Red → Green → Refactor)

Неверная конфигурация → startup failure; настоящий child → intake/доставка/health; потерянный ответ/SQL report и SIGKILL → durable recovery.

## Не входит

Обработка сигналов и graceful SIGTERM (OPS-011), новая бизнес-логика, runtime остальных сервисов, полный E2E, метрики/нагрузка.

## Размер сессии

Кандидат на одну сессию после проверки готовых интерфейсов и средств проверки.
Отсутствующие adapters и независимое поведение выделять отдельно по
[workflow](../workflow.md). Локальный профиль — [DEC-010](../../decisions/DEC-010.md).
