Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SET-009](SET-009.md), [CON-002](CON-002.md), [SUB-007](SUB-007.md), [DEC-007](DEC-007.md)

Выделен при сессионной проверке [MAT-008](MAT-008.md) 29 октября 2026.

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Read_committed регистрация, целые транзакции журнала и bounded чтение требуют проверки реальных брокерных границ и ошибок.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Правила выбора](../MODELS.md).

## Один результат

Один Kafka-адаптер subscription-changes с явной регистрацией до H и выдачей целых транзакций API-журнала с исходными транспортными позициями.

## Критерии приёмки

- Регистрация подтверждает назначенную единственную партицию subscription-changes и исходную позицию до возврата; MAT-008 вызывает её до BeginReplay/фиксации H. Хвост ограниченно буферизуется либо перечитывается с подтверждённой позиции; тихого reset на latest при утрате позиции нет.
- Чтение read_committed; auto-commit отсутствует. Сохраняются исходные JSON/event_id, key subscription_id, position/transaction_end и следующий Kafka offset. C не выводится из offset.
- На выходе только полная последовательная транзакция журнала, включая транзакцию из нескольких записей; aborted/open Kafka-транзакции не видны. Повторная публикация целого пакета с прежними C/event_id допустима.
- Неизвестная версия, повреждение/key mismatch, нарушение границы транзакции, потеря позиции/регистрации и превышение явных лимитов памяти дают видимую ошибку без skip/ack. Журнальный пропуск передаётся координатору для SQL-replay; он не маскируется как актуальность.
- Подтверждение транспортного прогресса разрешается caller только после durable сохранения; интерфейс не делает автоматический ack при выдаче. Ошибки/отмена отзывают пригодность регистрации, в том числе на пустом потоке.
- До ready закрепить Go-интерфейс регистрации/чтения/подтверждения и численные лимиты согласно DEC-008, согласованные с размерами целых пакетов SUB-007; превышение не режет и не пропускает пакет.
- На существующем disposable Kafka runner с race detector проверены регистрация/конкурентная публикация, commit/abort/open, дубли, целый multi-record пакет, отмена, недоступность/потеря cursor и лимиты. Интерфейс/воспроизведение документированы; выполнены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Регистрация до и во время публикации; открытая транзакция на момент регистрации, затем commit; abort; повтор relay; несколько событий одной API-транзакции; журнальный пропуск; плохой контракт/key; переполнение; отмена/потеря позиции. Никакой broker commit до явного подтверждения caller. Использовать готовые producer/runner/fault proxy, без нового независимого harness.

## Не входит

SQL-projection/replay и API ack, Latest/ценовой pricefeed, индекс/кандидаты, readiness и переключение поколений, consumer group/rebalance/fencing, runtime и нагрузка.

## Закреплённый контракт до ready

- `New(ctx, Config)`, однократный `Register(ctx) → *Registration`; `Start/Done/Err`, `Next(ctx) → Transaction`, `Confirm(nextOffset)`, `Close/Revoke`. Только direct assignment partition 0 topic с ровно одной партицией; регистрация фиксирует LSO до запуска чтения и возврата caller.
- Transaction хранит исходные JSON/key/envelope/after-image и позиции; выдаётся только после Kafka commit marker того же producer ID (epoch равен epoch записей либо +1 по KIP-890), ровно один полный пакет на Kafka-транзакцию SUB-007. Пропуск между целыми C виден caller по First/C и закрывается SQL-replay.
- ≤4 KiB payload, ≤1 024 records и ≤4 MiB payload всей очереди, включая сборку и выданную неподтверждённую транзакцию; key ≤256 bytes. Default 1 024, тестовый Buffer уменьшает предел. Fetch/decompressed batch ≤4 MiB, broker response ≤8 MiB, один concurrent fetch. Это профиль ниже 16 MiB прикладных буферов, не квалификация RSS/нагрузки.
- SUB-007 публикует пакеты произвольного размера, не режет их; превышение профиля Kafka-входа явно инвалидирует регистрацию без ack. Для таких пакетов координатор использует paginated SQL-replay; producer/SQL-контракт не меняется. Admission/квалификация размеров остаётся OPS-015.
- Не более одной выданной неподтверждённой Transaction. Confirm допустим только для её NextOffset после durable commit caller; освобождает очередь/локальный transport progress, не коммитит broker group offset. Durable SQL cursor авторитетен; consumer groups — MAT-010/011.
- Сессионная проверка: прямые зависимости/артефакты и существующие producer/fault proxy/runner доступны; одно поведение, продуктовых решений не требуется.
