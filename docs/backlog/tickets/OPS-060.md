# OPS-060 — Проверить поколение Kafka-источника на входах matcher

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MAT-015](MAT-015.md), [MAT-018](MAT-018.md), [SET-009](SET-009.md)

Разделённый исходный тикет: [OPS-059](OPS-059.md).

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Проверка broker metadata и TopicID каждого fetch требует закрыть гонку delete/recreate до dispatch на двух входах.

Это рекомендация, а не смена модели; см. [MODELS](../MODELS.md).

## Один результат

Один переиспользуемый контракт проверенного Kafka-источника, применённый к changefeed и pricefeed до выдачи записей вызывающему коду.

## Критерии приёмки

- Зафиксировать публичный тип source identity и ошибки: broker ClusterID,
  ненулевой TopicID, имя topic; partition отдельно. Сверять явно ожидаемую
  identity с broker metadata без auto-create, с deadline и отменой. Не считать
  endpoint, consumer group, member или token источником identity.
- Проверять TopicID в каждом PollRecords fetch до dispatch/декодирования,
  включая транзакционные control records. Не сворачивать fetch в Records до
  проверки. Ошибочная/нулевая identity либо недоступная metadata дают явный
  отказ и отмену reader, без fallback/reset. Metadata-проверка только при старте
  недостаточна; проверить смену topic во время работы уже открытого reader.
- changefeed Register/RegisterAt и pricefeed direct/group используют один
  контракт. Resume получает ожидаемую identity вместе с позицией. Регистрация,
  выдача assignment, Next и Confirm не должны пропускать обнаруженную смену
  источника. Не присваивать новой identity уже выданной позиции.
- Документировать интерфейс для OPS-061/062, источник ожидаемых IDs и границы
  доверия. Сохранить bounded buffers/read_committed/cancellation/join и прежние
  проверки partitions. Прямые тестовые readers не должны скрыто отключать
  проверку. SQL/runtime wiring выполняются следующими карточками.
- Выполнены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

На готовом disposable Kafka: правильные/неизвестные IDs, пустые metadata,
ошибка/отмена metadata, restart reader того же topic. Удалить и пересоздать
только собственный уникальный topic с тем же именем и диапазоном offsets:
старый reader и RegisterAt обязаны отказать до выдачи новой записи. Отдельно
проверить TopicID mismatch на границе fetch до dispatch, включая commit marker;
для контролируемой границы использовать существующий Config.Dialer и типы kmsg,
без создания отдельного универсального fault harness. Старые feed/group тесты
проходят с явной ожидаемой identity; реальные Kafka сценарии не заменять mocks.

## Не входит

SQL binding/миграции, конфигурация cmd/matcher, exporter, cleaner, перенос источника и нагрузка.

## Размер сессии

Кандидат после сессионной проверки готовых интерфейсов и средств проверки.
Использовать существующие disposable runners; новый harness и независимое
поведение не добавлять скрытно. Контракт источника — в OPS-059; изменяющие
гарантии продуктовые решения сначала выделять в DEC.
