# OPS-046 — Собрать минимальный процесс API для отмены и relay

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-005](SUB-005.md), [SUB-012](SUB-012.md), [IAM-005](IAM-005.md), [SUB-007](SUB-007.md), [SUB-009](SUB-009.md), [OPS-001](OPS-001.md), [DEC-010](DEC-010.md), [OPS-047](OPS-047.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Сборка одного процесса на готовых HTTP/SQL/Kafka интерфейсах;
  ошибки startup, владение ресурсами и завершение relay требуют проверки.

Это рекомендация, а не автоматическая смена модели. См. [MODELS](../MODELS.md).

## Один результат

Исполняемый локальный `cmd/api` с готовой HTTP-отменой подписки и двумя relay,
к которому OPS-004 сможет добавить и проверить ограниченную graceful остановку.

## Критерии приёмки

- Конфигурация адреса HTTP, собственной API-БД, Kafka topics и двух различных
  стабильных transactional.id проверяется до готовности; секреты не выводятся.
  Миграции выполняются существующим runner отдельно, runtime не читает чужие БД.
- Подключены существующие session/auth и handler отмены с journal/outbox,
  `/healthz` и `/readyz`; после инициализации readiness использует API pool.Ping
  с ограниченным бюджетом. Поведение и маршруты берутся из README компонентов.
- Оба существующих relay Run запускаются в том же процессе. Fencing/потеря
  lease и другие terminal ошибки завершают владельца; ошибки запуска не
  маскируются успешной готовностью. Ресурсы закрываются при ошибке startup.
- Есть воспроизводимая проверка запуска отдельного процесса на disposable
  PostgreSQL/Kafka: заранее созданные штатной fixture аккаунт/сессия/подписка,
  аутентифицированная отмена через HTTP, durable cancelled и исходное событие
  subscription-changes у read_committed consumer; delivery relay проверяется
  с готовым outbox fixture. Рабочие БД/topics не используются.
- Команда запуска и настройки описаны без секретов. Минимальный состав
  endpoints явно указан; компиляция сама по себе не считается запуском API.

## Сценарии TDD (Red → Green → Refactor)

Неверная конфигурация и отказ bind/startup; readiness до/после инициализации;
реальная HTTP-отмена и отправка durable outbox; terminal отказ relay.
Использовать существующие disposable runners и fixtures; если отсутствует
самостоятельный процессный harness, сначала выделить его отдельной зависимостью.

## Не входит

Graceful SIGTERM/drain и сценарий SIGTERM во время транзакции (OPS-004),
регистрация/вход/создание подписки и другие HTTP endpoints, внутренние RPC,
полный runtime API для E2E, другие процессы, нагрузка и capacity qualification.
Это минимальный процесс для OPS-004, а не объявление готовности полного API.

## Размер сессии

Кандидат на одну сессию; перед ready проверить фактические интерфейсы и
средства запуска процесса. Отсутствующие adapters/harness не прятать в wiring.
Применяются [workflow](../workflow.md) и [DEC-010](../../decisions/DEC-010.md).

## Реализация OPS-046 — 6 ноября 2026

- cmd/api/main.go: обязательная конфигурация HTTP/API DSN/Kafka/topics и двух
  различных stable transactional.id; API database/роль api_runtime, безопасные
  фиксированные ошибки. Миграции запускаются отдельно. Один API pool,
  ограниченный startup, проверка HTTP schema и по одному Step обеих очередей
  до HTTP readiness. Ошибка bind/startup освобождает открытые ресурсы.
- Подключены DELETE /v1/subscriptions/{id} через auth/session и готовый cancel
  handler с journal, /healthz, /readyz с API pool.Ping и бюджетом 1 с.
  Оба relay Run работают в том же процессе. Выход любого обязательного
  компонента отменяет и дожидается соседей, закрывает HTTP и pool. Terminal
  ошибки библиотек (включая fencing/lease loss) не перезапускают владельца.
- cmd/api/main_test.go: конфигурация/разделение IDs и topics, отказ чужого DSN,
  остановка и ожидание двух соседей при выходе каждого из трёх компонентов.
  process_test.go: отказ bind и освобождение listener после startup failure;
  настоящий executable с race на disposable API PostgreSQL/Kafka, штатная
  Seed fixture, readiness/health, unauthenticated 401, authenticated cancel,
  durable cancelled/version и исходные Kafka key/value двух событий.
- Read_committed consumer сверяет точные bytes с canonical journal и delivery
  fixture (включая исходные event_id). Затем тест добавляет malformed journal
  штатно разрешённым INSERT только в disposable dataset: terminal Run должен
  завершить процесс; повторный startup обязан выйти до readiness. Отдельно
  проверен отказ подключения к БД. До/после initialization и budget/cancellation
  самого health покрыты готовыми тестами OPS-001, включёнными в race-регрессию.
- cmd/api/README.md и ссылка в корневом README описывают env/запуск/проверку,
  минимальные endpoints и границы. Первый Step при pending outbox требует
  доступного брокера; пустая очередь не вызывает Kafka. При busy lease startup
  завершается ошибкой. После startup transient сбои повторяются внутри Run;
  readiness использует только API-БД.
