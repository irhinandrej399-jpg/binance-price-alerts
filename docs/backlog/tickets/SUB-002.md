# SUB-002 — Обеспечить лимит 15 при конкурентном создании

Статус: `planned`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SUB-001](SUB-001.md), [DEC-004](DEC-004.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Лимит 15 — конкурентный инвариант БД: нужно доказать ограничение при множестве одновременных созданий.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Одна атомарная операция резервирования активного слота и создания подписки.

## Критерии приёмки

- По [DEC-006](../../decisions/DEC-006.md): READ COMMITTED и блокировка строки пользователя сериализуют проверку Telegram-привязки и квоты; счётчик 0..15 и подписка имеют одну транзакционную судьбу. Проверить 14 + два конкурентных создания. Блокировка квоты относится к пользователю; краткая сериализация журнала добавляется в SUB-011 отдельно.

- По [ADR DEC-004](../../decisions/DEC-004.md): лимит включает pending_delivery/sending/delivery_blocked; возврат к ожиданию не освобождает слот, delivered/cancelled освобождают ровно один раз.
- Число активных подписок пользователя не превышает 15; квоты разных пользователей не используют одну глобальную блокировку.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Запустить 30 конкурентных созданий одного пользователя: максимум 15 успехов; отмена освобождает один слот.

## Не входит

Квоты по тарифам.

## Размер сессии

Оценка: **кандидат на одну сессию после закрытия зависимостей**, не подтверждённый `ready`.
Для старта нужны только эта карточка, применимые ADR, готовые интерфейсы из зависимостей и относящийся к поведению код. Если требуется выбрать протокол, реализовать недостающую зависимость или менять независимое поведение, карточка сначала уточняется либо делится по [сессионной проверке](../workflow.md#сессионная-проверка-перед-ready).
