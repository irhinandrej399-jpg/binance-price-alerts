# OPS-047 — Подготовить disposable harness отдельного процесса API

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [SET-009](SET-009.md), [SUB-005](SUB-005.md), [SUB-012](SUB-012.md), [IAM-005](IAM-005.md), [SUB-009](SUB-009.md), [DEC-010](DEC-010.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Изоляция disposable ресурсов, владение child-процессом,
  deadlines и cleanup при отказах; продуктовый runtime сюда не входит.

Это рекомендация, а не автоматическая смена модели. См. [MODELS](../MODELS.md).

## Один результат

Переиспользуемый тестовый harness, который предоставляет отдельному процессу
изолированные API PostgreSQL и Kafka, fixture и ограниченный lifecycle.
OPS-046 использует его для проверки настоящего cmd/api.

## Критерии приёмки

- На базе существующих compose/init и scripts/migrate.py поднимаются disposable
  PostgreSQL/Kafka с уникальными либо сериализованными ресурсами, loopback
  портами и префиксными topics. Рабочие проекты/БД/topics не адресуются.
  Дочернему процессу передаётся только DSN API; секреты не выводятся и не
  передаются в argv. Миграции применяются отдельно от child.
- Есть доступная тестам fixture аккаунта, действующей session, активной
  подписки с квотой через готовые API-интерфейсы и delivery outbox на основе
  существующих fixtures. Возвращаются ID/token и исходные bytes событий
  для проверок; fixture не реализует новое продуктовое поведение.
- Harness запускает заданный executable отдельным процессом, предоставляет
  loopback HTTP адрес и env, ждёт readiness с deadline и наблюдением раннего
  exit. Есть ограниченные stop/kill/wait и cleanup child/volumes при ошибке
  старта, timeout, ошибке проверки и штатном завершении.
- Harness проверен на минимальном тестовом child: успешный старт/HTTP probe,
  ранний ненулевой exit и timeout. Никакой зависимости от OPS-046, регистрации,
  Telegram, Binance или runtime остальных сервисов нет. Child остаётся
  тестовым инструментом, не временной реализацией cmd/api.
- Реальные disposable PostgreSQL/Kafka и fixture проверяются в отдельном
  воспроизводимом прогоне; read_committed consumer может сопоставить исходные
  key/value/event_id с fixture. Cleanup обоих стендов подтверждён.
- README описывает команду, интерфейс запуска child и fixture для OPS-046;
  критерии HTTP-отмены/relay самого cmd/api остаются в OPS-046.

## Сценарии TDD (Red → Green → Refactor)

Успешный child; ранний exit вместо readiness; зависший child/readiness timeout;
cleanup при ошибке callback. Fixture проверяется на реальной API-БД, consumer —
на disposable Kafka. Использовать существующие средства SET-009, не писать
новые compose или fake broker. Реальный cmd/api для готовности harness не нужен.

## Не входит

Wiring cmd/api, продуктовая graceful SIGTERM/drain, запуск четырёх сервисов,
новые endpoints, capacity qualification и нагрузка.

## Размер сессии

Один тестовый lifecycle и его fixture на готовой инфраструктуре. Перед ready
проверить интерфейсы, пригодность существующих runners и отсутствие циклической
зависимости от runtime. Применяется [workflow](../workflow.md).

## Ход работы

- `internal/testutil/apiprocess/process.go`: With/Config/Process, отдельный
  Unix child process group, случайный loopback HTTP_ADDR, явное окружение,
  readiness `/readyz` с deadline и early exit. TERM/kill/wait ограничены;
  callback error/panic/Goexit и cancellation завершают child. Вывод child
  отбрасывается; ошибки не содержат argv/env. PID registry позволяет внешнему
  runner убрать child после аварии/timeout владельца без Go defers.
- `fixture.go`: account.Create/session.Issue и LockQuota/Create создают
  владельца, session и две подписки с reserved slots. Тестовая Telegram binding
  задана как в прежних quota fixtures. Первая подписка active; для второй
  готовый RequestDelivery сохраняет canonical workflow, journal и delivery
  outbox. Fixture возвращает ID/token и исходные delivery key/value/event_id.
  Частичный seed не переиспользуется, весь disposable dataset удаляется.
- `scripts/check_api_process.py`: уникальные PostgreSQL/Kafka projects,
  случайные loopback ports/topics, отдельные API migrations через migrate.py,
  только API runtime DSN в env. Все команды имеют timeout; cleanup обоих
  проектов проверяет containers/volumes/networks по exact project labels.
  `--package` позволяет использовать среду для будущих process tests OPS-046.
- `process_test.go`: успешный HTTP probe; callback error; ранний exit=23;
  несуществующий executable; child, игнорирующий TERM, с readiness timeout;
  cancellation после readiness. После lifecycle/timeout/early exit проверяется
  отсутствие PID; lifecycle проверяет создание/удаление registry marker и
  отсутствие у child родительского секрета/чужого owner DSN.
- `integration_test.go`: реальная session.Verify, active state, квота=2 и два
  reserved slots, canonical workflow/event identity, отдельный child с API
  PostgreSQL. Родитель вызывает готовый delivery relay; независимый
  read_committed consumer сравнивает исходные key/value/event_id с fixture.
- `testdata/ownerexit/owner_test.go`: намеренно аварийный владелец выходит
  с кодом 19 после готовности child, обходя defers. Не входит в `go test ./...`.
  README описывает интерфейсы/команды, env/fixture и границы OPS-046/004.
