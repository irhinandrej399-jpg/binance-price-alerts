# OPS-054 — Подготовить disposable окружение процесса notifications

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-047](OPS-047.md), [NTF-001](NTF-001.md), [NTF-012](NTF-012.md), [NTF-013](NTF-013.md), [SUB-018](SUB-018.md), [SUB-020](SUB-020.md), [DEC-010](DEC-010.md)

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Изоляция child и управляемые границы HTTP/SQL/RPC должны позволить доказать durable recovery без внешних Telegram запросов.

Это рекомендация, не смена модели; см. [MODELS](../MODELS.md).

## Один результат

Notifications fixture/runner над готовым apiprocess lifecycle для OPS-055 и OPS-011.

## Критерии приёмки

- Переиспользованы apiprocess lifecycle/PID registry и существующий disposable
  PostgreSQL/Kafka runner; уникальные проекты/topics, deadlines и cleanup.
  Применяются только API и notifications migrations. Child получает только
  notifications DSN и явный allowlist Kafka/RPC/HTTP/PKI; API DSN только у fixture.
  Секреты не логируются, child не имеет доступа к чужим БД.
- Родительская API fixture создаёт канонический workflow/outbox готовыми
  интерфейсами; публикация через готовый relay даёт исходные AlertTriggered
  bytes. Настоящие Admission/PrepareRecipient и Result RPC используют API БД,
  mTLS и управляемый Latest по готовому контракту. Не подменять admission
  разрешением из события или прямым чтением API БД ребёнком.
- Локальный управляемый Telegram HTTP endpoint использует готовый wire-контракт:
  наблюдение входа, задержка/обрыв ответа и подтверждённый message_id; без
  реального bot token. Границы позволяют проверить OPS-011 до Send, во время
  Send и после ответа. Это узкая fixture, общий E2E fake остаётся E2E-004.
- Независимые observers видят SQL job/checkpoint/lease/attempt/outcomes/reports,
  canonical API result и broker offsets. Минимальный тестовый child проверяет
  свою БД/Kafka/mTLS/HTTP и startup failure; не реализует продуктовый worker.
- Реальный disposable/race прогон проверяет fixture, исходные bytes, изоляцию,
  ранний exit и аварийный owner exit cleanup. README описывает интерфейс,
  --package для cmd/notifications и ограничения. Без opt-in SKIP, с opt-in
  отсутствующая конфигурация — FAIL. Новый lifecycle не создаётся.

## Сценарии TDD (Red → Green → Refactor)

Тестовый child → подключение к своей БД/RPC/Kafka/HTTP; canonical workflow и наблюдение исходов; startup failure и owner exit cleanup.

## Не входит

cmd/notifications, продуктовый SIGTERM, новая политика попыток, общий E2E fake, четыре процесса и нагрузка.

[workflow](../workflow.md). Локальный профиль — [DEC-010](../../decisions/DEC-010.md).
