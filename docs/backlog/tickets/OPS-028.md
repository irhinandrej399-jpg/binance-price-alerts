# OPS-028 — Подготовить API fixture продолжения notifications с исходными ID

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [OPS-024](OPS-024.md), [OPS-025](OPS-025.md), [NTF-014](NTF-014.md), [NTF-012](NTF-012.md)

Выделен при сессионной проверке OPS-026 5 ноября 2026: frozen journal matcher
не восстанавливает канонические подписки и разрешения API для notifications RPC.

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high` (High).
- Обоснование: Восстановление межсервисного fixture требует сохранить исходные идентичности, границы состояния и известность попыток без оживления старых разрешений.

Это рекомендация, а не переключение модели. [Условия выбора](../MODELS.md).

## Один результат

Проверенный API-owned setup fixture для OPS-026, сохраняющий provenance исходных
OPS-024/run-a2 → OPS-025/run-a3 ID/bytes и позволяющий настоящие notifications RPC.

## Критерии приёмки

- Зафиксировать вход и SHA256 исходного OPS-024/run-a2/identities.json и связь
  с OPS-025/run-a3. Использовать все четыре исходных AlertTriggered и пять
  read_committed delivery records; bytes/event/owner/subscription/trigger ID
  не переписывать. Fixture не обращается к рабочим БД и внешним Binance/Telegram.
- Подготовить API-owned setup через api_runtime на disposable БД с текущими
  миграциями: согласованные user/channel/quota/subscription/workflow и данные
  разрешений для заявленных сценариев. Явно описать воспроизводимую границу
  истории, а не считать финальный journal дампом текущих таблиц. Setup-импорт
  является инфраструктурным fixture, не новым продуктовым endpoint/переходом.
- Для reporter проверить реальный loopback mTLS SaveDeliveryResult по исходным
  attempt ID: API знает owner/subscription/workflow/permit, повтор после потери
  commit-ответа идемпотентен. Использовать готовые fault/TLS helpers; notifications
  читает только свою SQL БД. Проверить соответствие binding version/fence/response
  исходным данным, недостающие поля вывести явно и валидировать, не выдумывать
  незаписанное состояние как исторический факт.
- Для handler определить отдельную исходную границу до доставки: PrepareRecipient
  и новый AdmitDelivery проходят на тех же source subscription/trigger, свежая
  контрольная quote возвращается готовым локальным adapter. Новые attempt ID
  являются новыми разрешениями и явно связаны с исходными event/trigger/attempt;
  исходные permits с истёкшим TTL никогда не разрешают HTTP. Исторический replay
  и новый допуск не смешиваются в одном несовместимом состоянии fixture;
  при необходимости использовать отдельные чистые datasets/прогоны.
- Проверить fixture на двух чистых disposable состояниях, сохранять проверяемое
  evidence связей/границ/версий и cleanup. Отвергать чужой hash, несовпадение
  event/trigger/owner и ошибку восстановления; не обходить production проверки
  admission/result и не ослаблять права runtime. Сохранить команды и инструкцию
  вызова setup из существующего OPS-023 protocol driver.

## Проверка

Инфраструктурная проверка fixture на реальном disposable PostgreSQL с текущими
миграциями и готовом loopback mTLS; необходимые Kafka records берутся из
сохранённых bytes. Подходящие отрицательные проверки provenance/границы истории.
Полный нагрузочный/race suite не заменяет проверку fixture. Реальные сообщения
не отправлять; недоступную проверку не обозначать как успех.

## Не входит

Manifest/физические измерения OPS-026 и сводка стоимости, новый runner/collector,
новые бизнес-переходы/миграции, runtime четырёх процессов, исправление OPS-027.
