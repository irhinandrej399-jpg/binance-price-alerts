# OPS-056 — Экспортировать durable Kafka-прогресс matcher

Статус: `done`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MAT-011](MAT-011.md), [MAT-009](MAT-009.md), [SET-007](SET-007.md), [SET-008](SET-008.md), [OPS-053](OPS-053.md), [OPS-062](OPS-062.md)

## Модель для сессии

- Модель: `gpt-6.1-sol`.
- Уровень размышления: `high` (High).
- Обоснование: Согласованное чтение SQL-прогресса и идентичности потребителя необходимо для необратимой очистки, без доступа cleaner к чужой БД.

Это рекомендация, а не смена модели; см. [MODELS](../MODELS.md).

## Один результат

Защищённый read-only unary gRPC экспорт авторитетных Kafka next-offsets matcher для будущего OPS-014.

## Критерии приёмки

- Использовать существующие projection.Recover и pricework.Checkpoint и собственную БД matcher. Не выводить offset из C, broker commit, health lag, текущего назначения или локального Confirm.
- Запрос явно задаёт стабильного логического consumer, ожидаемую идентичность поколения/источника, topic и partition; ответ связывает подтверждённый SQL next-offset с этой идентичностью. Replica/member ID и fencing token сами по себе не заменяют логического consumer. Рестарт/передача партиции сохраняют прогресс.
- Для subscription-changes учитывать зарегистрированные обязательные проекции, для prices — стабильный scope и partition. Не выбирать произвольную более продвинутую проекцию и не объявлять SQL-replay C Kafka offset. Отсутствующий Kafka checkpoint, несовпадение поколения/источника или SQL-ошибка дают явный неподтверждённый результат, запрещающий очистку; не синтезировать 0/latest.
- Смена поколения/повторный bootstrap не должны выдавать checkpoint другого поколения как прежний. Точная идентичность и правила её проверки документируются до реализации; если необходим отдельный протокол lifecycle, выделить предпосылку до ready. Реестр обязательных потребителей/его сериализация с DeleteRecords остаются OPS-014.
- Использовать Protobuf/генерацию SET-007 и mTLS deny-by-default SET-008, отдельное явно настроенное право cleaner на чтение. Ограничить запрос/ответ и deadline с отменой SQL. Подключить сервер в cmd/matcher с явной конфигурацией и существующим shutdown/join.
- Cleaner не получает matcher DSN, запрос не создаёт и не изменяет checkpoint/проекцию, не снимает replay-pin. Документировать wire/runtime контракт и способы воспроизведения.
- Выполнены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Реальный PostgreSQL и loopback mTLS: durable commit/rollback, Pending без продвижения Prefix, разные scope/проекции, неизвестная идентичность/поколение, SQL fault, deadline, запрет чужому caller; restart/failover сохраняют подтверждённую позицию. Проверить runtime wiring и воспроизводимость генерации.

## Не входит

DeleteRecords, реестр и вывод потребителей из эксплуатации, экспорт notifications, SQL cleaner и нагрузка.

Кандидат на одну сессию после проверки контрактов и средств проверки по [workflow](../workflow.md). Недостающие adapters/lifecycle выделять до ready, не выполнять несколько результатов скрытно.

  поколению источника. `projection.Recover` читает snapshot_id/C/topic/partition/
  next_offset; snapshot_id — происхождение SQL-снимка, а не Kafka topic incarnation.

  partitions; источник subscription-changes не является частью этого ID.
  `changefeed.singlePartition` проверяет наличие одной partition, но не сравнивает
  durable поколение topic. Проверка диапазона offsets в RegisterAt также не
  доказывает поколение источника.
- Контрпример по коду (без destructive эксперимента): сохранить checkpoint N,
  заменить Kafka-источник с теми же именами topics и повторно использовать
  прежние environment/group/replica/parts. Аргументы Recover/Checkpoint и SQL
  ключи остаются прежними; оба read API вернут прежний N. При диапазоне нового
  лога, включающем N, проверка RegisterAt не отличает источники. Это не отчёт о
  реальном пересоздании Kafka; рабочие topics/БД не изменялись.
- Нельзя дополнить ответ identity из текущего конфига: это приписало бы старому
  checkpoint недоказанное происхождение. Token/member/health/C проблему не
  решают. Постоянный отказ для всех запросов также не выполняет результат.
- Выделена предпосылка [OPS-059](OPS-059.md): durable привязка checkpoint matcher
  к поколению Kafka-источника и проверка этой привязки на write/resume путях.
  Реестр обязательных consumers и сериализация с DeleteRecords остаются OPS-014;
  OPS-059 не выводит исторические проекции из эксплуатации.

## Повторная сессионная проверка и контракт — 7 ноября 2026

- Отслеживаемые файлы без diff; прежние untracked исследования сохранены; прямые зависимости done, sourcebound Recover и
  ReadCheckpoint доступны после OPS-061/062/063. Готовы PostgreSQL runner,
  loopback mTLS grpctest и process fixture matcher. Readiness пройдена.
- Один запрос читает ровно один указанный logical consumer: для changes это
  точный durable projection_id (SQL generation, а не имя replica/member), для
  prices — точный стабильный scope. kind различает пространства имён.
  Consumer ID сохраняется в ответе вместе с kind/source/topic/partition/next.
  Не выбирать projection по текущему назначению, max offset или health.
- Cleaner OPS-014 обязан запросить ВСЕ зарегистрированные обязательные
  projections/scopes и взять минимум по source/topic/partition; ответ одного
  consumer не подтверждает полноту реестра. Реестр, retirement/bootstrap lifecycle
  и сериализация с DeleteRecords здесь не создаются. Историческую projection
  можно читать после revoke; отсутствие cursor блокирует очистку.
- Source = ClusterID + 16-byte TopicID + topic, partition отдельна. Ожидание
  из запроса сравнивается с SQL provenance, никогда не подставляется вместо неё.
  SnapshotID и C не являются source либо Kafka offset.
- Unary MatcherProgress/ReadProgress: один consumer, строки ID/topic <=256 байт,
  ClusterID <=256, TopicID ровно 16, partition >=0. Сообщения <=4096 байт,
  SQL/RPC budget 1 секунда с наследованием более короткого caller deadline.
  InvalidArgument для malformed; FailedPrecondition для отсутствия cursor,
  legacy либо source/topic/partition mismatch; Unavailable для SQL fault;
  DeadlineExceeded/Canceled для отмены. Только успешный RPC с presence next_offset
  является подтверждением; ошибка не несёт offset, 0/latest не синтезируются.
- Runtime: отдельные обязательные MATCHER_RPC_ADDR, MATCHER_RPC_CERT_FILE,
  MATCHER_RPC_KEY_FILE, CLEANER_SERVICE_URI; RPC_CA_FILE для client CA.
  Единственное право cleaner — ReadProgress. При shutdown Stop отменяет RPC,
  SQL завершается до pool.Close, Serve присоединяется.
