# MAT-010 — Назначить партиции двум работающим matcher

Статус: `planned`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MAT-005](MAT-005.md), [DEC-007](DEC-007.md)

Разделённый исходный тикет: [MAT-006](MAT-006.md).

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Назначение партиций двум репликам должно сохранять порядок одной пары и исключать работу без полномочий.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Нормальное распределение партиций между двумя репликами по выбранному механизму брокера.

## Критерии приёмки

- По [DEC-007](../../decisions/DEC-007.md): Kafka consumer group назначает фиксированные ценовые партиции, пары не перемещаются при обычном rebalance. Назначение связывается с durable монотонным fencing token в БД matcher; update проекции/checkpoint допускается только текущему token. Это условная SQL-запись назначения, не отдельная система distributed locks; failover проверяется MAT-011.

- Одна пара сохраняет необходимый порядок; реплика обрабатывает только назначенную ей работу.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Две живые реплики обрабатывают контролируемый набор пар, без пересечения владения в согласованной модели.

## Не входит

Failover, новый механизм распределённых locks и масштабирование горячей пары.

## Размер сессии

Оценка: **кандидат на одну сессию после закрытия зависимостей**, не подтверждённый `ready`.
Для старта нужны только эта карточка, применимые ADR, готовые интерфейсы из зависимостей и относящийся к поведению код. Если требуется выбрать протокол, реализовать недостающую зависимость или менять независимое поведение, карточка сначала уточняется либо делится по [сессионной проверке](../workflow.md#сессионная-проверка-перед-ready).
