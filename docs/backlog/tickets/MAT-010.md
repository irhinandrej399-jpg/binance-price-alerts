# MAT-010 — Назначить партиции двум работающим matcher

Статус: `planned`. Приоритет определяется зависимостями, а не номером.

Зависимости: [MAT-005](MAT-005.md), [DEC-007](DEC-007.md), [MAT-017](MAT-017.md), [MAT-018](MAT-018.md), [MAT-019](MAT-019.md)

Разделённый исходный тикет: [MAT-006](MAT-006.md).

## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Назначение партиций двум репликам должно сохранять порядок одной пары и исключать работу без полномочий.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Нормальное распределение партиций между двумя репликами: интеграция готового Kafka group-адаптера MAT-018 с защищёнными SQL-записями MAT-017 и handler/recovery MAT-004/005. SQL fencing и Kafka group готовы в MAT-017/018. Поддержка назначенных пар в полной live-view выделена в MAT-019 после повторной сессионной проверки.

## Критерии приёмки

- По [DEC-007](../../decisions/DEC-007.md): Kafka consumer group назначает фиксированные ценовые партиции, пары не перемещаются при обычном rebalance. Назначение связывается с durable монотонным fencing token в БД matcher; update проекции/checkpoint допускается только текущему token. Это условная SQL-запись назначения, не отдельная система distributed locks; failover проверяется MAT-011.

- Одна пара сохраняет необходимый порядок; реплика обрабатывает только назначенную ей работу.
- Выполнена указанная ниже проверка; соблюдены [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

Две живые реплики обрабатывают контролируемый набор пар, без пересечения владения в согласованной модели. Использовать готовый совместный disposable runner `KAFKA_RUN_POSTGRES=1 bash infra/kafka/verify-go.sh`.

- Каждое Kafka-назначение получает SQL token до начала работы; до восстановления проекции/Latest и Pending реплика не ready. Pricework scope и projection ID связываются с устойчивой идентичностью работы, а не PID/token.
- Пары маршрутизируются тем же фиксированным отображением, что producer; одна партиция сериализуется одним владельцем. Проекция подписок сохраняет собственные C и transport cursor, не подменяется ценовым offset.
- Непрерывный ценовой Prefix учитывает все прочитанные read_committed записи партиции, включая пары без подписок. Начальная Latest не получает выдуманный offset; broker commit не обгоняет SQL Complete.
- Изменение назначения отзывает старые подключения/готовность; отказное восстановление и запоздалые действия старого владельца проверяются отдельно в MAT-011.

## Не входит

Failover (MAT-011), реализация SQL fencing (MAT-017), реализация Kafka group-источника (MAT-018), новый механизм распределённых locks, масштабирование горячей пары и подключение всех сервисов в cmd.

## Размер сессии

Оценка: **кандидат на одну сессию после закрытия зависимостей**, не подтверждённый `ready`.
Для старта нужны только эта карточка, применимые ADR, готовые интерфейсы из зависимостей и относящийся к поведению код. Если требуется выбрать протокол, реализовать недостающую зависимость или менять независимое поведение, карточка сначала уточняется либо делится по [сессионной проверке](../workflow.md#сессионная-проверка-перед-ready).

## Сессионная проверка

29 октября 2026: MAT-005 и DEC-007 done подтверждены кодом Recover/Resume, pricework и принятым ADR. Исходное дерево чистое. В ready задача не переведена: обнаружены две отсутствующие независимые предпосылки.

- `internal/matcher/pricefeed/feed.go`: New использует AddConsumePartitions, clientOptions прямо исключает consumer group; Revoke вызывается внешним владельцем. Group lifecycle и broker commit ещё отсутствуют. Dispatch пропускает пары без регистрации, поэтому очередь регистраций сама по себе не доказывает общий Prefix.
- `internal/matcher/pricework/{work,operations}.go`, `internal/matcher/projection/{projection,replay}.go`, `migrations/matcher/004_price_work.sql`: Store содержит pool и scope/id, SQL-транзакции не проверяют assignment token. Одна предварительная проверка token вне транзакции не исключит запоздалый commit.
- Проекция хранит все подписки по projection ID и отдельный C; pricework хранит работу по scope и ценовые checkpoints по topic/partition. Их идентичности нужно явно связать с назначением, не смешивая шкалы и не превращая каждую ценовую партицию в отдельную партицию subscription-changes.

SQL-защита выделена в MAT-017, group-источник — в MAT-018. MAT-010 оставлен planned как интеграция их готовых интерфейсов. ORDER и индекс синхронизируются; дочерняя реализация в этой сессии не начинается.

Повторная проверка 29 октября 2026 после завершения MAT-017/018: обе предпосылки подтверждены текущими интерфейсами NewFenced, GroupConfig.Prepare, Assignment.Register/Next/Confirm и наличием тестов зависимостей (в этой сессии не перезапускались). Исходное дерево чистое. Найдена ещё одна отсутствующая предпосылка в live-view:

- `internal/matcher/live/coordinator.go`: Config не принимает назначение; Run после полного Walk вызывает ensureQuote для всех active пар; update подключает любую active пару после replay. Current и список подключений также не имеют ограничения назначения.
- `internal/matcher/pricefeed/group.go`: Assignment.Register проверяет PairPartition и делегирует Source.Register; `internal/matcher/pricefeed/feed.go` отвергает `!s.assigned[partition]` с ErrConfig. Полная проекция с активными подписками в партициях обеих реплик неизбежно потребует чужое подключение и сорвёт Run одной из них.
- Подставить пустую/фиктивную цену для чужой пары нельзя: Current должен запрещать чужую работу. Фильтровать durable Walk/replay также нельзя: это нарушит полный replica-local C/after-image и контракт MAT-017. Отдельный direct reader обошёл бы group-владение.

Нужный независимый результат — ограниченная назначением live-view с полным SQL-replay, restart и lifecycle/readiness. Он выделен в MAT-019 перед MAT-010; MAT-010 остаётся planned. Обработка полного потока пар без подписок, связь transport position с устойчивым work key и доказательство Prefix остаются в MAT-010, не считаются реализованными MAT-019.
