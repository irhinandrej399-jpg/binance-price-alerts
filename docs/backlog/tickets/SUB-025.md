## Модель для сессии

- Модель: `gpt-6.1-sol` (GPT-6.1 Sol).
- Уровень размышления: `high` (High).
- Обоснование: Сквозное сохранение владельца в after-image требует проверки всех писателей журнала, совместимости ранее сохранённых событий и snapshot → replay без потери идентичности.

Это рекомендация для выбора перед запуском, а не автоматическая смена модели. [Условия выбора и повышения уровня](../MODELS.md).

## Один результат

Владелец канонической подписки доступен matcher из durable after-image как для новой live-подписки, так и после обновления подписки из снимка; канонический RequestDelivery получает оба ID без доступа к чужой БД.

## Критерии приёмки

- Контракт SubscriptionChanged передаёт owner подписки из канонического Record API. Его передают все существующие production-писатели: создание, отмена, запрос workflow, допуск и фиксация исхода. Владелец replay/snapshot pin и mTLS principal не подменяют владельца подписки.
- Journal/outbox, SQL-replay и Kafka relay сохраняют идентичность владельца вместе с неизменяемыми байтами/ID; версия подписки, C и транспортные offsets остаются независимыми. Дубли и terminal tombstones не откатывают владельца/версию.
- `projection.ReadImage` даёт owner как после snapshot Initialize, так и после более нового Changed, включая новую подписку, которой в снимке не было. Owner читается после повторного открытия pool; одного сохранения в памяти/старом snapshot недостаточно.
- Явно описана и проверена совместимость с уже сохранёнными событиями/проекциями без owner: отсутствие owner не приводит к выдуманному ID, успешному ack непригодного кандидата или обходу SUB-014. До ready проверить необходимость версии контракта/миграции и безопасного bootstrap; не переписывать immutable журнал. Если требуется отдельный самостоятельный механизм миграции, сначала выделить его как предпосылку, не прятать внутри handler MAT-004.
- Обновлены документация контракта и интерфейс для MAT-004. Выполнены сценарии ниже и [общие критерии готовности](../workflow.md).

## Сценарии TDD (Red → Green → Refactor)

- Contract round-trip owner; некорректный/отсутствующий owner согласно явно выбранной политике совместимости.
- Реальный PostgreSQL: создание после snapshot C → journal → ApplyReplay/ReadImage возвращает владельца; снимок с owner → новая версия через replay → владелец сохранён после открытия второго pool.
- Каждый существующий production-переход API пишет правильный owner; rollback и идемпотентный повтор не меняют исходный after-image.
- Kafka Handle и SQL ApplyReplay дают одинаковый owner; дубли, старая версия и отмена не возрождают прежнее состояние. Использовать готовые harness/fixtures, без нового стенда.
- Старые байты без owner обрабатываются по документированной политике; ошибка видима и не разрешает запрос/ack с подставленным владельцем.
