# Размер тикета и порядок разработки

## Smart zone

Определение согласовано с владельцем: один проверяемый результат, явные зависимости, сценарии TDD и критерии готовности; несколько независимых изменений — несколько тикетов. Лимит токенов или процентов контекстного окна не задавался.

Каждая карточка содержит результат, зависимости, проверку и границу задачи. В одной задаче могут понадобиться модель, адаптер и тест одного поведения; объединять независимые endpoints, сервисы или инфраструктурные компоненты нельзя. Если после чтения кода задача требует исследования нескольких не связанных между собой участков или нескольких независимо принимаемых результатов, её сначала делят. Размеры — исходная декомпозиция, не гарантия без чтения будущего кода.

## Статусы

- `split`: контейнер заменён дочерними задачами; целиком агенту не выдаётся и сессией не считается.
- `decision`: нужно выбрать и записать одно решение. Это не задача на код.
- `planned`: предложение implementation/infra-задачи; зависимости ещё не закрыты.
- `ready`: зависимости выполнены, открытых вопросов внутри карточки нет, сценарии и контракты определены.
- `in-progress`, `review`, `done`: выполнение, проверка, завершение.

На момент создания бэклога **ни одна задача приложения не выполнена**. Решения из обсуждения уже находятся в requirements.md; открытые DEC-задачи не объявлены завершёнными. Начать обсуждение независимого DEC можно сразу. Текущий этап — фиксация требований и декомпозиция, без реализации приложения.

Файл карточки — источник истины статуса. Таблица индекса показывает исходный статус; при изменении обновлять оба места. Нет параллельного внешнего трекера и GitHub issues.

## Definition of Ready

1. Все зависимости done; результат предыдущего ADR доступен в docs/decisions/.
2. Владелец согласовал продуктовые решения; гипотезы не маскируются под требования.
3. Определены вход, выход, ошибки, граница результата и способ проверки.
4. Один тикет укладывается в одну рабочую сессию с самостоятельной проверкой; при сомнении сначала разделить.
5. Для зависимых от DEC-003/004 карточек уточнены владелец состояния, активация и арбитраж гонок. Упоминание метода или endpoint в карточке само по себе не выбирает протокол.

## Сессионная проверка перед ready

«Один результат» — необходимое, но недостаточное условие. Называть карточку подходящей для одной сессии только из-за одного endpoint или одного итогового отчёта нельзя. Сейчас кода приложения нет, поэтому оценки предварительные.

Перед каждой сессией агент проверяет:

1. Все зависимости завершены; он не будет выбирать стек, создавать отсутствующий adapter или доделывать предыдущую задачу внутри текущей.
2. Нужные контракты уже записаны. Если внутри реализации остался архитектурный выбор, сначала отдельная DEC-задача или уточнение карточки.
3. Изменяется одно поведение в одном рабочем участке; его прямые интерфейсы известны. Не нужно знакомиться со всем бэклогом или менять несколько независимых сервисов.
4. Средства проверки готовы. Разработка нового test harness, fake внешней системы или runner не прячется в E2E/нагрузочный тикет.
5. В сессию входят Red→Green→Refactor, необходимые проверки и краткий результат. Уменьшать тесты ради помещения в сессию нельзя.
6. Прогон нагрузки заканчивается отчётом о фактическом результате, в том числе отрицательном. Профилирование, исправление bottleneck и повторный эксперимент — отдельные задачи.

Если любой пункт не выполняется, карточка остаётся `planned`, делится либо получает недостающую зависимость. `ready` выставляется после этой проверки по фактическому состоянию кода. Проверка не гарантирует время исполнения модели и не задаёт вымышленный процент контекстного окна.

При завершении сессии сохраняются изменения, выполненные команды, результаты и статус в карточке. Следующая сессия начинает с файлов и карточки, а не нуждается в полной истории предыдущего чата.

Стартовый порядок и шаблоны запросов: [WORKING.md](../WORKING.md). Краткая навигация текущего состояния: [STATE.md](../STATE.md). Для выбора одной карточки использовать `python3 scripts/backlog.py next`; перед завершением — `python3 scripts/backlog.py check`. Эти команды читают файлы и не меняют статусы автоматически.

Последовательность сессий закреплена в [ORDER.md](ORDER.md). `next` выбирает первую незавершённую строку, предварительно предлагая продолжить активную работу. При изменении состава или зависимостей карточек обновлять очередь вместе с индексом; check проверяет полноту, уникальность и порядок зависимостей.

## TDD для поведения

1. Выбрать один сценарий карточки и написать проверку, которая падает по ожидаемой причине (Red).
2. Внести минимальное изменение, делающее проверку зелёной (Green).
3. Упростить код без изменения поведения (Refactor).
4. Повторить для оставшихся сценариев этого поведения. Домен проверяется unit-тестами; транзакции, лимиты, leases и outbox — интеграционными тестами с реальным выбранным хранилищем/брокером; сетевые сбои — управляемыми fake серверами.

Сценарии в карточках — **план будущих тестов**, не отчёт о выполнении. Тесты на конкурентный лимит, отсутствие потери работы и устойчивые ID должны проверять наблюдаемое поведение, а не последовательность вызовов mock.

Для документов, CI, каркаса и локальной инфраструктуры вместо искусственного Red используется проверка артефакта или команды. Для нагрузочных задач проверяется воспроизводимый сценарий и отчёт. TDD не требует бессмысленных тестов наличия каталогов.

## Definition of Done

- Получен ровно заявленный результат, соблюдено «не входит».
- Для поведения выполнен Red→Green→Refactor; прикладные сценарии покрыты, подходящие проверки проходят.
- Изменения контракта/миграции документированы; секреты не добавлены.
- Для инфраструктуры сохранена команда воспроизведения, для нагрузки — профиль, commit и реальные результаты, включая неуспех.
- Статус, ссылки на артефакты и краткий результат обновлены; последующие задачи уточнены, если решение изменило гипотезы.
- Для завершённого тикета агент самостоятельно создал локальный commit с ID, описанием изменений и проверок по [GIT.md](../GIT.md). SHA сообщён в ответе; карточка, индекс и STATE включены в commit.
- Тест производительности не считается успешным только потому, что он запустился. Непройденный целевой критерий остаётся явным и порождает отдельную узкую задачу после профилирования.
