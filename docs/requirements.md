# Требования и решения

## Текущая цель: практическая production готовность

Обновлено: 8 ноября 2026, Europe/Moscow. По [DEC-011](decisions/DEC-011.md)
нужен работающий пет-проект с безопасным реальным deployment, без тяжёлых
нагрузочных тестов. Функциональный fake E2E уже выполнен, production готовность
пока не подтверждена. Исходный эксплуатационный профиль — один хост, по одной
реплике сервисов, постоянные PostgreSQL/Kafka, без обещания HA или численного SLO.

До выпуска нужны: каталог реально обслуживаемых пар, воспроизводимый запуск,
HTTPS/webhook и секреты, проверенный backup/restore, контроль здоровья/очередей/
свободного диска и безопасная очистка. Завершение — малый restart smoke и один
реальный путь аккаунт → Telegram → подписка → цена → уведомление на своём chat.
Реальные credentials и данные хоста вводятся при соответствующей задаче.

Проверяем изменяемое поведение через TDD, целевые integration тесты и обычный CI.
Для инфраструктуры — проверка команд и небольшой запуск. Million fixture,
burst/p99, сравнение реплик, точный temp peak/kernel provenance и векторный
capacity ledger больше не требования к выпуску; история в DEC-008 сохраняется.
Ошибки записи не скрываются, принятая работа не удаляется ради места, а
мониторинг диска не объявляется гарантией завершения при заполненном volume.

## Согласовано

- По [OPS-013](decisions/OPS-013.md) регистрация и вход совместно ограничены 20 попытками на IP за фиксированную минуту UTC для всех реплик API. IP из RemoteAddr, proxy headers не учитываются; общая квота и время — PostgreSQL API. 429 с Retry-After при превышении, 503 без обработки credentials при сбое квоты. Учитываются успешные и неуспешные допущенные запросы.

- Учебный проект; backend на Go, микросервисы, TDD.
- По [DEC-006](decisions/DEC-006.md) постоянное хранилище — PostgreSQL: один локальный экземпляр, четыре отдельные БД с ролями и миграциями владельцев. Прямой SQL-доступ к чужой БД запрещён. Лимит, переход подписки и outbox атомарны в API; market-data сохраняет котировку и работу публикации в своём SQL-outbox; matcher сохраняет проекцию с checkpoint, notifications — задания/исходы/назначенные проверки. Граница снимка задаётся транзакционным журналом C и материализованным MVCC-снимком, не автоинкрементом или offset брокера. Устойчивость commit не означает HA; нагрузка ещё не подтверждена.
- По [DEC-007](decisions/DEC-007.md) брокер — Apache Kafka/KRaft, локально один узел с постоянным volume (без HA). Доставка допускает повторы: устойчивые event_id/trigger_id, транзакционные relay с fencing, read_committed и SQL-результат/checkpoint до commit offset. Подписки восстанавливаются через SQL-журнал C и durable pins; цены — через отдельный latest-price bootstrap. Автоматическое удаление по возрасту/объёму и compaction выключены; очистка допускается только ниже проверенного durable прогресса обязательных потребителей. При ошибке сохранения работа не объявляется принятой, уже принятая работа не удаляется. Строгий дисковый ledger DEC-008 снят с плана по DEC-011; для эксплуатации нужны контроль места и безопасная очистка.
- По [DEC-009](decisions/DEC-009.md) внешний пользовательский API — REST/JSON по HTTP; прямые внутренние вызовы — gRPC с Protocol Buffers, в первой версии unary RPC с deadlines и идемпотентными изменяющими операциями. Асинхронные события остаются в Kafka по DEC-007; JSON-контракты событий сохраняются. Прикладные RPC/HTTP подключены к runtime в OPS-069–073; реальный deployment проверяется по DEC-011.
- Четыре процесса: API аккаунтов и подписок; приём цен Binance; проверка условий; доставка уведомлений. Владельцы данных утверждены в [DEC-003](decisions/DEC-003.md); активация по последней цене, условная доставка и гонки определены в [DEC-004](decisions/DEC-004.md).
- Не более 15 незавершённых подписок на одного пользователя: ожидание цены, очереди/попытки доставки и delivery_blocked входят в лимит. Подтверждённо доставленные и отменённые не входят.
- По [OPS-014](decisions/OPS-014.md) локальный Kafka cleaner — явная maintenance-команда с одним durable file registry/OS lock на source/partition. Полный обязательный inventory задаётся provisioning; unknown/offline запрещают удаление, retirement явный. Граница возможного DeleteRecords сохраняется с fsync до отправки, новый consumer требует SQL proof не ниже этой границы. Область — один хост/local filesystem без rollback реестра и конкурентного административного topic recreate; автоматический reset/retention и межхостовая координация не входят.
- Binance Spot, доступные торговые пары к USDT; цена последней сделки.
- Пользователь задаёт конкретную цену либо рост/падение на процент. Процент считается от последней известной цены в момент создания; исходная цена и вычисленный порог сохраняются, порог впоследствии не меняется. Это не изменение за скользящий период. Доменный контракт [DOM-002](backlog/tickets/DOM-002.md): исходная цена положительна; нулевой процент и падение ≥100% отклоняются. Процент — точное десятичное число до 18 цифр целой и дробной части; порог вычисляется без округления и должен укладываться в диапазон и точность Price (18/18), иначе возвращается ошибка.
- По [DEC-001](decisions/DEC-001.md) для конкретной цены пользователь явно выбирает направление: `up` («не ниже», `P >= T`) или `down` («не выше», `P <= T`). Для процентов рост задаёт `up`, падение — `down`. Равенство включено; достаточно текущей допустимой цены, предыдущая цена и точное попадание в порог не требуются. Скачок через порог удовлетворяет условию.
- По [DEC-002, редакция 2](decisions/DEC-002.md) используется последняя известная корректная цена без максимального допустимого возраста. Возраст считается как `now_utc - traded_at`, где traded_at — время сделки Binance `T`; при возрасте больше 5 секунд пользователь получает предупреждение с временем и возрастом сделки. До 5 секунд включительно предупреждения о возрасте нет. Это не период обновления: цена обновляется по мере получения сделок. Возраст не округляется; время приёма и время события `E` не заменяют время сделки.
- Создание обоих видов подписок допускает старую последнюю цену: для процентов от неё фиксируется порог, для конкретной цены проверяется текущее известное условие. Ответ содержит исходную цену, время сделки, возраст и предупреждения; отдельное подтверждение не требуется. При известном разрыве связи или неподтверждённом состоянии потока возвращается отдельное предупреждение о возможных пропущенных сделках, даже если цена моложе 5 секунд. Корректная сохранённая цена после рестарта используется с таким предупреждением. Старый возраст сам по себе не доказывает потерю связи и не запрещает создание; предупреждения не являются периодической Telegram-рассылкой.
- При отсутствии цены (missing), будущем, отсутствующем или некорректном времени сделки (invalid_time) создание возвращает HTTP 503 и код `quote_unavailable`, без подписки и расхода слота. Рабочее предположение — синхронизированные UTC-часы без отдельного допуска на расхождение; отрицательный возраст не обнуляется.
- По [DEC-004](decisions/DEC-004.md) проверяется последняя известная цена при подключении/обработке и непосредственно перед каждой попыткой Telegram. Исчезнувшее условие, в том числе выполненное при создании, не даёт отложенного уведомления. Если условие всё ещё выполнено, нового пересечения ждать не нужно. Прошлые краткие достижения порога при задержке подключения/обработки и рестарте не восстанавливаются. При исчезновении условия сообщение не отправляется, подписка продолжает ждать с тем же порогом и workflow. Порог предупреждения не является TTL подписки или задания.
- Подписка завершается и освобождает слот, когда API атомарно сохраняет подтверждённый успех Telegram, либо при отмене. Постановка работы в очередь слот не освобождает. API сохраняет одно устойчивое trigger_id/workflow и идемпотентно принимает результаты попыток; notifications хранит задание и восстанавливаемую обязанность сообщить результат API. При постоянной ошибке/исчерпании попыток delivery_blocked остаётся незавершённой, автоматические повторы остановлены, причина видна, отмена доступна.
- В первой версии учитываем полученные рыночные данные. Разрывы обозначаем явно; пересечения внутри отсутствующих данных Binance не гарантируются. Команды, задания, результаты и изменения подписок сохраняются durable. Ценовое событие может быть явно обработано как заменённое более новой ценой по DEC-004; это не разрешает молчаливую потерю работы.
- Аккаунты с email и паролем; Telegram привязывается одноразовым кодом. Подтверждение email и восстановление пароля — следующая очередь.
- По [DEC-005](decisions/DEC-005.md) без Telegram создание возвращает 409 telegram_not_linked, без подписки и расхода слота. Если привязка исчезла перед допуском, подписка блокируется с видимой причиной; слот и прежний workflow сохраняются. Отдельная цена блокировки не нужна. После успешной перепривязки подписка автоматически возобновляется с прежним порогом: проверяется последняя цена, при ложном условии продолжается ожидание; перед каждой отправкой проверка повторяется. Восстановление durable и не требует нового ценового события. Подтверждённо доставленные/отменённые и блокировки по иной причине не возрождаются.
- Канал уведомлений — Telegram. Отмена до сохранения допуска отправки запрещает попытку; уже разрешённый/начатый внешний запрос может завершиться после отмены, последующие попытки запрещены. API явно возвращает возможность сообщения в полёте.
- Доставку измеряем отдельно с учётом Telegram rate limits и очереди. После неоднозначного timeout допускается повторное внешнее сообщение; каждый повтор проверяет последнюю цену, внутри приложения workflow и задание устойчивы к повторам. Подтверждённый успех не переотправляется из-за потери ответа API о фиксации результата. Последняя цена проверяется до внешнего запроса, но возможность сделки к прочтению сообщения не гарантируется.
- Smart zone: один проверяемый результат, явные зависимости, сценарии TDD, критерии готовности. Независимые изменения разделяются на отдельные тикеты.

## Владение данными

По [DEC-003](decisions/DEC-003.md) каждый вид канонических данных имеет одного владельца:

| Сервис | Собственные данные | Доступ других сервисов |
| --- | --- | --- |
| API аккаунтов и подписок | Аккаунты, сессии, Telegram-коды и привязка, подписки, активный лимит, срабатывания и trigger_id, outbox изменений/срабатываний, квоты входа | Защищённые интерфейсы, события и согласованный снимок подписок |
| Market-data | Каталог пар, котировки, ID/времена сделок, состояние потока, принятая рыночная работа и её публикация | Интерфейс каталога/последней котировки и поток цен |
| Matcher | Проекция подписок, индекс, checkpoints/replay, состояние координации обработки | Собственное служебное состояние; канонические изменения запрашиваются у API |
| Notifications | Задания доставки, дедупликация по trigger_id, попытки, leases, результаты, лимитеры бота/чата | Потребление AlertTriggered как запроса работы; допуск попытки и фиксация исхода через защищённые интерфейсы API |

Сервисы не читают и не изменяют чужие таблицы напрямую. Matcher запрашивает работу доставки у API; API атомарно сохраняет workflow и событие в своём outbox, сохраняя слот. Notifications сохраняет задание в своей транзакции до подтверждения события; получает допуск попытки с последней ценой и сообщает исход через API. Канонические переходы, слот и outbox меняет только API. Исходная котировка в подписке — неизменяемый снимок, а не каноническая текущая цена.

Владение относится ко всем репликам сервиса. Один физический сервер СУБД допустим при раздельных логических областях и правах; размещение определено DEC-006: отдельная БД каждого сервиса в одном локальном экземпляре PostgreSQL. Граница активации, снимок/replay и гонки определены в DEC-004; граница durable приёма рыночной работы — SQL-outbox по DEC-006; транспорт/ack публикации — DEC-007. Telegram-политика определена DEC-005: адресат и версия привязки определяются API при допуске. После исправления канала прежнее задание возобновляется через периодическую durable проверку. Изменение канала после допуска допускает сообщение в полёте на прежний chat; последующие попытки используют текущую привязку.

Брокер и модель доставки утверждены DEC-007, число партиций фиксировано DEC-008. Транспорт прикладных интерфейсов закреплён DEC-009: REST/JSON снаружи, gRPC внутри, Kafka для событий. Формат пользовательских сессий закреплён [IAM-004](decisions/IAM-004.md): случайный Bearer-токен на 24 часа, в PostgreSQL только SHA-256 токена, user_id и срок истечения. Сервисные credentials закреплены в [SET-008](decisions/SET-008.md): mTLS (TLS 1.3), отдельный сервисный CA, идентичность клиента из URI SAN и явные права на полные имена unary RPC; публичный Bearer не даёт сервисных прав. Runtime mTLS готов, provisioning deployment PKI входит в OPS-074/075; версии gRPC/Protobuf закреплены в SET-007. Названия endpoint и таблиц в карточках описывают поведение; окончательные контракты фиксируются в соответствующей задаче.

## За пределами первой очереди

Frontend, торговля и хранение средств, фьючерсы, другие quote assets, повторяющиеся подписки, процент за скользящее окно, редактирование активной подписки, история с пагинацией, email-уведомления, восстановление пропущенных внешних сделок и мульти-региональность. Эти функции не входят в обязательный план. Production-деплой одного хоста входит в план DEC-011.
