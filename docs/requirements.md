# Требования и решения

Обновлено: 26 октября 2026, Europe/Moscow. Источник продуктовых решений — обсуждение с владельцем проекта. Отметка «согласовано» относится к требованию, а не к готовности реализации.

## Согласовано

- Учебный проект; backend на Go, микросервисы, TDD.
- Четыре процесса: API аккаунтов и подписок; приём цен Binance; проверка условий; доставка уведомлений. Владельцы данных утверждены в [DEC-003](decisions/DEC-003.md); активация по последней цене, условная доставка и гонки определены в [DEC-004](decisions/DEC-004.md).
- 100 000 пользователей. Не более 15 незавершённых подписок на одного пользователя: ожидание цены, очереди/попытки доставки и delivery_blocked входят в лимит. Подтверждённо доставленные и отменённые не входят.
- Базовый нагрузочный набор: 1 000 000 активных подписок суммарно. Теоретический максимум при 100 000 × 15 — 1 500 000, это отдельный граничный профиль.
- Цель всплеска: 10 000 durable запросов работы доставки/с; это не скорость подтверждённой отправки Telegram. Длительность всплеска, входная скорость цен и ресурсы стенда ещё не утверждены: DEC-008.
- Binance Spot, доступные торговые пары к USDT; цена последней сделки.
- Пользователь задаёт конкретную цену либо рост/падение на процент. Процент считается от последней известной цены в момент создания; исходная цена и вычисленный порог сохраняются, порог впоследствии не меняется. Это не изменение за скользящий период.
- По [DEC-001](decisions/DEC-001.md) для конкретной цены пользователь явно выбирает направление: `up` («не ниже», `P >= T`) или `down` («не выше», `P <= T`). Для процентов рост задаёт `up`, падение — `down`. Равенство включено; достаточно текущей допустимой цены, предыдущая цена и точное попадание в порог не требуются. Скачок через порог удовлетворяет условию.
- По [DEC-002, редакция 2](decisions/DEC-002.md) используется последняя известная корректная цена без максимального допустимого возраста. Возраст считается как `now_utc - traded_at`, где traded_at — время сделки Binance `T`; при возрасте больше 5 секунд пользователь получает предупреждение с временем и возрастом сделки. До 5 секунд включительно предупреждения о возрасте нет. Это не период обновления: цена обновляется по мере получения сделок. Возраст не округляется; время приёма и время события `E` не заменяют время сделки.
- Создание обоих видов подписок допускает старую последнюю цену: для процентов от неё фиксируется порог, для конкретной цены проверяется текущее известное условие. Ответ содержит исходную цену, время сделки, возраст и предупреждения; отдельное подтверждение не требуется. При известном разрыве связи или неподтверждённом состоянии потока возвращается отдельное предупреждение о возможных пропущенных сделках, даже если цена моложе 5 секунд. Корректная сохранённая цена после рестарта используется с таким предупреждением. Старый возраст сам по себе не доказывает потерю связи и не запрещает создание; предупреждения не являются периодической Telegram-рассылкой.
- При отсутствии цены (missing), будущем, отсутствующем или некорректном времени сделки (invalid_time) создание возвращает HTTP 503 и код `quote_unavailable`, без подписки и расхода слота. Рабочее предположение — синхронизированные UTC-часы без отдельного допуска на расхождение; отрицательный возраст не обнуляется.
- По [DEC-004](decisions/DEC-004.md) проверяется последняя известная цена при подключении/обработке и непосредственно перед каждой попыткой Telegram. Исчезнувшее условие, в том числе выполненное при создании, не даёт отложенного уведомления. Если условие всё ещё выполнено, нового пересечения ждать не нужно. Прошлые краткие достижения порога при задержке подключения/обработки и рестарте не восстанавливаются. При исчезновении условия сообщение не отправляется, подписка продолжает ждать с тем же порогом и workflow. Порог предупреждения не является TTL подписки или задания.
- Подписка завершается и освобождает слот, когда API атомарно сохраняет подтверждённый успех Telegram, либо при отмене. Постановка работы в очередь слот не освобождает. API сохраняет одно устойчивое trigger_id/workflow и идемпотентно принимает результаты попыток; notifications хранит задание и восстанавливаемую обязанность сообщить результат API. При постоянной ошибке/исчерпании попыток delivery_blocked остаётся незавершённой, автоматические повторы остановлены, причина видна, отмена доступна.
- В первой версии учитываем полученные рыночные данные. Разрывы обозначаем явно; пересечения внутри отсутствующих данных Binance не гарантируются. Команды, задания, результаты и изменения подписок сохраняются durable. Ценовое событие может быть явно обработано как заменённое более новой ценой по DEC-004; это не разрешает молчаливую потерю работы.
- Аккаунты с email и паролем; Telegram привязывается одноразовым кодом. Подтверждение email и восстановление пароля — следующая очередь.
- Канал уведомлений — Telegram. Отмена до сохранения допуска отправки запрещает попытку; уже разрешённый/начатый внешний запрос может завершиться после отмены, последующие попытки запрещены. API явно возвращает возможность сообщения в полёте.
- На согласованном нагрузочном стенде p99 от приёма рыночной цены приложением до durable запроса работы доставки ≤ 1 секунды для сохраняющегося подходящего условия. Метрика включает транспорт и ожидание обработки внутри приложения; время внешней доставки в неё не входит.
- Доставку измеряем отдельно с учётом Telegram rate limits и очереди. После неоднозначного timeout допускается повторное внешнее сообщение; каждый повтор проверяет последнюю цену, внутри приложения workflow и задание устойчивы к повторам. Подтверждённый успех не переотправляется из-за потери ответа API о фиксации результата. Последняя цена проверяется до внешнего запроса, но возможность сделки к прочтению сообщения не гарантируется.
- Smart zone: один проверяемый результат, явные зависимости, сценарии TDD, критерии готовности. Независимые изменения разделяются на отдельные тикеты.

## Владение данными

По [DEC-003](decisions/DEC-003.md) каждый вид канонических данных имеет одного владельца:

| Сервис | Собственные данные | Доступ других сервисов |
| --- | --- | --- |
| API аккаунтов и подписок | Аккаунты, сессии, Telegram-коды и привязка, подписки, активный лимит, срабатывания и trigger_id, outbox изменений/срабатываний, квоты входа | Защищённые интерфейсы, события и согласованный снимок подписок |
| Market-data | Каталог пар, котировки, ID/времена сделок, состояние потока, принятая рыночная работа и её публикация | Интерфейс каталога/последней котировки и поток цен |
| Matcher | Проекция подписок, индекс, checkpoints/replay, состояние координации обработки | Собственное служебное состояние; канонические изменения запрашиваются у API |
| Notifications | Задания доставки, дедупликация по trigger_id, попытки, leases, результаты, лимитеры бота/чата | Потребление AlertTriggered как запроса работы; допуск попытки и фиксация исхода через защищённые интерфейсы API |

Сервисы не читают и не изменяют чужие таблицы напрямую. Matcher запрашивает работу доставки у API; API атомарно сохраняет workflow и событие в своём outbox, сохраняя слот. Notifications сохраняет задание в своей транзакции до подтверждения события; получает допуск попытки с последней ценой и сообщает исход через API. Канонические переходы, слот и outbox меняет только API. Исходная котировка в подписке — неизменяемый снимок, а не каноническая текущая цена.

Владение относится ко всем репликам сервиса. Один физический сервер СУБД допустим при раздельных логических областях и правах; размещение выберет DEC-006. Граница активации, снимок/replay и гонки определены в DEC-004; способ durable публикации рыночной работы — в DEC-006/007. Владелец Telegram-привязки определён; допуск без неё, получение адресата задания и поведение при её смене требуют уточнения до реализации соответствующих контрактов.

СУБД, брокер, wire-протоколы, конкретный формат сессий, стратегия шардирования и версии библиотек не утверждены. Названия endpoint и таблиц в карточках описывают поведение; окончательные контракты фиксируются в соответствующей задаче.

## За пределами первой очереди

Frontend, торговля и хранение средств, фьючерсы, другие quote assets, повторяющиеся подписки, процент за скользящее окно, редактирование активной подписки, история с пагинацией, email-уведомления, восстановление пропущенных внешних сделок, production-деплой и мульти-региональность. Их нет среди обязательных implementation-тикетов первой очереди.
