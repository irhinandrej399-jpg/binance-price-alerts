# DEC-010 — Сначала рабочий локальный пет-проект

Дата: 6 ноября 2026. Статус: принято.

Основание: пользователь прямо уточнил: «это пет проект», «мне главное чтобы
он запускался и работал». Обращение к поставщику за kernel provenance
не требуется для текущей цели.

## Решение

Текущий этап — функциональный локальный профиль на существующих PostgreSQL,
Kafka и Docker Desktop. Результат: воспроизводимый запуск четырёх сервисов,
регистрация/вход, привязка Telegram, создание подписки, получение цены и
уведомление, проверенные полным пользовательским сценарием E2E-001.
Управляемые fake Binance/Telegram дают повторяемый E2E; реальная доставка
требует пользовательских credentials и доступного webhook.

Сохраняются владельцы данных, транзакции/outbox, идемпотентность, проверка
допуска отправки, аутентификация и восстановление после сбоев. Готовые
компоненты используем через их интерфейсы. TDD для поведения сохраняется.

DEC-008 и связанные с ним требования к миллионному fixture, p99, физическим
резервам и квалифицированной таблице затрат относятся к отдельному будущему
нагрузочному этапу. Для локального профиля OPS-015/016/018 и исследовательская
цепочка OPS-044 → OPS-043 → OPS-034 → OPS-035 → OPS-036 → OPS-032
не блокируют healthchecks, сборку runtime и E2E. OPS-044 возвращён в planned:
работа отложена, исходные критерии не выполнены и не объявляются выполненными.
Raw и незавершённый код сохраняются без повторных smoke/поисков manifest.
Возврат к этой цепочке — по отдельному поручению после рабочего сценария.

Readiness API проверяет инициализацию и собственное хранилище; market-data —
инициализацию, своё хранилище и состояние feed. Исчерпание квалифицированного
capacity ledger не входит в локальные health-задачи. При фактической ошибке
записи операция не объявляется успешной; outbox не удаляется ради освобождения
места. Локальный профиль не гарантирует завершение при заполненном диске,
максимальную ёмкость или производительность. Недостаток места устраняется
оператором; не выдаём отсутствие измерений за нулевые расходы.

## Изменения плана и проверка

ORDER ставит функциональные OPS и E2E перед незавершённой квалификацией.
Зависимости OPS-001/006 от OPS-015/016 заменены DEC-010. Остальные зависимости
нагрузочных задач сохранены. Артефакты прежних измерений не переквалифицированы.

Существующие cmd и готовые библиотеки сами по себе не доказывают готовность
процессов. Перед E2E-002 необходимо проверить wiring runtime; недостающую
сборку сервисов выделять в конкретные задачи, не прятать в E2E harness.

Рассмотрено: продолжить kernel provenance сейчас либо отложить квалификацию.
Выбрано второе: оно соответствует уточнённой цели и убирает внешний блокер.
Проверка решения — целостность backlog/ORDER, согласованность требований,
health-карточек и передачи; функциональный запуск этим решением не выполнен.
