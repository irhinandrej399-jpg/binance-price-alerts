# DEC-004 — Проверка последней цены и жизненный цикл уведомления

Дата: 26 октября 2026, Europe/Moscow.
Статус: **принято**.
Карточка: [DEC-004](../backlog/tickets/DEC-004.md).

## Контекст и выбор

Цель — сообщить пользователю о сохраняющейся возможности совершить выгодную по его мнению сделку. Уведомление о кратком достижении порога, уже исчезнувшем к проверке/отправке, этой цели не отвечает.

Рассмотрены варианты:

1. Replay всех цен от снимка создания с обязательным уведомлением о любом выполненном условии. Отклонён владельцем: опоздавшее сообщение может описывать уже исчезнувшую возможность.
2. Проверка последней цены только при подключении. Недостаточна: сообщение затем может долго ждать Telegram.
3. **Последняя известная цена при подключении/обработке и повторная проверка непосредственно перед каждой попыткой Telegram. Выбран.** Исчезнувшее условие не приводит к отправке; подписка продолжает ждать.

Решение пересматривает безусловное срабатывание по исходному снимку из [DEC-001](DEC-001.md), упоминания этого правила в [DEC-002](DEC-002.md) и прежний terminal-переход/освобождение слота до доставки из [DEC-003](DEC-003.md). Направления, включённое равенство, фиксированный процентный порог и владельцы данных сохраняются. История исходных решений сохранена с отметками о пересмотре.

## Цена и граница подключения

- Market-data — единственный владелец последней корректной котировки и её монотонной ревизии по паре. Ревизия включает идентичность потока/поколения; её нельзя заменять временем API или сравнивать между разными парами. Source ID и времена сделки/приёма сохраняются отдельно.
- API при создании сохраняет исходную цену, время, порог, направление и предупреждения. Подписка принимается как `active`, занимает слот; выполненное исходное условие не фиксирует необратимый результат. При подключении проверяется последняя известная цена, без ожидания нового пересечения, если она всё ещё удовлетворяет условию. Процентный порог от цены создания не пересчитывается.
- Matcher сначала регистрирует подписку для обновлений пары, затем получает последнюю котировку через интерфейс market-data и объединяет её с пришедшими обновлениями по монотонной ревизии. До завершения этого шага ценовая готовность подписки не выставляется. При конфликте побеждает более новая ревизия; чтение снимка не откатывает уже принятую новую цену. Обновления, пришедшие во время подключения, либо вошли в последнюю цену, либо остаются работой после регистрации. Этот протокол требует готового адаптера регистрации/буферизации; он вынесен в MAT-012.
- Событие цены — повод проверить последнее состояние, а не приказ отправить по историческому значению. При догоняющей обработке matcher обновляет/читает последнюю цену и не восстанавливает исчезнувшие возможности. Существующий durable поток не теряется молча: сообщения подтверждаются после сохранения обновления/результата или явного результата «заменено более новой ценой». Старые версии не откатывают новое состояние.
- Пропуск краткого истинного условия допустим, если к моменту проверки последняя известная цена уже не удовлетворяет порогу. Это осознанная семантика продукта, включая подключение, задержку обработки и рестарт. История цен специально для восстановления таких условий не требуется.
- DEC-002 сохраняется в части корректности и возраста: старая последняя известная цена не запрещена, время сделки не обновляется при чтении/replay. Возраст > 5 секунд и неподтверждённый поток дают предупреждения, а не новый TTL. При missing/invalid_time создание возвращает прежний 503 quote_unavailable; при недоступной/некорректной цене на поздней проверке отправка откладывается, подписка сохраняется. Последняя известная цена не гарантирует совпадения с Binance при разрыве.

## Состояния, работа доставки и лимит

API владеет каноническим состоянием. Уточнённые названия состояний описывают контракт, wire-имена задаются последующими карточками.

| Состояние | Смысл | Входит в лимит 15 |
| --- | --- | --- |
| active | Ожидает подходящей последней цены; работа доставки может уже существовать | Да |
| pending_delivery | Подходящее условие замечено, есть durable работа доставки | Да |
| sending | API разрешил конкретную попытку после повторной проверки | Да |
| delivery_blocked | Постоянная ошибка/исчерпаны повторы; автоматическая отправка остановлена, причина видна | Да |
| delivered | Telegram подтвердил успех, API сохранил результат | Нет |
| cancelled | Пользователь отменил подписку | Нет |

Временные состояния доставки не являются новыми независимыми подписками. Исчезновение условия возвращает `pending_delivery → active` без освобождения/повторного занятия слота. Нет автоматического перевзвода уже подтверждённой `delivered`. При 15 незавершённых подписках создание отклоняется, даже если исходное условие новой подписки выполнено. Delivery_blocked не объявляется успешной доставкой; пользователь может отменить такую подписку. Автоматическая починка Telegram-привязки этим ADR не добавляется. Позднее [DEC-005](DEC-005.md) уточняет возобновление прежней подписки после успешного исправления канала: порог сохраняется, проверяется последняя цена, отдельная цена блокировки не нужна.

У каждой подписки не более одного устойчивого workflow ID `trigger_id` и одного задания notifications на весь одноразовый цикл. Имя `AlertTriggered` сохраняется для совместимости плана, но **означает запрос работы доставки, а не terminal-срабатывание**. В событии явно фиксируется этот смысл; цена в нём — диагностический снимок кандидата, не разрешение отправки. Окончательный подтверждённый результат сохраняется отдельно по тому же trigger_id.

Когда цена ушла, существующее задание не уничтожается и не создаётся заново: оно переходит в ожидание условия. Каждая новая проверка получает новый request ID; повтор прежнего request ID восстанавливает прежний результат. Scheduler назначает следующую проверку с ограниченной частотой, без busy loop и без удержания lease/слота rate limiter в ожидании. Конкретный интервал — настраиваемый параметр реализации, проверяемый fake clock; лимит времени, автоматически удаляющий подписку, не вводится. Повторный кандидат matcher возвращает тот же workflow, не создавая новое задание. Дубликат старого события не сбрасывает состояние задания, доставку или отмену.

## Внутренние операции и локальные транзакции

### Запрос работы от matcher

Защищённая операция API получает ID подписки, ожидаемую версию и котировку-кандидат с парой/source ID/ревизией/временами. Пользовательская сессия не даёт права передавать цену. API проверяет канонические порог/направление, версию и допустимое состояние, обращается к последней котировке market-data через интерфейс и проверяет условие по ней. Чужие таблицы не читаются. Старое событие не разрешает отправку по утраченному условию.

Если условие истинно, API атомарно сохраняет `pending_delivery`, устойчивый trigger_id, новую версию и AlertTriggered в своём outbox; слот остаётся занятым. Если workflow уже существует, возвращается его ID/состояние без второго задания. Ложное условие не создаёт работу; недоступность цены/API требует повтора или отложенной проверки, а не удаления подписки. После неоднозначного timeout вызывающий восстанавливает результат по ID и повторяет идемпотентно.

### Допуск одной попытки отправки

После получения задания и допуска лимитеров notifications вызывает защищённый интерфейс API. API проверяет действующий workflow, отсутствие отмены/успеха, отсутствие другой действующей попытки, получает последнюю цену у market-data и вычисляет канонический предикат.

- Ложно: API возвращает состояние active и результат `wait_condition`; notifications паркует то же задание без sendMessage.
- Цена недоступна/некорректна: отложить попытку, не отправлять по старому событию задания.
- Истинно: API атомарно сохраняет `sending` и ID/ограниченный срок разрешения попытки, привязанные к workflow; возвращает проверенную цену/время/предупреждения. Сообщение формируется по этой цене, а не по исходному событию.

Разрешение не предназначено для хранения в очереди. После него выполняется одна непосредственная попытка HTTP без нового ожидания лимитеров. Если отправка отложена, срок/lease истёк или процесс восстановился, требуется новый допуск и новая проверка цены. Повтор той же команды возвращает тот же результат, а не ещё одно разрешение; новые полномочия не выдаются при действующей предыдущей попытке. Локальные fencing token запрещают старому worker менять новый результат. Они не дают внешней exactly-once гарантии.

Чтение цены и транзакция API не образуют распределённую транзакцию. Проверка относится к последнему известному значению в момент внутреннего чтения; рынок может измениться сразу после него. Между проверкой, HTTP, доставкой и прочтением пользователем возможность может исчезнуть — обещания цены исполнения нет.

### Сохранение исхода

Notifications durable сохраняет исход попытки и обязанность сообщить его API до окончательного ack/завершения локальной работы. API идемпотентно принимает результат по workflow/attempt ID. Потеря ответа API повторяет фиксацию результата, а не Telegram-вызов.

- Подтверждённый успех: API сохраняет `delivered`, результат/message_id, освобождает слот ровно один раз и записывает изменение подписки в outbox. Если цена ушла после уже начавшейся отправки, это не отменяет подтверждённый успех.
- Доказанный временный отказ: pending_delivery с отложенным повтором; перед повтором новая проверка последней цены. Если условие исчезло — active и ожидание в том же задании.
- Постоянный отказ или исчерпание автоматических попыток: delivery_blocked, работа не крутится бесконечно, причина видна. Слот остаётся занят до отмены/успеха; устранение причины отдельно.
- Неоднозначный timeout/падение после допуска: внешний результат может быть неизвестен. Это явное состояние попытки. Сохраняется ранее принятая политика возможного повтора с риском дубля; каждый новый HTTP-повтор проходит проверку текущего условия. Если оно ложно, повтор не отправляется и подписка ждёт. Устойчивый workflow ID не меняется. Запоздалый достоверный успех известной попытки прекращает новые отправки и фиксирует результат; не обнуляется только из-за истёкшего локального lease. Уже выполняющийся внешний запрос отозвать нельзя.

Контракт Telegram проверен 26 октября 2026: [sendMessage](https://core.telegram.org/bots/api#sendmessage) возвращает Message при успехе; вывод о неопределённости при потере ответа — инженерный. Вызов Telegram и commit наших сервисов не атомарны. Возможный внешний дубль после неоднозначного исхода не превращается в обещание ровно одного сообщения.

## Отмена и три временные проверки

Все переходы разрешает API по одной канонической записи; реплики не принимают независимые решения. Отменять можно все незавершённые состояния, включая ожидание цены/доставки и blocked. Отмена атомарно сохраняет cancelled, освобождает слот один раз и пишет изменение в outbox. После неё новые разрешения отправки запрещены.

Граница гонки — commit допуска конкретной попытки отправки. Если отмена сохранилась первой, отправки нет. Если допуск сохранился первым, уже разрешённый/начатый запрос может завершиться; отмена останавливает следующие попытки и явно сообщает о возможности сообщения в полёте. Запоздалый результат сохраняется в аудите, но не возвращает отменённую подписку в active и не освобождает слот повторно. Создание workflow само по себе отмене не препятствует. Если успех сохранился раньше отмены, API возвращает delivered.

Во всех примерах `up`, порог 100.

### 1. Исходное условие и задержка подключения

```text
создание: P=101 → commit active, слот занят
рынок:                              P=99
matcher:                                  подключение → последняя P=99
результат: уведомления нет; подписка active; снимок 101 не даёт отложенный trigger
```

Если при подключении последняя цена всё ещё 101 — создаётся работа без ожидания нового пересечения, но цена снова проверяется перед отправкой. Тот же контракт действует для старой допустимой исходной цены; предупреждения не меняют предикат.

### 2. Краткое условие до индексации или в очереди

```text
создание: P=99 → рынок P=101 → рынок P=99 → подключение: последняя P=99
результат: не догонять исторические 101; уведомления нет

matcher: P=101 → pending_delivery → очередь/лимитер → рынок P=99
worker:                                              допуск: wait_condition
результат: HTTP-вызова нет; active, тот же workflow и слот
позже: P=102 → проверка/допуск → Telegram success → API delivered, слот освобождён
```

После рестарта действуют те же правила. Повтор старого события не отправляет сообщение по прошлым 101. При replay с неизменной подходящей последней ценой незавершённая durable работа продолжается.

### 3. Отмена и попытка доставки

```text
A: API commit cancelled → запрос допуска → отказ → sendMessage не вызывается
B: API commit sending → sendMessage в полёте → cancel → новые попытки запрещены
C: Telegram success → API commit delivered → cancel видит delivered
```

В B внешний запрос может завершиться после отмены; слот освобождён отменой, повторно не освобождается. В A запоздавший кандидат/дубликат события ничего не возрождает. Само ожидание сообщения в очереди не делает отмену проигравшей.

## Снимок подписок и восстановление

API выдаёт неизменяемый снимок подписок S на логической границе C журнала изменений; replay содержит изменения строго после C. Все страницы имеют один snapshot_id, стабильный cursor и объявленный expires_at. Конкурентный commit должен находиться либо в снимке, либо в последующем журнале, без окна. Максимум заранее выделенных ID или последнего опубликованного сообщения не доказывает такую границу.

Истёкший/невалидный ресурс снимка отклоняется явно; matcher отбрасывает частичную загрузку и начинает новый снимок. Точная длительность ресурса конфигурируется в контракте хранилища; это не TTL подписки или принятого задания. Replay изменений подписок удерживается до durable прогресса/отказа от снимка. Граница догонки фиксируется явно; после неё продолжается тот же поток. До загрузки, replay и подключения к последним ценам matcher не готов. Cursor не опережает durable проекцию.

Снимок включает все незавершённые состояния и ссылки на существующий workflow. Работу notifications восстанавливает её собственное хранилище; snapshot matcher не создаёт второй workflow. После перезапуска активные подписки проверяются по последним ценам, без восстановления исчезнувших возможностей. Ценовая ревизия и cursor журнала подписок — разные шкалы. Точные механизмы журнала/ack/retention выбираются в DEC-006/007; уже принятые команды, результаты и задания не теряются из-за отказа от исторического поиска условий.

## Последствия и границы

- Уточнены требования, DEC-001/002/003, контракты событий, жизненный цикл, создание/лимит/отмена, запрос работы, snapshot/replay, matcher, notifications и измерения. Старые слова «срабатывание» не должны скрывать различие запроса работы и подтверждённого завершения.
- SUB-013/014 теперь сохраняют/открывают запрос работы, а не terminal active→triggered. Отдельные новые SUB-017/018/019/020 покрывают допуск попытки и фиксацию исхода: storage и защищённый интерфейс — разные сессии. NTF-014 отдельно сохраняет исход и восстанавливаемую обязанность сообщить API. MAT-012 отдельно обеспечивает подключение к последней цене. Все новые задачи planned, с моделями, зависимостями и местами в ORDER.
- Нагрузка до durable запроса работы измеряется отдельно от условной доставки/подтверждённого завершения. Цель p99 ≤ 1 секунды и burst 10 000/с не переименовываются в обещание Telegram-производительности. DEC-008 должен зафиксировать подходящие контрольные цены и долю исчезнувших условий.
- Выбор СУБД, брокера, Telegram-привязки, профиля стенда и Go-реализация не входят в результат. Внешняя история Binance не восстанавливается. Новая архитектура не считается реализованной или проверенной нагрузкой.

## Согласование

В текущей сессии 26 октября 2026 владелец сначала отклонил обязательный replay исчезнувшего условия до подключения, затем пояснил цель возможности выгодной сделки сейчас. На предложение «проверять последнюю цену, перед Telegram перепроверять, при исчезновении условия не отправлять и продолжать ожидание; не завершать подписку только из-за очереди» ответил «да». Это основание пересмотра исходного условия и момента завершения. Границы отмены/неоднозначной отправки и локальные транзакции выше конкретизируют согласованное поведение без обещания отзыва уже ушедшего внешнего запроса. Дата и политика возраста не пересматривались.
