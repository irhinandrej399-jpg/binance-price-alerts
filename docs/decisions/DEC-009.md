# DEC-009 — Транспорт внешних и внутренних интерфейсов

Дата: 27 октября 2026, Europe/Moscow. Статус: **принято**.

Карточка: [DEC-009](../backlog/tickets/DEC-009.md).

## Контекст и варианты

DEC-003/004 определяют владельцев данных и прямые операции между сервисами; DEC-007 — доставку событий через Kafka. Wire-протокол прямых вызовов ранее оставался открытым.

Рассмотрены REST/JSON по HTTP и gRPC с Protocol Buffers. REST удобен для внешнего клиентского API и ручной отладки. Для внутренних Go-сервисов выбран gRPC: явные типизированные контракты в `.proto` и генерируемые клиенты/серверные интерфейсы. Цена выбора — инструменты генерации и контроль совместимости схем. Преимущество производительности на нашем стенде пока не измерено.

## Решение

- Внешний пользовательский API: REST/JSON по HTTP.
- Прямые внутренние вызовы: gRPC с Protocol Buffers. Для первой версии используются unary RPC (один запрос — один ответ); снимок и replay выдаются ограниченными страницами с прежними cursor/pin-гарантиями.
- Асинхронные события: Kafka по DEC-007. gRPC не заменяет durable события и outbox. Существующие JSON-контракты Kafka не переводятся в Protobuf этим решением.

| Отправитель → получатель | Назначение | Транспорт |
| --- | --- | --- |
| Пользовательский клиент → API | Аккаунты, подписки, отмена, Telegram-привязка | REST/JSON |
| API → market-data | Каталог пар и последняя котировка | gRPC |
| Matcher → market-data | Последняя котировка при подключении и обработке | gRPC |
| Matcher → API | Снимок подписок, страницы replay и подтверждение прогресса | gRPC |
| Matcher → API | Запрос работы доставки | gRPC |
| Notifications → API | Допуск конкретной попытки и фиксация исхода | gRPC |
| API → matcher через Kafka | SubscriptionChanged, topic subscription-changes | Kafka |
| Market-data → matcher через Kafka | PriceObserved, topic prices | Kafka |
| API → notifications через Kafka | AlertTriggered, topic delivery-requests | Kafka |

Внешние интеграции сохраняют свои протоколы: поток сделок Binance — WebSocket, Telegram Bot API — HTTPS. Этот ADR определяет прикладные интерфейсы, не транспорт health/metrics.

## Требования к внутренним вызовам

- Клиент задаёт конечный deadline; бюджет конкретной операции определяется при реализации и учитывает вложенное чтение market-data. Отмена передаётся через context.
- Сервисная аутентификация и авторизация обязательны. Публичная пользовательская сессия не даёт полномочий внутренних RPC; прямой доступ к чужим БД запрещён.
- Изменяющие состояние операции сохраняют request/workflow/attempt ID и идемпотентность DEC-004. Timeout не доказывает отсутствие commit; повтор восстанавливает результат, а не создаёт второе задание или разрешение. Безусловные автоматические повторы изменяющих состояние вызовов не вводятся.
- При реализации различаются доменные результаты (например, wait_condition) и транспортные ошибки. Проверяются deadlines, недоступность зависимости, авторизация и повтор после потери ответа.
- `.proto` и генерируемые Go-интерфейсы версионируются; номера удалённых полей не переиспользуются. Цены сохраняют точность доменного Price, без float/double. Точные сообщения, методы и отображение ошибок определяются в соответствующем интерфейсном тикете.

## Последствия и границы

Уточнены MKT-006, SUB-014/016/018/020/022 и требования. Их прикладные инварианты, состояния, снимок/replay и владельцы данных сохраняются. Kafka-контракты CON-001–004 и текущая очередь продуктовой реализации не переоткрываются.

Код gRPC, `.proto`, версии библиотек, инструменты генерации, механизм сервисных credentials и сетевые тесты этим ADR не реализованы. Перед ready соответствующего интерфейсного тикета проверяются готовые адаптеры, генерация и test harness; при отсутствии общей предпосылки сначала выделяется отдельная узкая задача по workflow. Выбор транспорта не подтверждает готовность runtime или целевую нагрузку.

## Согласование

В обсуждении пользователь предложил gRPC. После рекомендации «gRPC внутри, REST снаружи, Kafka для событий» 27 октября 2026 пользователь поручил «закрепи это». Это основание принятия решения; повторного согласования выбора не требуется.
