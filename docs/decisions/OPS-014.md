# OPS-014 — Локальный реестр безопасной очистки Kafka

Дата: 8 ноября 2026, Europe/Moscow. Статус: **принято**.
Карточка: [OPS-014](../backlog/tickets/OPS-014.md).

Пользователь выбрал «Локальный файл и блокировка — для текущего локального профиля»
в ответ на выбор локального durable файла либо отдельного SQL владельца.

Для локальной maintenance-команды выбран один доверенный постоянный каталог
реестра на source/partition, общий для init/register/retire/clean на этом хосте.
Постоянный lock file сериализует процессы; atomic replace state не заменяет
inode блокировки. После исчезновения/повреждения state clean запрещён; init
явный и никогда не вызывается автоматически. Offline/restart не удаляют consumer.

Реестр хранит exact source ClusterID/TopicID/topic/partition, обязательные
consumer descriptors (matcher kind+scope/projection ID, notifications ID+SQL
generation), явные retirement tombstones и монотонную границу возможного удаления.
Init требует явно перечислить полный обязательный набор. Полнота — обязанность
provisioning; consumers запускаются только после включения в авторитетный реестр.

До DeleteRecords граница возможного удаления сохраняется с fsync файла и
каталога. Ошибка сохранения запрещает отправку. Неизвестный broker result не
откатывает границу: после смерти процесса старый запрос ещё мог выполниться.
Register требует exact SQL proof не ниже max(log-start, сохранённой границы).
Необходимый новый bootstrap выполняется владельцем явно до регистрации.
Retire явно называет прежний descriptor/generation, сохраняет tombstone и не
возникает автоматически при ошибке, offline или restart.

Clean удерживает ту же блокировку от чтения состава через SQL proofs до bounded
DeleteRecords. Каждый обязательный consumer обязан дать exact source-bound SQL
next по защищённому RPC; ошибка, unknown, missing offset, mismatch или пустой
активный набор запрещают удаление. Удаляется [log-start, target), где target не
выше минимального SQL next и read_committed LSO; число offsets за команду ограничено.
SQL replay-pins, broker commit offsets и retention не меняются.

Область решения — один хост и local durable filesystem. Все исполнители обязаны
использовать тот же авторитетный каталог; нельзя создавать параллельные реестры,
удалять lock/state, восстанавливать устаревшую копию или переносить generation
без отдельного операторского плана. NFS/shared filesystem и разные хосты не входят.
Топик не пересоздаётся администрацией во время операций: DeleteRecords адресует
имя topic, и metadata check не является атомарной блокировкой delete/recreate.
Клонирование storage с прежними IDs неразличимо, как в source binding контракте.

Новый SQL владелец, HA, автоматическая topic/SQL migration, нагрузочная
квалификация и обещание немедленного освобождения физических байтов не входят.
