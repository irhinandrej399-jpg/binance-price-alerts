# DEC-006 — Постоянное хранилище и локальные транзакции

Дата: 26 октября 2026, Europe/Moscow. Статус: **принято**.

Карточка: [DEC-006](../backlog/tickets/DEC-006.md). Основания: принятые [DEC-003](DEC-003.md), [DEC-004](DEC-004.md), [DEC-005](DEC-005.md). Приложение и схемы БД этим документом не реализуются.

## Варианты и выбор

Выбран PostgreSQL как единственная СУБД первой очереди. Один локальный экземпляр обслуживает четыре отдельные БД: API, market-data, matcher, notifications. У каждого сервиса собственные роли и миграции. Точная поддерживаемая версия и закреплённый образ выбираются в SET-003 после проверки актуальных выпусков.

| Вариант | Оценка для проекта |
| --- | --- |
| PostgreSQL | Транзакции, блокировки строк, ограничения уникальности и MVCC позволяют выразить лимит, outbox и согласованный снимок в одном хранилище. Выбран как единый механизм для четырёх владельцев. |
| MySQL/InnoDB | Допустимый альтернативный вариант с транзакциями и блокировками строк. В текущих требованиях нет преимущества, ради которого стоило бы поддерживать второй SQL-диалект. Не отклоняется как технически неспособный. |
| SQLite | Удобна для локального приложения, но один одновременно пишущий процесс на файл усложняет целевую работу нескольких реплик с интенсивной записью. Для данного стенда не предлагается. |

Свойства проверены 26 октября 2026 по официальным источникам: [PostgreSQL — изоляция](https://www.postgresql.org/docs/18/transaction-iso.html), [блокировки](https://www.postgresql.org/docs/18/explicit-locking.html), [ограничения](https://www.postgresql.org/docs/18/ddl-constraints.html), [MySQL/InnoDB](https://dev.mysql.com/doc/refman/26.10/en/innodb-transaction-model.html), [области применения SQLite](https://www.sqlite.org/whentouse.html). Выбор PostgreSQL — инженерное решение для этого проекта; достижение нагрузки из него не следует.

## Изоляция владельцев и миграции

- Отдельная БД и отдельный login для каждого сервиса. У runtime-роли нет superuser, CREATEDB, CREATEROLE, прав подключения к чужим БД и членства в чужих ролях. У PUBLIC отзываются лишние CONNECT/CREATE; схемы и search_path задаются явно. Общие credentials администратора сервисам не выдаются.
- DDL выполняется отдельной migration-ролью владельца; runtime получает только необходимые права на собственные объекты. Межсервисные SQL-запросы, FDW/dblink, общие таблицы и внешние ключи между владельцами не используются. Компоненты outbox-relay работают с правами своего владельца.
- SET-003 должен проверить разрешённое подключение к своей БД и отказ подключения к трём чужим под каждой runtime-ролью. Основа разделения — [БД, схемы и права PostgreSQL](https://www.postgresql.org/docs/18/ddl-schemas.html).
- SET-004: отдельная история версионированных миграций в каждой БД; один исполнитель миграций на владельца через блокировку. Повторный запуск не применяет уже выполненную версию; изменение применённого файла обнаруживается. Для транзакционного DDL ошибка откатывает миграцию и её запись истории вместе. Неатомарные операции требуют явного отдельного плана; runtime не меняет схему при старте запроса.
- Для принятой durable работы требуются постоянный volume, `fsync=on`, `synchronous_commit=on`, `full_page_writes=on` и обычные WAL-logged таблицы. Ack/успешный ответ выдаётся после commit. [Асинхронный commit](https://www.postgresql.org/docs/18/wal-async-commit.html) не подходит для обещанной устойчивости. Один экземпляр не обеспечивает переживание утраты диска/узла; HA и production-кластер вне объёма.

## Граница транзакций API

Обычные изменения выполняются в READ COMMITTED с явными блокировками. Единый порядок блокировок: строка пользователя/квоты и привязки → подписка → её workflow/attempt → счётчик журнала. Все пути одного инварианта используют этот порядок. Deadlock/serialization failure откатывают всю транзакцию; повтор ограничен и использует прежний ID команды. Сетевые вызовы market-data, брокера и Telegram не выполняются под блокировками БД. Полученная application-слоем котировка проверяется по контракту DEC-004; состояние/версия/канал перепроверяются под блокировкой.

1. **Создание:** заблокировать существующую строку пользователя, проверить текущую Telegram-привязку и число занятых слотов; при значении < 15 увеличить счётчик и записать подписку, версию и SubscriptionChanged/outbox одной транзакцией. Счётчик ограничен CHECK от 0 до 15; он равен числу незавершённых подписок. Один CHECK без сериализации путей создания/завершения не является защитой лимита.
2. **Запрос работы:** заблокировать каноническую подписку, проверить версию и состояние; сохранить единственный workflow, pending_delivery и AlertTriggered/outbox. Счётчик не уменьшается. Повтор возвращает прежний workflow.
3. **Допуск попытки:** согласовать привязку, workflow и подписку; сохранить request ID, результат допуска, attempt ID, срок и fencing token вместе с нужным переходом/событием. Единовременность действующей попытки проверяется под блокировкой workflow; время само по себе не используется в условии уникального индекса. Повтор request ID возвращает прежний результат, включая отказ/ожидание.
4. **Отмена/успех:** атомарно изменить допустимое состояние, сохранить результат, освободить слот однократно и записать изменение/outbox. Повтор и поздний исход известной попытки следуют DEC-004/005: отмена не возрождается, старый отказ не отменяет новый успех, слот повторно не освобождается.

Ограничения БД: уникальный нормализованный email; не более одного workflow на subscription_id; уникальные trigger_id, event_id и ключи идемпотентности в области соответствующей операции; известная попытка ссылается на свой workflow. Notifications независимо обеспечивает UNIQUE(trigger_id) для задания и уникальность attempt/result ID. Обязательные части ключей NOT NULL. Цены/пороги сохраняются точным десятичным представлением, не float; масштаб/границы закрепляются контрактом доменного типа. Конкретные таблицы и индексы — implementation-тикеты.

## Снимок S и commit-согласованная граница C

Для первой реализации выбран транзакционный счётчик журнала API в обычной строке PostgreSQL. Каждая транзакция, меняющая представление подписки в снимке, увеличивает счётчик под блокировкой и записывает неизменяемое изменение/outbox с этим номером в той же транзакции. Блокировка удерживается до commit/rollback; после неё запрещены дополнительные блокировки бизнес-строк и сетевое ожидание. Для нескольких изменений в одной транзакции выделяется диапазон, C указывает на конец целой транзакции. Это сериализует завершение таких записей; откат откатывает и счётчик.

Snapshot-builder API в одной REPEATABLE READ транзакции читает C и материализует все незавершённые подписки с workflow в собственные неизменяемые строки snapshot_id. Публикация ресурса и pin журнала от C выполняются до завершения builder-транзакции. Выдача страниц начинается только после её commit и использует стабильный порядок по ID; долгоживущая SQL-транзакция между HTTP-страницами не требуется. Ресурс хранит expires_at; после истечения/потери ресурса matcher начинает новый снимок.

Очистка журнала обязана согласовываться с регистрацией снимков: builder получает session-level shared advisory retention-lock до BEGIN REPEATABLE READ, чтобы ожидание блокировки не фиксировало преждевременный MVCC-снимок, и удерживает его до commit публикации pin. Очистка получает исключительный advisory lock и только после него читает актуальные pins в READ COMMITTED. Lock освобождается при завершении/ошибке builder, при утрате соединения ресурс снимка не публикуется. Реализация механизма и проверка гонки относятся к SUB-015. Журнал хранится как минимум до durable прогресса/отказа потребителей и действующих снимков; отправка outbox сама по себе не разрешает удаление replay-данных.

Обоснование: видимому в MVCC-снимке C соответствуют все транзакции журнала до C. Следующая транзакция не получает номер, пока предыдущая не завершилась. Не попавшее в снимок изменение получает номер > C и доступно replay. `MAX(sequence_id)`, время записи и последний опубликованный offset такой гарантии не дают: [sequence не откатывается с транзакцией](https://www.postgresql.org/docs/18/functions-sequence.html), а заранее выделенный номер не задаёт порядок commit.

Цена решения — общая точка сериализации записей журнала и стоимость материализации большого снимка. Короткая критическая секция не доказывает 10 000 запросов/с. Это явный риск для DEC-008/нагрузочных задач; если профиль не проходит, нужен отдельный пересмотр механизма по измерениям. DEC-007 должен сохранить C в событиях и определить транспорт replay/ack/retention; номер брокера не подменяет C автоматически.

## Durable состояние остальных владельцев

| Владелец | Что фиксируется до признания работы принятой |
| --- | --- |
| Market-data | Последняя корректная котировка/ревизия, идентичность поколения и статус потока плюс принятая работа публикации в собственном SQL-outbox одной транзакцией. Relay повторяет публикацию с устойчивым event_id; удаление/свёртка возможны только после явного результата по DEC-004/007. Сбой до commit не называется принятием; отсутствие upstream replay Binance остаётся наблюдаемым разрывом. |
| Matcher | Durable проекция или применённый результат вместе с checkpoint в своей БД до ack. Индекс в памяти восстанавливается из durable проекции; утрата полномочий отсекается fencing token. Устаревшая цена может получить явный результат «заменена более новой». Cursor не опережает durable применение; новая загрузка снимка строится отдельно до переключения. |
| Notifications | Задание до ack события; попытки, leases, fencing token, next_check_at, версия канала и состояние лимитеров между репликами. Исход Telegram и обязанность сообщить его API сохраняются одной локальной транзакцией. Потеря ответа API повторяет сообщение исхода; подтверждённая отправка не повторяется. Периодические проверки blocked переживают рестарт по DEC-005. |

Общей SQL-транзакции четырёх сервисов нет. Результат внешнего Telegram-вызова не становится атомарным с PostgreSQL; неоднозначность и возможный дубль сохраняются по DEC-004. Durable SQL-outbox market-data выбран как исходная граница принятия, а брокер и его режимы остаются DEC-007.

## Проверка решения на сценариях

Это проверка принятого протокола рассуждением, не выполненные интеграционные тесты.

| Сценарий | Ожидаемый результат по решению |
| --- | --- |
| 14 подписок, два конкурентных create | Первый держит lock пользователя и фиксирует 15. Второй после ожидания видит 15 и отклоняет создание; его подписки/outbox нет. |
| Ошибка вставки outbox после резервирования слота | Rollback подписки, счётчика лимита и номера журнала; до commit успешного ответа нет. |
| Commit прошёл, relay упал до publish | Событие остаётся в БД; после рестарта публикуется с тем же event_id. |
| Publish прошёл, подтверждение потеряно | Relay повторяет; потребитель дедуплицирует, второго workflow/job нет. Конкретный ack протокол — DEC-007. |
| Одновременно cancel и success, затем повтор success | Сериализация по пользователю/подписке; слот освобождается один раз, поздний успех сохраняется согласно DEC-004. |
| T1 получил номер C, T2 хочет C+1, snapshot во время T1 | T2 ждёт T1; snapshot видит целиком прежние данные и прежнюю C либо весь commit T1. Поздний commit не скрывается ниже видимой границы. |
| Подписку изменили между страницами | Страницы читают один материализованный snapshot_id; изменение приходит replay после C. |
| Cleaner конкурирует с созданием snapshot | Retention-lock не позволяет удалить нужный хвост между фиксацией границы и публикацией pin. Истечение возвращает явную ошибку и новый bootstrap. |
| Рестарт market-data/notifications/matcher | Восстанавливаются outbox/проверки/проекция с checkpoint; нет ack раньше локального commit. |
| Runtime сервиса пытается подключиться к чужой БД | Отказ прав; доступ к чужим данным остаётся через интерфейс владельца. |

Фактические интеграционные проверки перечисленных инвариантов обязательны в соответствующих implementation-тикетах с реальным PostgreSQL. В DEC-006 исполняемые тесты не требуются.
