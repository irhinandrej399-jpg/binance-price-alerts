# DEC-007 — Брокер событий и модель доставки

Дата: 26 октября 2026, Europe/Moscow. Статус: **принято**.

Карточка: [DEC-007](../backlog/tickets/DEC-007.md). Основания: принятые [DEC-003](DEC-003.md), [DEC-004](DEC-004.md), [DEC-006](DEC-006.md). Ни брокер, ни Go-адаптеры этим документом не реализованы. Ниже зафиксирован согласованный протокол; реализация и нагрузочная проверка относятся к последующим карточкам.

## Варианты и рекомендация

Выбран Apache Kafka в режиме KRaft как единственный брокер первой очереди. Для локального стенда — один broker/controller с постоянным volume, replication factor 1 и min.insync.replicas=1. Это переживание рестарта процесса при сохранном хранилище, а не HA и не защита от утраты диска. Версию, образ и ресурсы закрепляет SET-005 после проверки поддерживаемого выпуска; ссылка на документацию 4.3 не назначает версию стенда.

| Вариант | Оценка для проекта |
| --- | --- |
| Apache Kafka | Рекомендуется: журнал, порядок внутри партиции, повторное чтение и consumer groups прямо соответствуют запланированным MAT-010/011. Цена — более тяжёлый локальный runtime и явная работа с offsets, транзакционным producer и очисткой. |
| NATS JetStream | Допустимая альтернатива: durable pull consumers, явные ack и управление переполнением. Для исключительного владения ценовыми шардами между репликами пришлось бы дополнительно закрепить координацию и fencing; shared consumer сам по себе этого не доказывает. |

Это инженерное сравнение для данного бэклога, не измерение производительности брокеров. Kafka не доказывает выполнение p99 или burst 10 000/с. Свойства JetStream: [официальное описание](https://docs.nats.io/concepts/jetstream).

## Потоки и порядок

Три отдельных topic: `subscription-changes`, `prices`, `delivery-requests`. Имена получают префикс среды; тесты не используют рабочие topics.

- `subscription-changes`: одна партиция первой версии, один логический relay API, последовательная публикация целых транзакций журнала по C. События содержат исходные event_id, subscription_id, версию и позицию/конец транзакции журнала. Полный журнал или явные маркеры его границ позволяют отличить пропуск от записи, не меняющей проекцию. C не выводится из Kafka offset.
- `prices`: ключ — нормализованная пара; фиксированное отображение пары в партицию. Число партиций задаётся SET-005 и фиксируется профилем DEC-008 до измерений. Изменять его на работающем потоке без остановки и миграции checkpoint нельзя. Market-data назначает монотонную ревизию пары durable; идентичность поколения и source ID сохраняются. Relay публикует ревизии одной пары последовательно. Независимые пары могут обрабатываться параллельно.
- `delivery-requests`: ключ — subscription_id, payload с устойчивым trigger_id/workflow. Глобального порядка с ценами и изменениями подписок нет. Notifications всё равно запрашивает канонический допуск API перед отправкой.

На каждый publish-шард — стабильный transactional.id, зависящий от среды, владельца и шарда, а не PID. Новый relay сначала инициализирует producer и отсекает прежний Kafka producer, затем продолжает SQL-outbox. Одновременно работающий старый producer после fencing прекращает публикации. Стабильный ID нельзя совместно использовать независимым шардам. Consumers читают только `read_committed`; приложение не выдаёт SQL-отметку публикации раньше успешного commit Kafka-транзакции. Это локальная Kafka-транзакция, не распределённая транзакция с PostgreSQL.

Конфигурация producer: `acks=all`, идемпотентность включена, retries включены, max.in.flight не больше 5. Имена параметров здесь приведены по Kafka; Go-клиент должен обеспечивать эквивалентную семантику. Идемпотентность producer не заменяет устойчивый event_id при повторном чтении SQL-outbox после рестарта. Основания: [producer configuration](https://kafka.apache.org/43/configuration/producer-configs/).

## Durable принятие, публикация и ack

1. API/market-data фиксируют своё состояние и SQL-outbox одной PostgreSQL-транзакцией по DEC-006. До commit работа не считается принятой.
2. Relay публикует исходное событие и ждёт подтверждения commit Kafka-транзакции. Только затем помечает outbox опубликованным. Ошибка/timeout оставляет обязанность повтора; повтор использует тот же event_id. Сбой после Kafka commit до SQL-отметки создаёт допустимый дубль.
3. Consumers отключают auto-commit. Matcher сохраняет результат/проекцию и checkpoint в одной своей SQL-транзакции; notifications сохраняет уникальное задание по trigger_id и позицию входа. Только после этого разрешён commit следующего Kafka offset. Продвигается лишь непрерывно обработанный префикс партиции.
4. Сохранённое задание notifications подтверждает приём события, а не отправку Telegram. Попытки, проверки, результаты и обязанность сообщить исход API восстанавливаются из БД notifications по DEC-004/005/006.
5. Matcher не подтверждает цену после одного поиска кандидатов. Либо сохранена durable продолжимая работа со всеми оставшимися кандидатами, либо завершены необходимые идемпотентные запросы API и сохранён результат. Старая цена может получить явный durable результат «заменена ревизией R»; принятые workflow/результаты этим не удаляются.

Kafka offset хранится вместе с результатом в PostgreSQL и является транспортной позицией. После рестарта SQL-checkpoint авторитетен: потерянный broker offset commit даёт повтор, а не потерю результата. Незнакомые версии/повреждённые сообщения останавливают соответствующую партицию с видимой ошибкой; молчаливый skip и автоматический ack после N ошибок запрещены. Backoff ограничен по частоте, но durable работа не истекает по числу попыток.

Для локального RF=1 предлагается `flush.messages=1` для прикладных topics; постоянный volume обязателен. `acks=all` само по себе не означает fsync или несколько реплик. Частый fsync — осознанная цена первой конфигурации и риск для нагрузки; ослаблять его под видом оптимизации без пересмотра гарантии нельзя. Внутренние topics/transaction state должны быть настроены для одноброкерного профиля и проверены в SET-005. Утрата диска остаётся за границей обещаний.

Основания: [consumer configuration](https://kafka.apache.org/43/configuration/consumer-configs/), [Kafka о совместном хранении результата и позиции](https://kafka.apache.org/43/design/design/), [flush и retention topics](https://kafka.apache.org/43/configuration/topic-configs/). Фактические проверки с выбранным Go-клиентом обязательны позднее.

## Retention и перегрузка

Для всех трёх topics начальная безопасная конфигурация: `cleanup.policy=delete`, `retention.ms=-1`, `retention.bytes=-1`; compaction выключена. Возраст и объём не удаляют необработанные задания. Это не обещание бесконечного диска: память, очереди и диск имеют явные бюджеты; DEC-008 задаёт вместимость и длительность опыта. До безопасной очистки локальный стенд работает в пределах этого бюджета.

Достижение верхнего порога диска останавливает приём новой работы до физического исчерпания, показывает degraded/not-ready и метрики. Relay ограничивает in-flight/память, повторяет с backoff и не удаляет принятые SQL-записи при ошибке брокера. API отклоняет новые изменения до commit с временной ошибкой; команды завершения уже принятой работы требуют зарезервированного места. Market-data при невозможности durable commit прекращает приём, обозначает разрыв Binance; не называет незафиксированные события принятыми. Политика не обещает бесконечный burst.

Очистка брокера разрешена только отдельным проверенным cleaner через безопасную границу каждой партиции: ниже минимального durable SQL-checkpoint всех зарегистрированных обязательных потребителей. Kafka committed offset сам по себе не доказывает бизнес-прогресс. Неизвестный/потерянный потребитель запрещает очистку до явного вывода из эксплуатации; рестарт не считается отказом от работы. Автоматический cleaner не прячется в SET-005 или producer: при принятии ADR ему нужна отдельная узкая карточка с тестами гонок. До его реализации автоматической очистки нет.

SQL-журнал API очищается независимо от брокера: только с учётом действующих snapshot-pins и durable прогресса потребителей по DEC-006. Отметка publish не снимает pin. Снимок имеет объявленный expires_at; после истечения загрузка отклоняется явно, частичная проекция отбрасывается и строится заново. У принятого workflow/задания TTL нет.

## Snapshot, replay и live

API выдаёт S на commit-согласованной границе C из PostgreSQL. Matcher регистрирует durable replay-pin, загружает страницы, затем читает SQL-журнал строго после C до объявленной целой границы H. Применение изменений и cursor атомарны в БД matcher; API получает только подтверждённый durable прогресс. Транспорт SQL-replay — защищённый интерфейс API, без доступа к его БД.

Kafka-потребление изменений регистрируется до фиксации H; входной хвост сохраняется ограниченно и durable либо перечитывается. Изменения до H дедуплицируются, после H применяются по C. Если публикация отстаёт, matcher продолжает SQL-replay, включая периодическую проверку head журнала: отсутствие Kafka-событий не доказывает актуальность. При пропуске C используется SQL-хвост, при потере необходимого SQL-pin — явный новый snapshot. Kafka offset никогда автоматически не считается C; Kafka здесь ускоряет доставку, а SQL-журнал закрывает replay-окна.

Последние цены подключаются отдельно по MAT-012: зарегистрировать обновления, прочитать последнюю котировку market-data, объединить по монотонной ревизии. Старое событие не откатывает новую цену; cursor цен не смешивается с C. До snapshot/replay и подключения цен matcher не ready. При смене владельца партиции сначала восстанавливаются checkpoint и последние цены, затем разрешается обработка. Исчезнувшее историческое условие не воспроизводится.

Consumer group распределяет ценовые партиции. MAT-010/011 обязаны согласовать назначение с durable fencing token в БД matcher: старый владелец не меняет checkpoint/проекцию после смены токена. Одного rebalance Kafka недостаточно для запрета запоздалой SQL-записи. Запоздалый внешний запрос API безопасен благодаря канонической идемпотентности и проверке текущего условия.

## Проверка протокола на сбоях

Это анализ предлагаемого решения, не выполненные интеграционные тесты.

| Точка сбоя | Восстановление |
| --- | --- |
| До commit PostgreSQL | Работа не принята; нет успешного ответа, разрыв рынка наблюдаем. |
| После SQL commit, до publish | SQL-outbox остаётся; relay повторяет после восстановления. |
| После publish, до Kafka commit | Незавершённая Kafka-транзакция не видна read_committed; следующий producer завершает восстановление и повторяет из SQL. |
| Kafka commit произошёл, ответ потерян | SQL-отметки нет; повтор с прежним event_id, consumer дедуплицирует. |
| После локального commit consumer, до commit offset | Повтор не создаёт второго job/workflow; SQL-checkpoint не откатывается. |
| Matcher упал после 37 из 100 кандидатов | Продолжается durable работа; при прежней подходящей цене достигаются 100 уникальных workflow, при изменившейся цене исчезнувшее условие не восстанавливается. |
| Старый владелец партиции ожил | Producer fencing запрещает старые публикации; SQL fencing запрещает старый checkpoint. |
| Snapshot читается, create/cancel commit после C | Изменение находится в SQL-replay > C; Kafka-дубль не откатывает версию. |
| Relay отстаёт или потерян Kafka cursor | SQL-replay/pin закрывают окно подписок; цены проходят latest-price bootstrap. Delivery-задания не пропускаются через reset на latest. |
| Snapshot истёк | Явная ошибка, отказ от частичной загрузки и новый снимок. |
| Брокер недоступен/диск у порога | Ограниченные повторы, сохранение SQL-outbox, остановка нового приёма; никаких удалений по возрасту. |
| Telegram ответил успешно, API временно недоступен | Notifications повторяет durable фиксацию исхода API, а не подтверждённый Telegram-вызов. |

## Последствия для реализации

Обновлены требования и карточки SET-005, CON-001, SUB-007/009, MKT-013/014, NTF-001, MAT-008/009/010/011/012. SUB-015 сохраняет pin/cleaner журнала API. Защищённый интерфейс SQL-replay с durable прогрессом/pins выделен в [SUB-022](../backlog/tickets/SUB-022.md), безопасный cleaner Kafka — в [OPS-014](../backlog/tickets/OPS-014.md); ORDER синхронизирован. Они не реализуются скрытно в SUB-016 или SET-005. Ограничители нового приёма выделены в [OPS-015](../backlog/tickets/OPS-015.md) для API и [OPS-016](../backlog/tickets/OPS-016.md) для market-data: health-задачи используют готовое состояние и не реализуют эти ограничения скрытно. DEC-008 должен согласовать точный учёт/резервирование ёмкости до их ready. Сессионную готовность всех implementation-задач проверять заново.
