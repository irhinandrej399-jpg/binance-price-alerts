# DEC-001 — Семантика достижения цены

Дата: 26 октября 2026, Europe/Moscow.
Статус: **принято**.
Карточка: [DEC-001](../backlog/tickets/DEC-001.md).

## Контекст

Согласованы цена последней сделки Binance Spot, фиксированный порог и одноразовая подписка. До этого решения требования не определяли направление сравнения, включение равенства и случай, когда условие выполнено уже при создании. На момент принятия кода приложения нет; внешнее API не определяет продуктовую семантику нашего уведомления.

## Принятый контракт

Вход предиката: текущая допустимая цена `P`, фиксированный порог `T` и направление `up` либо `down`. Выход — логическое значение:

- `up` («не ниже»): `P >= T`.
- `down` («не выше»): `P <= T`.

Для конкретной цены пользователь явно выбирает направление; оно не выводится из положения порога относительно текущей цены. Для процентной подписки рост задаёт `up`, падение — `down`; процент преобразуется в фиксированный порог от исходной свежей цены, как уже установлено требованиями.

Равенство удовлетворяет обоим направлениям. Предыдущая цена не нужна: это проверка текущего условия, а не обязательного перехода из ложного состояния в истинное. Поэтому скачок через порог и первая допустимая цена за порогом также удовлетворяют условию.

Если свежая цена, используемая при создании, уже удовлетворяет условию, подписка принимается и подлежит однократному срабатыванию без ожидания нового пересечения. Это не обещание отправить Telegram в HTTP-запросе. DEC-004 должен определить фиксацию этого срабатывания, границу активации и обработку гонок; он не должен терять уже выполненное условие из-за задержки индексации. Критерий свежести остаётся в DEC-002.

## Проверка примеров

Во всех строках `T = 100`. Стрелка показывает последовательность полученных цен; предикат проверяется для каждой допустимой цены активной подписки.

| Направление | Цены / ситуация | Ожидаемый результат |
| --- | --- | --- |
| up | 99 → 100 | false → true; равенство срабатывает |
| down | 101 → 100 | false → true; равенство срабатывает |
| up | 99 → 101 | false → true; точное попадание в 100 не нужно |
| down | 101 → 99 | false → true; точное попадание в 100 не нужно |
| up | 98 → 99 | false → false |
| down | 102 → 101 | false → false |
| up или down | При создании P = 100 | true; срабатывание без ожидания следующей цены |
| up | При создании P = 101 | true; подписка принимается и срабатывает |
| down | При создании P = 99 | true; подписка принимается и срабатывает |
| up | Первая допустимая цена P = 101, предыдущей нет | true; предыдущее значение не требуется |
| down | Первая допустимая цена P = 99, предыдущей нет | true; предыдущее значение не требуется |

После первого срабатывания подписка завершается по согласованному одноразовому жизненному циклу; повторные истинные значения не создают новое срабатывание. Пропущенные внешние сделки не восстанавливаются этим предикатом.

## Рассмотренные варианты

1. **Явное направление, включённое равенство и проверка текущего условия — выбран.** Формулировки «не ниже» и «не выше» однозначны; для проверки достаточно одной цены; уже выполненная заявка не ждёт возврата рынка.
2. **Строгое пересечение с предыдущей ценой.** Требует хранить предыдущее значение и отдельно определять начальное состояние. Уже выполненная заявка может ждать обратного движения и повторного пересечения.
3. **Автоматическое направление по цене создания.** Убирает выбор направления для абсолютного порога, но требует отдельного правила равенства и не позволяет явно попросить уже выполненное условие.
4. **Отклонять уже выполненное условие.** Исключает немедленное срабатывание, но добавляет продуктовую ошибку вместо обработки допустимого ценового условия.

## Последствия

- Контракт закреплён в requirements.md и реестре ADR; зависимые карточки уточнены без изменения их статусов и зависимостей.
- DOM-002: фиксировать направление роста/падения вместе с порогом; точность, округление и допустимость процентов остаются в этой доменной задаче.
- DOM-003: чистый предикат от одной цены, порога и направления; заменить неоднозначные сценарии «пересечения» явными проверками из таблицы.
- DEC-004: учесть уже выполненное условие создания при выборе протокола активации. Сам протокол здесь не выбирается.
- Не добавлять Go-код, повторяющиеся подписки и реализацию следующих тикетов.

## Основание согласования

26 октября 2026 владелец ответил «да» на предложение согласовать явные направления «не ниже»/«не выше», включённое равенство, скачок через порог и срабатывание уже выполненного условия при создании. Подтверждение относится к изложенному контракту; freshness и протокол активации остаются отдельными решениями DEC-002 и DEC-004.
