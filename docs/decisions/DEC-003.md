# DEC-003 — Владельцы данных четырёх сервисов

Дата: 26 октября 2026. Статус: **принято**.

Карточка: [DEC-003](../backlog/tickets/DEC-003.md). Основание — согласованные [требования](../requirements.md) и проверка зависимых карточек. Схема согласована владельцем проекта, основание приведено в разделе «Согласование».

## Уточнение DEC-004

26 октября 2026 [DEC-004](DEC-004.md) сохранил таблицу владельцев, но пересмотрел прежнюю независимость terminal-срабатывания от доставки. API хранит канонический workflow, допускает конкретную попытку после проверки последней цены и завершает подписку/освобождает слот после подтверждённого успеха либо отмены. AlertTriggered теперь запрашивает условную работу доставки и не освобождает слот. Notifications владеет заданием/попытками и durable передаёт исход API; никогда не меняет его таблицы. При исчезнувшем условии подписка ждёт дальше. Описание прежнего active→triggered и уже освобождённого до доставки слота ниже — история исходного решения, заменённая DEC-004. Остальная таблица владения и изоляция остаются действующими.

## Контекст и варианты

Нужно сохранить лимит активных подписок, однократность срабатывания и независимую доставку в четырёх процессах. У каждого канонического состояния должен быть один владелец. Реплика или проекция другого сервиса не получает права менять оригинал.

1. **API владеет жизненным циклом подписки, matcher — проекцией.** Создание, отмена, лимит и срабатывание сходятся в одной транзакционной границе. Matcher обращается к API для фиксации найденного условия. Цена решения — внутренний вызов на срабатывание и нагрузка на API-хранилище.
2. **Matcher владеет жизненным циклом подписки.** API передаёт ему команды создания и отмены. Возможный вариант, но matcher получает также пользовательский лимит, каноническое хранение и обслуживание команд; существующую декомпозицию SUB/MAT потребуется существенно пересмотреть.
3. **API и matcher напрямую меняют общие таблицы.** Упрощает отдельный вызов, но связывает сервисы схемой хранения и распределяет ответственность за переходы и лимит. Не предлагается.

Принят вариант 1: он сохраняет текущую декомпозицию и объединяет связанные инварианты у одного владельца. Выбор не доказывает достижение целевой нагрузки; это проверяется отдельными нагрузочными тикетами.

Владелец — сервис как логическая граница, а не отдельная реплика. Общее состояние его реплик остаётся ответственностью этого сервиса. Допускается один физический сервер СУБД с раздельными логическими областями и правами; чужие таблицы напрямую не читаются и не изменяются. Конкретное размещение определит DEC-006.

## Проверка жизненного цикла

1. **Создание.** API аутентифицирует пользователя, получает каталог/последнюю котировку у market-data, сохраняет исходную цену и порог у себя. Проверка лимита и принятие подписки согласованы внутри владельца. Изменение для matcher сохраняется в локальном outbox. При missing/invalid_time возвращается 503 quote_unavailable без подписки и слота по DEC-002. Передача уже выполненного условия и граница активации требуют DEC-004.
2. **Отмена.** API проверяет владельца и выполняет допустимый переход у себя, освобождает слот и сохраняет изменение в своём outbox атомарно. Matcher применяет событие к своей проекции. Запоздавший кандидат срабатывания проходит проверку канонического состояния в API; одна лишь старая проекция не разрешает срабатывание.
3. **Срабатывание.** Matcher находит кандидата по цене и вызывает защищённую операцию API. API проверяет каноническую подписку и условие согласно будущему DEC-004. Успешная операция атомарно фиксирует срабатывание, устойчивый trigger_id, освобождение слота и AlertTriggered в outbox. Повтор не создаёт нового уникального срабатывания. Какая конкурентная операция отмены/срабатывания побеждает и какое доказательство цены принимается, определяет DEC-004.
4. **Доставка.** Notifications сохраняет задание по trigger_id в своём хранилище до подтверждения события. Повторная доставка события не создаёт второе задание. Ошибка Telegram оставляет работу в notifications; активный слот уже освобождён владельцем подписки.

Во всех четырёх путях каждый сервис пишет только собственное состояние. Единой транзакции API и notifications нет: разрыв между ними закрывают durable событие, повтор и дедупликация. Точный транспорт и правила подтверждения относятся к DEC-007.

## Границы и последствия

- DEC-004 должен использовать API как владельца атомарного перехода, но отдельно определить активацию, согласование снимка с потоком цен, проверку кандидата и гонки. Владение само по себе эти задачи не решает.
- DEC-005 определит допуск без Telegram. Способ получения адресата для задания, поведение при смене привязки и состав контракта AlertTriggered нужно явно определить до реализации соответствующих контрактов; эта таблица выбирает только владельца привязки.
- Уточнены requirements.md и карточки DEC-004/006/007, SUB-001/013/014/016, MKT-006, MAT-001, NTF-001/004 и OPS-001/013 в части владельцев и доступа. Состав и зависимости задач сохранены; порядок ORDER остаётся прежним.
- СУБД, брокер, wire-протоколы, шардирование, точные схемы событий и способ репликации не выбираются этим ADR. Реализация Go не входит в DEC-003.

## Согласование

26 октября 2026 владелец ответил «да» на предложение согласовать таблицу владения: API — аккаунты, Telegram-привязка, подписки, лимит, срабатывания и outbox; market-data — котировки и состояние потока; matcher — проекция, индекс и checkpoints; notifications — задания, повторы и лимитеры. Перед согласованием были представлены внутренний вызов matcher → API и проверка жизненного цикла без записи в чужую БД. Решение принято в пределах этого ADR; протокол активации и выбор инфраструктуры остаются отдельными тикетами.
