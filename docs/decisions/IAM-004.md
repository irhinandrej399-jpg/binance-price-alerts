# IAM-004 — Формат пользовательской сессии

Дата: 27 октября 2026, Europe/Moscow. Статус: **принято**.
Карточка интерфейсной задачи: [IAM-004](../backlog/tickets/IAM-004.md).

Требования оставляли формат сессии для соответствующей интерфейсной задачи.
В этой сессии предложен непрозрачный Bearer-токен вместо самостоятельных
подписанных claims. Пользователь явно ответил: «Согласовать: Bearer-токен, 24 часа».

- Токен: 32 случайных байта crypto/rand, canonical base64url без padding
  (43 символа). Передаётся клиенту только при успешном входе.
- API хранит в PostgreSQL только SHA-256 от строкового токена, user_id и
  expires_at. Это API-owned состояние, другим сервисам доступ к таблице не даётся.
- Конечный TTL — 24 часа с момента выдачи. Условие действительности строгое:
  now < expires_at; на самой границе и после неё сессия отклоняется.
- Успех выдачи требует успешного INSERT/commit. Время задаёт сервер API;
  реплики должны иметь согласованные часы. В тестах часы управляемые.
- Неизвестный email и неверный пароль дают один 401 invalid_credentials.
  Для неизвестного email выполняется dummy Argon2id-проверка с тем же профилем.
- Токены, пароли и хеши паролей не логируются и не включаются в ошибки.
  Клиент использует HTTPS и Authorization: Bearer <token>, не query string.

Проверка токена требует чтения PostgreSQL; недоступность БД не разрешает доступ.
В отличие от JWT, нет ключа подписи и автономной проверки claims. Привязка
токена к user_id в хранилище даёт доверенного владельца для будущего IAM-005.
Middleware, logout, refresh, password reset, очистка истёкших строк и runtime
в этой задаче не реализуются. Повторный вход создаёт независимую сессию;
удаление аккаунта каскадно удаляет его сессии.
