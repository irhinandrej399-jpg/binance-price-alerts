# Проверенные ограничения интеграций

Проверено по официальной документации 25 октября 2026. Перед реализацией адаптеров ограничения и поля нужно сверить снова.

## Binance Spot

Одно WebSocket-соединение объединяет до 1024 streams. Пользовательские правила не требуют отдельных соединений: одинаковая пара может обслуживать много подписок приложения. Соединение рассчитано на 24 часа; ping приходит каждые 20 секунд, pong с тем же payload ожидается в течение минуты. Нужно обрабатывать shutdown и восстановление подписок.

Ограничение 5 входящих сообщений/с относится к сообщениям **клиента в Binance**, включая управляющие команды и ping/pong; это не лимит получаемых ценовых событий. Есть отдельный лимит попыток соединения по IP.

Официальные источники: [WebSocket streams](https://github.com/binance/binance-spot-api-docs/blob/master/web-socket-streams.md), [рыночный REST API](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/market).

Trade/aggTrade дают события сделок с ценой и идентификатором. В MKT-002 выбран raw `trade`: отдельная сделка, ID `t`, цена `p`, время сделки `T` и события `E`. Поля повторно сверены 27 октября 2026 по официальному WebSocket-контракту; чистый [декодер](../internal/marketdata/trade/README.md) готов, сетевой клиент ещё не реализован. Reconnect сам по себе не восстанавливает отсутствовавшие сделки. По решению владельца восстановление внешней истории отложено; от приложения требуется наблюдаемый разрыв.

## Telegram

Бесплатная массовая рассылка ограничена примерно 30 сообщениями/с на бота; в один чат рекомендуется избегать частоты выше одного сообщения/с. Это внешние ограничения, а не целевая производительность matcher. Фактический limiter конфигурируется с учётом актуальных условий API.

При flood control Telegram может вернуть retry_after — время ожидания в секундах. Успешный sendMessage возвращает Message. У метода не опубликован параметр клиентского ключа идемпотентности.

Официальные источники: [FAQ: рассылка](https://core.telegram.org/bots/faq#how-can-i-message-all-of-my-bot-39s-subscribers-at-once), [ResponseParameters](https://core.telegram.org/bots/api#responseparameters), [sendMessage](https://core.telegram.org/bots/api#sendmessage).

Инженерный вывод из контракта: при потере ответа после приёма запроса Telegram сообщение могло быть отправлено. Локальный уникальный trigger_id защищает внутренние задания от дублей, но не даёт exactly-once внешней доставки.

Расчёт для масштаба: один всплеск из 10 000 отдельных сообщений при 30/с требует около 333 секунд отправки даже без ошибок. Непрерывный вход 10 000 уведомлений/с при таком выходе не образует устойчивую систему: нужно менять продуктовую политику, бюджет рассылки либо входной профиль. В DEC-008 требуется явно установить длительность burst.

Нагрузочные тесты используют fake Binance и fake Telegram; массовые реальные сообщения не отправляются.
