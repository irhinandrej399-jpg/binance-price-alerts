# Работа агента в Binance Price Alerts

Учебный Go backend, четыре микросервиса, разработка поведения через TDD. Согласованные требования: [docs/requirements.md](docs/requirements.md). Протокол работы по тикетам: [docs/WORKING.md](docs/WORKING.md).

## Начало сессии по тикету

1. Возьми ровно один ID, названный пользователем. Если поручено выбрать следующий, используй `python3 scripts/backlog.py next`: он берёт первую незавершённую строку [ORDER.md](docs/backlog/ORDER.md), предварительно показывая уже начатую работу. Выполни только один тикет. Самостоятельно не перескакивай очередь; прямое поручение пользователя имеет приоритет, зависимости проверяются всегда. Обслуживание самого процесса работы не требует выдумывать продуктовый тикет.
2. Прочитай [docs/STATE.md](docs/STATE.md), карточку `docs/backlog/tickets/<ID>.md`, [правила TDD и готовности](docs/backlog/workflow.md). Затем прочитай только нужные ADR, интерфейсы завершённых зависимостей и относящийся к задаче код. Весь бэклог загружать в контекст не нужно.
3. Проверь состояние файлов, а при наличии Git — `git status --short` и относящийся к работе diff. Существующие изменения пользователя сохраняй. Код, конфигурация и наблюдаемые результаты важнее устаревшей сводки.
4. Проверь зависимости и размер сессии. `split` — контейнер: целиком его не выполнять. `done` у зависимости проверяй по её результату и артефактам. Если зависимость не готова, зафиксируй препятствие и назови нужный ID вместо скрытого выполнения нескольких задач.
5. Для реализации переведи `planned` в `ready` только после сессионной проверки, затем в `in-progress`; обнови строку индекса и активный ID в STATE. Для DEC сначала исследуй факты и сформулируй варианты; несогласованное продуктовое решение оставь в `decision`.

## Выполнение

- Один проверяемый результат за сессию, включая проверку и передачу состояния. После него не переходи к следующему тикету автоматически.
- Для поведения соблюдай Red → Green → Refactor. Фиксируй проверенную причину падения и итоговые команды. Для документации/инфраструктуры используй соответствующую проверку без искусственных unit-тестов.
- Готовые зависимости используй через их интерфейсы; новую архитектуру, отсутствующий test harness или независимое поведение не прячь внутри текущей задачи. Если объём вырос, сначала выдели узкую задачу и обнови зависимости.
- При добавлении, разделении или изменении зависимостей тикета синхронизируй ORDER.md: каждая активная карточка присутствует ровно один раз, все зависимости находятся раньше неё. Контейнеры split в очередь не входят.
- Исправляй ошибки внутри текущего результата. Обнаруженную независимую проблему запиши с воспроизведением и отдельным ID, не расширяя текущую реализацию.

## Завершение и передача

1. В карточке добавь/обнови `Ход работы` и `Передача следующей сессии`: что изменено, файлы, команды и фактические результаты, открытые вопросы, точный следующий шаг. При незавершённой работе особенно важно сохранить недостающие действия и текущую причину сбоя.
2. `done` выставляй только при выполненных критериях и необходимых проверках. Недоступную проверку так и запиши; не подменяй её успехом. При согласованном отдельном ревью используй `review` до его завершения. Незаконченная работа остаётся `in-progress` либо `planned`, если упёрлась в предпосылку, с явно записанной причиной.
3. Синхронизируй статус карточки, строку [индекса](docs/backlog/README.md) и краткую навигацию [STATE](docs/STATE.md). STATE не должен дублировать весь журнал тестов или список карточек.
4. Материальное принятое решение запиши в `docs/decisions/<ID>.md`, свяжи с DEC-карточкой и при необходимости обнови требования. Гипотезы отмечай как гипотезы.
5. Выполни `python3 scripts/backlog.py check`. После выполнения всех критериев **самостоятельно создай локальный коммит** по [правилам Git](docs/GIT.md), используя `scripts/git_ticket.py`, явный список файлов и сообщение `type(ID): описание` с разделами изменений и проверок. Пользователь уже разрешил эти коммиты; повторно спрашивать не нужно. Карточка, индекс и STATE входят в коммит. Незавершённую работу не коммить как завершённый тикет.
6. После commit проверь `git status --short` и `git show --stat HEAD`. В итоговом ответе назови ID, статус, SHA коммита, результат, проверки и оставшиеся ограничения. SHA этого же коммита не вписывай обратно в STATE/карточку: его можно найти в Git log по ID.

Не полагайся на память предыдущего чата: рабочее состояние должно восстанавливаться из файлов. Чтение тикета само по себе не повод создавать commit. Для завершённого результата commit — часть поручения. Один агент работает последовательно; для текущего этапа достаточно ветки main.
