# Общий лимитер бота — NTF-004

`New(notificationsPool, botID, rate)` и `TryAcquire(ctx) (wait, error)`
ограничивают совокупные допуски всех реплик одного бота. `botID` — каноническое
положительное числовое ID бота, сохраняющееся при ротации секрета; это числовая
часть token до `:`, без секрета. Все реплики обязаны использовать одну БД
notifications и один ID. Доступ к API-хранилищу не нужен.

`rate` — целое число допусков/с, 0 выбирает 25/с; диапазон 1..1 000 000
ограничен разрешением PostgreSQL в микросекундах. Интервал `ceil(1s/rate)`
округляется вверх. Диапазон — технический, не разрешение превышать политику
Telegram. На 30 октября 2026 бесплатная рассылка ограничена примерно 30/с,
поэтому default 25/с оставляет запас; paid broadcast адаптером не включается.
Настройки проверяются по актуальному [Telegram FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).
429 всё равно возможен: ожидание retry_after и retry-политика — другие тикеты.

Миграция `migrations/notifications/002_bot_limit.sql` добавляет только собственную
таблицу notifications. Транзакционная блокировка одной строки сериализует
конкурентов; после получения блокировки читается `clock_timestamp()` БД.
Grant сохраняет `next_allowed_at = now + interval` и возвращается только после
commit. Положительный wait не резервирует будущую отправку: caller ждёт с
context и снова вызывает TryAcquire. Ошибка всегда запрещает отправку, в том
числе при неизвестном исходе commit. Неиспользованный grant не возвращается.
Пауза БД назад продлевает ожидание; скачок вперёд допускает только один grant.
После простоя нет накопления credits, после рестарта состояние не сбрасывается.

Успех — **только** `err == nil && wait == 0`. Допуск используется немедленно
для одной попытки. Его нельзя складывать в локальную очередь или сохранять
для последующей отправки: лимитер измеряет допуски, а планировщик/сеть могут
задерживать реальные HTTP-запросы. После положительного wait обязательно заново
конкурировать за квоту. Worker отдельно должен проверить актуальный допуск API
и последнюю цену перед Send, не сохраняя старый допуск на время ожидания.
Отмена/ошибка HTTP не возвращает квоту. Лимитер чата и runtime здесь отсутствуют.

Интервал хранится вместе с ID. Несогласованная конфигурация возвращает
`ErrConfiguration` без grant. Для изменения rate нужно остановить реплики,
транзакционно изменить interval_us у владельца, сохранив next_allowed_at,
и запустить все реплики с новой настройкой. Удалять строку для обычного
рестарта/ротации token нельзя: это сброс квоты. Изменение rate не даёт новый
немедленный grant в обход сохранённого срока.

Проверки: `python3 scripts/check_postgres.py` запускает реальные PostgreSQL
тесты с race detector. Два независимых pool, восемь конкурирующих вызовов на
каждом из 100 fake-clock шагов, повторное создание лимитера, простой, обратный
ход часов, несовпадение настроек, отмена, точная граница округления и часы БД.
Fake clock доступен только внутренним тестам; публичный API не принимает часы
реплики. Без POSTGRES_TEST интеграционные тесты явно пропускаются. Нагрузочная
производительность и фактическая доставка Telegram этим прогоном не измеряются.
