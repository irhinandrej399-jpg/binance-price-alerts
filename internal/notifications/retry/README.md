# Расписание повторов — NTF-006

`New(Config)` создаёт неизменяемую политику; все интервалы и `MaxFailures`
задаются явно. Runtime-конфигурация и её значения подключаются отдельно.

- `Retry(now, failures, cause, entropy)` принимает число уже сохранённых временных
  ошибок **до** текущего исхода и `telegram.Error` (в том числе wrapped) с Kind
  RateLimited или Server. Возвращает новый счётчик и `NextAttemptAt`.
- После ошибки номер N локальный ceiling равен
  `min(BaseDelay * 2^(N-1), MaxDelay)`. Equal jitter выбирает наносекундную задержку
  от `ceil(ceiling/2)` до ceiling включительно. Caller передаёт свежий случайный
  uint64, например `math/rand/v2.Uint64()`; сам пакет не хранит PRNG или часы.
- Положительный `retry_after` у 429 — нижняя граница задержки, даже если он больше
  MaxDelay. Отсутствующий/неположительный параметр оставляет backoff. Значение,
  не помещающееся в time.Duration, возвращает ошибку без расписания; caller обязан
  сохранить исход и поднять явную операционную ошибку, а не немедленно отправлять.
- `MaxFailures` включает первую временную ошибку Telegram. Ошибка с этим номером
  даёт `Exhausted=true`, без даты следующей попытки. Уже исчерпанный счётчик
  сохраняется без переполнения. Caller прекращает автоматическую отправку и
  сообщает API delivery_blocked; слот остаётся занят по DEC-004.
- `WaitCondition(now, failures)` назначает проверку через отдельный положительный
  `ConditionInterval`. Счётчик не увеличивается и не сбрасывается; исчерпанный
  бюджет не возобновляется. Это фиксированный ограниченный интервал, без TTL
  подписки, jitter Telegram и зависимости от числа проверок условия.

Пример настройки для теста: BaseDelay=2s, MaxDelay=8s, MaxFailures=5,
ConditionInterval=3s. При entropy=0 ошибки 1–4 назначают задержки 1/2/4/4s,
ошибка 5 останавливает повторы. 429 с retry_after=90 назначает не раньше 90s.
Это пример, а не согласованные production defaults.

Политика только рассчитывает план: не спит, не берёт lease/лимитеры, не вызывает
HTTP/API и не меняет SQL. План и счётчик сохраняются caller один раз по attempt ID
вместе с исходом под fencing до освобождения lease. После рестарта читается уже
сохранённая дата, jitter заново не рассчитывается. Дубль intake не сбрасывает её.
Worker leases/схема и durable исходы подключаются в следующих тикетах.

**Наступивший срок не разрешает Send.** Каждому HTTP-повтору нужны оба лимитера,
новая команда допуска API с новым request ID и проверка текущей цены/канала,
затем немедленный Send. Старое разрешение повторно не используется.
Unknown/timeout, Forbidden/Rejected, NotSent, произвольная ошибка и nil не
планируются этой политикой; NTF-007/008 и worker определяют их обработку.
Повтор 5xx не даёт гарантии отсутствия внешнего дубля.

Проверка с fake clock/entropy и loopback HTTP 429/503:

```sh
GOTOOLCHAIN=local GOCACHE=/tmp/binance-go-build go test -race ./internal/notifications/retry -count=1
```

SQL/Kafka, отправка в Telegram и нагрузочные измерения для чистого расчёта не
требуются и этим тестом не заявляются.
