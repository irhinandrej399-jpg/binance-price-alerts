# Планировщик допуска чатов — NTF-005

`New(notificationsPool, botID, interval)` создаёт общий для реплик лимитер
по `(botID, chatID)`. Числовой bot ID стабилен при смене token, секрет не
сохраняется. Нулевой interval выбирает 1 с; положительный должен быть целым
числом микросекунд. Настройка одинакова у всех реплик. Различие с сохранённым
interval того же чата возвращает `ErrConfiguration`, запрещая отправку.

На 2 ноября 2026 [Telegram FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this)
рекомендует не превышать одно сообщение в секунду в отдельный чат. Здесь
используется приватный канал привязки приложения; отдельная политика групп
(20 сообщений/мин) этим default не реализуется. Настройка интервала не отменяет
ограничений Telegram, 429/retry_after обрабатываются отдельно.

`Next(ctx, chats) (index, wait, error)` принимает упорядоченный список chat ID
готовых кандидатов, выбирает первого доступного и возвращает исходный индекс.
Повторяющиеся chat ID в одном проходе проверяются один раз. Занятый или ожидающий
чат пропускается, поэтому 15 заданий одному чату не задерживают два других.
Если все ждут, возвращается `index == -1` и минимальная задержка до повторной
конкуренции; пустой список даёт `(-1, 0, nil)`. Нулевой chat ID запрещён,
отрицательные ID поддерживаются. Весь список валидируется до первого допуска.

Caller сохраняет задания и убирает из списка только выбранное. Порядок и
справедливое пополнение ограниченных пакетов принадлежат caller: бесконечный
приоритет первых кандидатов здесь не устраняется. Метод не хранит очередь,
не подтверждает задание и не удерживает его lease во время сна. При появлении
новой работы caller может перепроверить список раньше возвращённого wait.
Стоимость прохода линейна по числу различных чатов до выбранного кандидата;
нагрузочная производительность не измерена.

`TryAcquire(ctx, chatID) (wait, error)` проверяет один чат. Допуск — только
`wait == 0 && err == nil`, для Next дополнительно нужен `index >= 0`.
Положительный wait не резервирует будущую отправку. После ожидания с context
нужно снова конкурировать. Ошибка, включая неизвестный исход commit, запрещает
отправку. Неиспользованный допуск не возвращается.

Миграция `migrations/notifications/003_chat_limit.sql` хранит срок и interval
в собственной области notifications. `pg_try_advisory_xact_lock` по стабильному
ключу бота/чата исключает конкурирующую запись, включая INSERT первого допуска,
без ожидания другой реплики. Занятый ключ возвращает advisory wait 1 мс,
позволяя Next перейти к следующему чату. Возможная коллизия hash даёт лишний
повтор, но не лишний допуск. Все писатели обязаны соблюдать этот протокол;
оператор меняет interval при остановленных репликах, сохраняя next_allowed_at.
Обычный restart не удаляет строки.

После получения блокировки используются часы PostgreSQL `clock_timestamp()`.
Допуск сохраняет `next_allowed_at = now + interval` и возвращается после commit.
Простой не накапливает квоту; ход часов назад продлевает ожидание. Нет общего
mutex всех чатов. Истощение pool или недоступность БД могут задерживать все
вызовы; caller задаёт deadline.

В будущем worker должен соблюдать **оба** лимитера — `botlimit` и `chatlimit`.
Допуски используются сразу, не накапливаются. Если второй лимитер или API
отказал/потребовал ожидания, первый допуск теряется консервативно: после
ожидания проверяются оба заново. Перед Send нужен свежий API-допуск и его
актуальный chat; при смене адресата проверяется новый chat, старый допуск
не переносится. Нельзя хранить разрешение API во время ожидания лимитеров.
Точная частота HTTP-запросов зависит также от планировщика/сети и проверяется
при интеграции worker/runtime. Реальных Telegram-запросов здесь нет.

Проверка: `python3 scripts/check_postgres.py` — реальный disposable PostgreSQL
с race detector; fake clock, сценарий 15+1+1, два независимых pool/8 конкурентов,
restart, граница интервала, простой, изоляция ботов, несовпадение настроек,
отмена и удерживаемая блокировка первого чата. Без POSTGRES_TEST эти тесты
явно пропускаются.
