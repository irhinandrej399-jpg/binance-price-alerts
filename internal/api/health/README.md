# Health API

`health.New(apiPool.Ping, time.Second)` возвращает `http.Handler`:

| Маршрут | Успех | Отказ |
| --- | --- | --- |
| GET /healthz | 200, `{"status":"ok"}` | Не обращается к зависимостям |
| GET /readyz | 200, `{"status":"ready"}` | 503, `{"status":"not_ready"}` |

Оба маршрута поддерживают HEAD по правилам Go ServeMux. Ответы JSON с
`Cache-Control: no-store`; ошибки probe и credentials не попадают в ответ.
Неизвестный маршрут возвращает 404, неподдерживаемый метод — 405.

Начальное состояние — не инициализирован. Runtime вызывает
`SetInitialized(true)` после применения миграций отдельным runner и успешной
сборки обязательных компонентов API; `SetInitialized(false)` снимает готовность.
Состояние безопасно для конкурентных вызовов. Probe вызывается на каждом
readiness-запросе с отменой HTTP-запроса и отдельным timeout (по умолчанию 1 с).
Он обязан соблюдать context и поддерживать конкурентные вызовы.

Для локального профиля DEC-010 используется только pool собственной БД API.
Binance, Telegram, market-data и Kafka напрямую не проверяются: outbox хранит
принятую работу при недоступном брокере. Чужие таблицы не читаются.
Ошибка probe всегда даёт 503; восстановление БД возвращает готовность без
перезапуска. Liveness не вызывает probe даже при отказе БД.

Ping проверяет доступность БД, а не гарантирует будущую запись, свободное место
или квалификацию capacity ledger. Прикладные операции обязаны возвращать свои
ошибки записи/commit независимо от текущего readiness. Health не меняет их
результаты и не удаляет outbox. Квалификация дисковых квот отложена DEC-010.

Подключение в будущем runtime: смонтировать обработчик на `/healthz` и
`/readyz` вне Bearer middleware. В OPS-001 готов HTTP-компонент; `cmd/api`
пока остаётся каркасом. Запуск процесса и wiring всех прикладных компонентов
нужны отдельно перед E2E-002.

Проверки: `go test -race ./internal/api/health`; реальный PostgreSQL —
`python3 scripts/check_postgres.py` (disposable стенд, включая другие пакеты).
