# Привязка Telegram — IAM-008

`telegramlink.New(pool, nil).Consume(ctx, code, chatID)` фиксирует одну привязку
до возврата успеха. Пул принадлежит API; передаваемая БД должна поддерживать
самостоятельную READ COMMITTED транзакцию. Вход — код IAM-006 и положительный
int64 chat ID из проверенного приватного Telegram message. Владелец выбирается
по SHA-256 кода, а не по user_id из запроса.

Подключение HTTP-адаптера:

```go
next := telegramlink.Handler(telegramlink.New(pool, nil))
webhook, err := telegramwebhook.Handler(secret, next)
// Проверить err; зарегистрировать webhook на POST /v1/telegram/webhook.
```

Команда — `/start <code>` в обычном приватном чате; подходит ссылка
`https://t.me/<bot_username>?start=<code>`. Формат параметра и поля Update/Message
сверены 27 октября 2026 с [Telegram deep linking](https://core.telegram.org/bots/features#deep-linking)
и [Bot API](https://core.telegram.org/bots/api#message). Принимается только
`message.chat.type=private`, положительный chat.id и canonical base64url код
IAM-006 (43 символа/32 байта). Business messages, edited_message, другие типы
Update/чата и неизвестные команды игнорируются. Неизвестные JSON-поля допустимы;
лимит тела 64 KiB, повреждённый JSON/лишнее значение/превышение — 400.
Адаптер нужно ставить за защитой IAM-007; самостоятельно он секрет не проверяет.

Успех, повтор поглощённого кода, истечение, неизвестный код и занятый chat
подтверждаются пустым HTTP 200: это терминальные результаты для данного Update,
повторы Telegram их не изменят. Ошибка БД/отмена запроса — пустой 500 для повтора.
Ответ не содержит код, chat, SQL или персональные данные; Cache-Control no-store.
Отправка подтверждений пользователю через sendMessage здесь не выполняется.

Миграция `004_telegram_binding.sql` добавляет в `app.users` nullable
`telegram_chat_id` с UNIQUE и `telegram_version bigint NOT NULL DEFAULT 0`.
NULL/0 означает отсутствие первоначальной привязки; успешное поглощение нового
кода всегда увеличивает версию на 1, включая перепривязку на тот же chat.
Chat уникален среди аккаунтов; переноса с чужого аккаунта нет. Старый chat
освобождается при успешной смене. Версия не сбрасывается; переполнение приводит
к отказу и откату, а не к оборачиванию.

Транзакция сначала находит владельца по digest, блокирует его строку FOR UPDATE,
затем новым запросом проверяет **текущий** digest и строгую границу
`now < expires_at` и удаляет код. Время берётся после ожидания блокировки.
Обновление chat/версии и удаление кода фиксируются вместе. Конфликт UNIQUE
откатывает также удаление кода; его можно использовать с другим свободным chat.
Повтор старого кода не меняет версию. Блокировка общая с `telegramcode.Issue`;
порядок DEC-006 — user → code. Сырые ошибки скрыты за ErrStorage, UNIQUE chat —
ErrChatInUse, неизвестный/заменённый/поглощённый/истёкший код — ErrInvalidCode,
неположительный chat — ErrInvalidChat. Отмена context возвращается вызывающему.

Контракт будущим SUB-003 и SUB-017: создание подписки/допуск доставки в своей
транзакции **сначала** блокируют эту же строку `app.users FOR UPDATE`, затем
читают актуальные chat/version, после чего блокируют subscription/workflow.
Нельзя использовать предварительный снимок привязки. При фиксации допуска
сохраняются chat/version этой попытки. Если допуск фиксируется раньше смены,
разрешено сообщение в полёте на прежний chat (DEC-005). Хранилища подписок и
допуска пока отсутствуют; этот тикет даёт им точку сериализации, а не их реализацию.
Автовозобновление blocked — SUB-018/NTF-015, без события перепривязки.

Проверка: `go test ./internal/api/telegramlink`; реальные транзакции, гонки,
защищённый HTTP flow и race detector — `python3 scripts/check_postgres.py`.
Тесты принудительно удерживают owner lock и проверяют замену/истечение во время
ожидания. Runtime cmd/api и реальный Telegram ещё не подключены; рабочая БД
миграцией этой сессии не изменялась. Rate limits — отдельные задачи OPS.
