# Учётные записи API — IAM-001

Миграция `migrations/api/001_users.sql` создаёт только в БД API обычную
WAL-logged таблицу `app.users`: UUID `id` (генерируется PostgreSQL), уникальный
NOT NULL `email` и NOT NULL `password_hash`. Прикладной код подключается как
`api_runtime`; DDL выполняет отдельная команда `scripts/migrate.py --owner api`.
Другие владельцы эту миграцию не применяют.

`account.New(pool)` принимает также выделенное соединение или `pgx.Tx`:

- `Create(ctx, email, passwordHash)` сохраняет аккаунт и возвращает его ID,
  нормализованный email и прежний хеш. Успех с пулом означает commit отдельного
  INSERT; при передаче транзакции commit/rollback остаётся обязанностью вызывающего.
- `ByEmail(ctx, email)` читает внутреннюю запись с хешем для будущего входа.
- `NormalizeEmail` удаляет внешние пробельные символы (`strings.TrimSpace`) и
  приводит весь адрес к нижнему регистру (`strings.ToLower`). Точки и `+suffix`
  сохраняются, provider-specific rewriting и IDNA-преобразование не выполняются.
  Полная проверка формата входного email относится к IAM-003. Ограничение БД
  запрещает пустой email, пробельные символы и ненормализованный регистр.
- `ErrEmailExists`, `ErrNotFound`, `ErrInvalidInput` — стабильные ошибки.
  Прочие ошибки БД возвращаются как `ErrStorage`, без SQL Detail с данными
  аккаунта; при отменённом context возвращается его ошибка. После ошибки SQL
  внутри явной транзакции вызывающий выполняет rollback.

`passwordHash` — уже вычисленное кодированное значение из [адаптера IAM-002](../password/README.md)
(`password.Hash`). Репозиторий сохраняет его без изменения; алгоритм/соль здесь не
выбираются. Непустая строка сама по себе не доказывает, что это хеш: вызывающий
обязан передать результат password adapter, а не пользовательский пароль.
Поля для открытого пароля нет. `Account` — внутренние credentials, их нельзя
логировать, сериализовать в HTTP-ответ или включать в событие. IAM-003 должен
сформировать отдельный публичный ответ без `PasswordHash`.

Строка `app.users` — канонический первый lock из DEC-006. Будущие транзакции
квоты и Telegram-привязки должны использовать **одну и ту же** строку:
`SELECT id FROM app.users WHERE id=$1 FOR UPDATE`, затем подписка → workflow →
счётчик журнала. Колонки квоты/привязки и их операции добавят соответствующие
тикеты; наличие строки само по себе ещё не реализует лимит или привязку.
Сетевых вызовов под этим lock быть не должно.

Проверка: `python3 scripts/check_postgres.py`. Два удерживаемых соединения
выполняют вставки одного нормализованного email: первая транзакция ещё не
зафиксирована, вторая действительно ждёт PostgreSQL lock (проверяется через
`pg_stat_activity`), после commit выигрывает ровно одна запись. Проверяются
чтение до/после commit, сохранность хеша, ошибки и ограничения прямого SQL.
Тест использует искусственный предвычисленный хеш, не проверяет IAM-002.
