# Каноническая подписка, квота и HTTP API (SUB-001/002/003/004/005/011)

Миграция `migrations/api/005_subscriptions.sql`; пакет `internal/api/subscription`.
`New(db)` принимает pool, connection или `pgx.Tx` через готовый `account.DB`.
`Insert(ctx, Record)` сохраняет полный after-image с заданным устойчивым UUID;
`ByID(ctx, ownerID, id)` читает только запись указанного владельца. Внешний слой
берёт ownerID из доверенного контекста аутентификации. Чужая и отсутствующая
подписка дают одинаковый `ErrNotFound`. Прямой доступ matcher к API-БД запрещён.

Пара, направление и состояния используют существующие доменные значения.
Порог и цена создания — `price.Price`, PostgreSQL `numeric` без typmod с проверкой
диапазона 18/18: лишняя точность отклоняется, не округляется. Процент — необязательный
знаковый десятичный текст; фиксированный порог вычисляет application-слой через
`price.NewPercentageThreshold` до записи. Согласованность процента, порога и
направления остаётся обязанностью этого слоя. Для конкретной цены процент — nil.
Время сделки хранится в `timestamptz` с точностью PostgreSQL до микросекунд;
на входе следует использовать время Binance с милли-/микросекундами, при чтении
возвращается UTC. Возраст при будущем ответе вычисляется заново по времени сделки;
`Stale`, `StreamUnconfirmed`, `GapDetected` сохраняют предупреждения создания.

Версии подписки/workflow — положительные `int64` (до 9223372036854775807), версия
неудачной привязки — неотрицательная. `Activation = latest_price` соответствует
CON-002/DEC-004: отдельная историческая ценовая граница для replay не используется.
Это политика подключения к последней цене, не journal C и не ревизия котировки.
Исходный снимок не является TTL и не разрешает отправку.

Все шесть состояний DOM-004 сохраняются без преобразования; workflow ID и версия
не теряются у active/blocked/terminal. Pending_delivery, sending и delivered
требуют workflow; blocked сохраняет причину и версию канала. PK не позволяет
повторить ID подписки, UNIQUE(workflow_id) — разделить один workflow между двумя
подписками. Миграция 005 хранит ссылку на workflow; его создание и outbox
добавлены в SUB-013, история разрешений — в SUB-017, исходы — отдельный SUB-019.
SQL-ограничения проверяют
форму записи, не разрешённость перехода DOM-004.

`Insert` — примитив для композиции, не готовая операция создания подписки.
Публичного wiring нет. При записи через транзакцию успешный Insert ещё не означает
commit. Application-операция должна атомарно объединить блокировку пользователя,
Telegram-политику, лимит (SUB-002), подписку и журнал/outbox (SUB-021/011), соблюдая
порядок DEC-006. Сам Insert не меняет счётчик квоты; для создания используйте OwnerQuota ниже. Сам Insert событий не создаёт. Универсального
upsert нет: он мог бы затереть новую версию или возродить terminal-подписку.

Ошибки: `ErrExists` для конфликта идентичности, `ErrInvalidInput` для нарушений
схемы/UUID, `ErrStorage` для прочих сбоев; отмена/deadline возвращаются из context.
Сырые ошибки PostgreSQL с пользовательскими значениями наружу не выдаются.
Ошибка SQL внутри `pgx.Tx` требует rollback всей операции или savepoint вызывающего.

Проверка с реальным PostgreSQL и race detector:

```sh
GOCACHE=/tmp/binance-go-build python3 scripts/check_postgres.py
```

Runner применяет миграции к disposable проекту и удаляет его volume. Обычный
`go test` пропускает PostgreSQL-тесты без opt-in и не подтверждает round-trip БД.

## Транзакционная квота (SUB-002)

Миграция `006_subscription_quota.sql` добавляет `users.active_subscriptions`
с CHECK 0..15 и внутренний `subscriptions.quota_reserved`: durable-признак
занятого слота для однократного освобождения. Она инициализирует оба поля по
существующим незавершённым записям; при превышении 15 миграция откатывается,
данные не удаляются. Применять при остановленных писателях API.

Порядок композиции (HTTP SUB-003 следует ему; runtime пока отсутствует):

1. Получить/проверить котировку и вычислить порог вне транзакции.
2. Начать `pgx.ReadCommitted`, установить `defer tx.Rollback(...)`.
3. `q, err := subscription.LockQuota(ctx, tx, authenticatedOwnerID)` блокирует
   общую с Telegram-операциями строку пользователя; чужой ID брать из запроса нельзя.
4. `q.Create(ctx, record)` перепроверяет текущую Telegram-привязку и счётчик,
   увеличивает его, сохраняет начальный `active` с версией 1 и отмечает слот.
   OwnerID должен совпадать с заблокированным владельцем, workflow/blocked отсутствуют.
5. Добавить остальные обязательные записи в той же транзакции и выполнить commit.
   До commit успешного ответа нет. **При любой ошибке откатывать всю транзакцию.**

`ErrTelegramNotLinked` и `ErrQuotaExceeded` не расходуют слот и не создают подписку.
Остальные ошибки используют общую безопасную классификацию; неизвестный владелец —
`ErrNotFound`. Автоматических повторов нет, SQL-конфликт требует отката; политику
повтора со стабильным ID команды реализует вызывающая операция. HTTP-создание
добавляет журнал/outbox перед commit; операция описана ниже.

Освобождение: сначала `LockQuota`, затем блокировка подписки, проверка доменного
перехода/версии/workflow/attempt и сохранение after-image; после этого
`q.ReleaseTerminal(ctx, id)` в **той же транзакции**. Метод освобождает отмеченный
слот только для `delivered`/`cancelled`; повтор ничего не уменьшает. Active,
pending_delivery, sending и delivery_blocked сохраняют слот, включая возврат к
ожиданию. Чужая/отсутствующая подписка — `ErrNotFound`. Этот метод не разрешает
переход и не заменяет будущие отмену/фиксацию исхода, fencing, audit и outbox.

Все писатели обязаны соблюдать порядок user → subscription → workflow/attempt →
journal. У разных владельцев разные user locks. Блокировка удерживается до конца
транзакции, сетевого I/O под ней нет. `Insert` остаётся низкоуровневым примитивом:
его прямой вызов, произвольный UPDATE/DELETE или ручная смена счётчика обходят
протокол квоты. Для пользовательского создания разрешён только `OwnerQuota.Create`;
terminal-сохранение обязано вызывать `ReleaseTerminal` до commit. Runtime пока
не подключён, триггеров и универсального upsert нет.

## HTTP-создание (SUB-003)

`NewHandler(apiPool, catalogrpc.NewClient(conn), latest.NewClient(conn), time.Now)`
обслуживает `POST /v1/subscriptions`. Обернуть в `auth.New(sessionStore, handler)`;
без доверенного `auth.UserID` сам обработчик также возвращает 401. Соединение с
market-data создаётся будущим runtime с serviceauth credentials; оба Go-клиента
ограничивают каждый RPC одной секундой и передают отмену. API не читает чужую БД
и не обращается к Binance. В `cmd/api` операция пока не подключена.

Тело — `application/json`, один объект одной из форм (точные числа — строки):

```json
{"pair":"BTCUSDT","price":"105","direction":"up"}
```

```json
{"pair":"BTCUSDT","percent":"+5"}
```

Для конкретной цены направление обязательно: up/down. Для процента направление
вычисляется из знака; цена и percent взаимоисключающие. Неизвестные поля, включая
user_id, отклоняются; query/header user_id не задают владельца. Pair сверяется с
точным symbol успешного полного каталога, без повторной фильтрации Binance.

Успех — 201 после commit, например:

```json
{"id":"00000000-0000-4000-8000-000000000001","pair":"BTCUSDT","state":"active","threshold":"105","direction":"up","percent":"+5","creation_price":"100","creation_trade_time":"2026-10-28T12:00:00Z","age":{"seconds":6,"nanos":0},"warnings":["stale"]}
```

Для цены поле percent отсутствует. Age вычисляется по времени сделки при
использовании снимка под user lock (не по готовому возрасту RPC), представляется
секундами/наносекундами без насыщения time.Duration. Предупреждения возвращаются
в порядке `stale`, `stream_unconfirmed`, `gap_detected`; без них — пустой массив.
Возраст ровно 5 с не вызывает stale, любой больший вызывает. Gap и unconfirmed
не зависят от возраста. Исходные цена/время и предупреждения создания сохраняются;
в будущих чтениях возраст и предупреждения следует вычислять заново.

Котировка проверяется и процент вычисляется до транзакции. После user lock время
повторно проверяется, возраст актуализируется. Внутри транзакции нет сетевого I/O:
LockQuota → Create → чтение сохранённого after-image → journal.Append → commit.
Даже истинное исходное условие сохраняет active/version=1,
latest_price и занятый слот, без workflow. Порог процента фиксирован навсегда.
Тест конкурентного изменения канала наблюдает реальное ожидание user lock и
проверяет текущую привязку после commit изменения; проверка квоты не обходится.

| Ошибка | HTTP / error.code |
| --- | --- |
| Нет сессии | 401 invalid_session |
| Неверный Content-Type | 415 unsupported_media_type |
| Неверная форма/число/направление/процент | 400 invalid_request |
| Пары нет в успешном каталоге | 400 unknown_pair |
| Ошибка чтения каталога | 503 catalog_unavailable |
| Нет допустимой цены/времени или RPC недоступен | 503 quote_unavailable |
| Нет актуальной Telegram-привязки | 409 telegram_not_linked |
| Уже заняты 15 слотов | 409 quota_exceeded |
| Ошибка транзакции/commit | 500 internal_error |

Ошибки не содержат исходных сообщений БД/RPC. При ошибке до commit транзакция
откатывается; 201 выдаётся только после успешного commit. Потеря ответа после
commit оставляет неопределённость для клиента: идемпотентных повторов HTTP здесь
нет, автоматически повторять создание нельзя. Journal/outbox создания подключён
в SUB-011; этот endpoint ещё не даёт работающего конвейера matcher/доставки.
Точность времени БД — микросекунды; Binance-времена в готовом контракте используют
милли-/микросекунды. Runtime, общий лимит размера тела и admission control — будущие задачи.

Проверки HTTP, сохранения и квоты выполняются общим `scripts/check_postgres.py`:
реальные сессии и PostgreSQL, управляемые источники каталога/котировки, race detector.
Отказ commit проверяется обёрткой над реальной транзакцией: вставка/резервирование
выполняются, commit возвращает ошибку, defer rollback удаляет оба изменения.
Без opt-in эти интеграционные тесты пропускаются; обычная компиляция не заменяет их.

## Журнал создания (SUB-011)

После Create обработчик читает сохранённую запись в той же транзакции и передаёт
один SubscriptionChanged в готовый `journal.Append`. Поля события соответствуют
CON-002: active/version=1, пара, точный порог, направление, latest_price,
исходная цена/время, без workflow. Сохранённое время читается из PostgreSQL,
чтобы событие совпадало с канонической записью при микросекундной точности БД.
Процент и предупреждения остаются в канонической записи по существующему контракту;
в событии CON-002 передаётся вычисленный порог и снимок создания.

UUID события выделяется один раз до транзакции, независимо от ID подписки;
корневая correlation_id равна event_id, ordering_key — ID подписки,
occurred_at — времени проверки снимка под user lock. Append сохраняет весь
конверт и назначает position=transaction_end=C. Повторное чтение/будущий relay
обязаны использовать сохранённые байты и event_id. HTTP-идемпотентность и
автоматические повторы не добавлены.

Все бизнес-блокировки, записи и чтение after-image заканчиваются до Append;
после него — только commit/rollback, без сетевого I/O и новых бизнес-блокировок.
При ошибке записи события или commit ответ — 500 internal_error без деталей;
rollback откатывает подписку, слот, C и пакет журнала. Успех 201 — после commit.
Проверки: точный after-image цены/процента, устойчивые байты и ID, принудительная
SQL-ошибка вставки события после резервирования и ошибка commit. Общий runner
запускает пакеты последовательно (`-p=1`): тесты journal проверяют глобальный C,
а HTTP-тесты теперь записывают тот же журнал. Relay/storage, читающие всю
market-data очередь, запускаются до оставляющих записи Latest fixtures.
Внутрипакетная конкурентность квоты и журнала сохраняется. Отмена также пишет журнал (SUB-012); relay — SUB-007.

## HTTP-список (SUB-004)

`NewListHandler(apiPool)` обслуживает `GET /v1/subscriptions`. Подключать под
`auth.New(sessionStore, handler)` рядом с POST-обработчиком на родительском router:

```go
mux.Handle("POST /v1/subscriptions", subscription.NewHandler(pool, catalogs, quotes, time.Now))
mux.Handle("GET /v1/subscriptions", subscription.NewListHandler(pool))
protected := auth.New(session.New(pool, nil), mux)
```

Владелец берётся только из `auth.UserID`, query/header/body user_id не влияет на
выборку. Без доверенного владельца — 401 invalid_session; отказ чтения — 500
internal_error без деталей БД и без частичного списка. Успех — 200, application/json,
Cache-Control: no-store. Пустой результат: `{"subscriptions":[]}`.

В список входят `active`, `pending_delivery`, `sending`, `delivery_blocked`,
включая active с сохранённым workflow. `delivered`/`cancelled` исключены.
Один SQL-запрос возвращает согласованный снимок на момент чтения, ORDER BY id ASC,
LIMIT 15; порядок по UUID, не по времени создания. Используется существующий индекс
(owner_id,id). Каноническое состояние определяет включение, внутренний
quota_reserved не используется как фильтр. Квоту писателей обеспечивает SUB-002;
LIMIT ограничивает ответ даже при ошибочных данных сверх квоты.

Пример элемента:

```json
{"subscriptions":[{"id":"00000000-0000-4000-8000-000000000001","pair":"BTCUSDT","threshold":"105","direction":"up","percent":"+5","state":"delivery_blocked","version":3,"workflow":{"trigger_id":"trigger-1","version":2},"blocked":{"reason":"channel_unavailable","binding_version":4}}]}
```

Точные цены и процент — строки, версии — положительные int64. Необязательные
percent/workflow/blocked отсутствуют, если их нет в сохранённой записи. Причины
blocked соответствуют каноническому DOM-004/схеме: `channel_unavailable` (проблема
Telegram-канала, включая отсутствие привязки), `attempts_exhausted`, `permanent_failure`.
Чтение не проверяет канал/котировки и не выполняет восстановление: оно показывает
фактическое сохранённое состояние. После будущего восстановления та же подписка
появляется с новой версией/состоянием, прежними ID, workflow, порогом и процентом,
без старого blocked. Протокол восстановления — SUB-018/019 и NTF-015.

Возраст/предупреждения текущей цены этот endpoint не возвращает: исходный снимок
не выдаётся за текущую котировку. История и пагинация отсутствуют. Схема БД не меняется,
`cmd/api` ещё не подключён. Интеграционные HTTP-тесты используют реальные сессии/БД,
два владельца, все состояния, лимит 15, fixture восстановления и отказ чтения в
начале/после получения строк; запуск — `scripts/check_postgres.py` с race detector.

## HTTP-отмена (SUB-005)

`NewCancelHandler(apiPool)` обслуживает `DELETE /v1/subscriptions/{id}` под
`auth.New`. Тело не требуется; query/header/body user_id не задают владельца.
Родительский router подключает `DELETE /v1/subscriptions/{id}` рядом с GET/POST.
Ответ после commit — 200, JSON и Cache-Control: no-store, например:

```json
{"id":"00000000-0000-4000-8000-000000000001","state":"cancelled","version":4,"message_may_be_in_flight":true}
```

Одна READ COMMITTED транзакция: LockQuota (user) → SELECT собственной подписки
FOR UPDATE → UPDATE с проверкой owner, прочитанных version/state → ReleaseTerminal
→ чтение after-image → journal.Append → commit. Первая отмена любого незавершённого состояния увеличивает версию на 1,
снимает blocked и освобождает слот. Порог, процент, исходный снимок и workflow
сохраняются. Cancelled и delivered остаются в прежнем состоянии/версии; повторы
и конкурентные отмены не уменьшают квоту второй раз. Delivered возвращается
как delivered: состоявшуюся доставку отменить нельзя. Наличие Telegram не требуется.
Версию HTTP-клиент не передаёт: повтор отменяет текущее незавершённое состояние;
проверка версии выполняется сервером в SQL под блокировкой. MaxInt64 при первом
переходе даёт 500 с rollback, без переполнения и освобождения слота.

`message_may_be_in_flight` — консервативное предупреждение, не статус попытки:
true при наличии workflow у любой недоставленной подписки, включая cancelled.
Без истории попыток нельзя исключить уже допущенный неоднозначный запрос даже
после возврата к active/pending/blocked. True допустим и у workflow, который ещё
не имел допуска. False — workflow отсутствует либо подписка уже delivered.
Сохранение workflow делает предупреждение стабильным при повторе и рестарте.
Отмена не отзывает разрешённый внешний HTTP-запрос.

Нет сессии — 401 invalid_session; некорректный UUID — 400 invalid_request;
чужой/отсутствующий ID — одинаковый 404 subscription_not_found; ошибка БД/commit —
500 internal_error без исходных деталей. До успешного commit ответа 200 нет;
ошибки откатывают состояние, версию, слот, C и журнал одной транзакцией.

Будущие admission/result writers обязаны соблюдать тот же порядок блокировок,
проверять terminal/version перед допуском и сохранять поздний успех cancelled
только в аудите, без нового освобождения слота. Сам допуск/история попыток —
SUB-017/019/020. Journal/outbox отмены подключён в SUB-012 через SUB-021.
Текущий адаптер фиксирует canonical отмену; запрет отправки во всём конвейере
потребует подключения этих операций и runtime. Схема БД не меняется.

Проверка — `scripts/check_postgres.py`: реальные сессии/PostgreSQL, все состояния,
чужой/отсутствующий ID, повтор, 20 конкурентных отмен, rollback при отказе commit,
позднее освобождение, переполнение версии, отмена без Telegram и ожидание
конкурирующего изменения версии/допуска под user lock. Runtime cmd/api
по-прежнему не подключён; нагрузка и реальные Telegram-запросы не проверялись.

### Журнал отмены (SUB-012)

Только первый переход в cancelled вызывает один journal.Append после всех
бизнес-блокировок, освобождения слота и чтения сохранённого after-image.
Событие CON-002 содержит terminal-состояние, новую версию подписки, прежние
порог/снимок создания и workflow с его собственной неизменённой версией.
Повторы cancelled/delivered не создают события и не выделяют новый C.
UUID события назначается один раз до транзакции, correlation_id равна event_id,
ordering_key — ID подписки, occurred_at — время формирования события после
перехода под блокировками. После Append — только commit/rollback. Будущий relay
использует сохранённые байты/ID; автоматических повторов транзакции здесь нет.

Проверки на реальном PostgreSQL: after-image всех незавершённых состояний,
workflow, неизменные байты и replay, отсутствие нового события при terminal-повторе,
20 конкурентных отмен с одним событием/версией, SQL-ошибка INSERT журнала после
освобождения слота и отказ commit. Ошибки откатывают и переход, и слот, и пакет/C;
после неудачной записи последующий HTTP-повтор выполняет единственный переход.
Публикация событий и runtime остаются отдельными задачами.

## Атомарный запрос работы доставки (SUB-013)

`RequestDelivery(ctx, Beginner, DeliveryCandidate) (Record, error)` открывает
READ COMMITTED транзакцию и получает блокировки пользователя, затем подписки.
Вход — owner/subscription ID, ожидаемая положительная версия и корректная
`priceobserved.Observed` от доверенного application-слоя. SUB-014 должен сам
прочитать последнюю цену до вызова; пользовательская цена недопустима.
Вызовов сети под SQL-блокировками нет. Старая корректная цена, unconfirmed и gap
не запрещают запрос работы: цена здесь диагностическая, каждую отправку позднее
разрешает отдельный допуск API по новой проверке.

Если workflow отсутствует, разрешены только `active`, точная версия и истинный
канонический `price.Satisfied` для совпадающей пары. Равенство включено для обоих
направлений. Операция сохраняет `pending_delivery`, version+1, случайный UUID
trigger_id и workflow version=1, не меняя квоту. Затем пишет один неизменяемый
AlertTriggered в `app.delivery_outbox` и полный SubscriptionChanged через
`journal.Append`, последним получает блокировку C и выполняет commit.
Миграция `009_delivery_outbox.sql` задаёт уникальность subscription_id, trigger_id
и event_id, хранит точные wire-байты и разрешает runtime только SELECT/INSERT.
Ссылка на подписку логическая: удаление canonical-строки не удаляет retained work
каскадно, как и в журнале; целостность записи обеспечивает общая транзакция.
Публикация и её cursor/lease — SUB-009; миграция не реализует relay.

Повтор возвращает текущий Record с прежним workflow, даже если исходная версия
уже изменилась. Он не создаёт новое событие и не меняет active/sending/blocked
или terminal-состояние. Это восстановление идентичности, а не допуск отправки.
Без workflow неверная версия/ложное условие/запрещённое состояние возвращают
Record и `ErrCandidateRejected`; чужая/отсутствующая запись — `ErrNotFound`;
невалидный вход, несовпадение пары или переполнение версии — `ErrInvalidInput`.
Ошибки SQL скрывают данные БД, отмена context сохраняется. Любая ошибка записи
или commit откатывает переход, outbox и C; потеря подтверждения уже выполненного
commit требует повтора по подписке и восстановления прежнего workflow.
Отмена, получившая пользовательскую блокировку первой, запрещает новую работу.
`Record.Workflow` хранит устойчивый workflow; attempt/lease добавлены в SUB-017,
фиксация результата — отдельный SUB-019. Runtime cmd/api этим результатом не подключён.

Проверка: `GOCACHE=/tmp/binance-sub013-build python3 scripts/check_postgres.py`.
Интеграционные тесты `delivery_test.go` проверяют конкуренцию, лимит, точные
сохранённые события, повтор, блокировки отмены и rollback на реальном PostgreSQL.

Защищённый unary-запрос работы доставки и чтение последней цены доступны через
[deliveryrpc (SUB-014)](../deliveryrpc/README.md). Он вызывает эту атомарную
операцию; подключение runtime и публикация outbox остаются отдельными задачами.


## Допуск одной попытки (SUB-017)

`AdmitDelivery(ctx, Beginner, AdmissionCommand) (AdmissionResult, error)` — storage
операция без сетевых вызовов. Доверенный application-слой передаёт owner/subscription,
workflow ID, уникальный request ID, последнюю проверенную `priceobserved.Observed`
и настроенный TTL разрешения. Сетевой интерфейс/чтение цены — SUB-018. TTL задаётся
сервисом в диапазоне от 1 мкс до 1 минуты, с точностью до микросекунды. PostgreSQL
вычисляет deadline по `clock_timestamp()` после получения бизнес-блокировок;
ожидание журнала/commit может израсходовать срок ещё до ответа. Отправлять по
истёкшему разрешению нельзя; новая проверка требует нового request ID.

Миграция `010_delivery_admission.sql` добавляет `admission_fence` и
`current_attempt_id` в каноническую подписку и неизменяемую таблицу
`delivery_admissions`. Она хранит точные JSON-байты ответа команды, включая
котировку только разрешённой попытки, её chat/version, attempt ID, fencing token
и deadline. Runtime имеет только SELECT/INSERT; удаления canonical-строки не
каскадируют в историю. Очистка и ограничения объёма — отдельная работа.

Порядок блокировок: пользователь/привязка → подписка → чтение команд/попытки →
журнал. Писатели привязки и отмены используют тот же user lock. Текущая
действующая попытка даёт `attempt_busy` без второго разрешения, даже после
смены/исчезновения канала. После её истечения новая команда заново проверяет
канал и канонический предикат по переданной цене:

- true → `sending`, `admitted`, новый attempt UUID и монотонный fence;
- false → `active`, `wait_condition`, без разрешения;
- нет привязки → `delivery_blocked`, `blocked`, причина `channel_unavailable`
  и текущая версия канала; отдельная цена блокировки не сохраняется;
- blocked по каналу восстанавливается только при существующей привязке со
  строго большей версией; другая причина остаётся blocked;
- cancelled/delivered → `terminal`, без новых разрешений.

Порог, процент, исходная цена/время, workflow и занятый слот сохраняются при
ожидании/блокировке/восстановлении. Каждое новое разрешение, включая замену
истёкшего в sending, увеличивает версию подписки. Изменение состояния и полный
SubscriptionChanged/C через SUB-021 сохраняются одной транзакцией с ответом
команды. Для busy/terminal/неизменившегося blocked или active новый C не выделяется.
Ошибка команды/журнала/commit откатывает всё, включая pointer/fence; неоднозначный
commit восстанавливается повтором той же команды.

Повтор `(subscription_id, request_id)` возвращает **исторический ответ**, даже
после отмены, смены привязки или истечения срока. Он не обновляет состояние,
адресата, котировку или deadline. При восстановлении достаточно идентичности
команды: цена/TTL повторно не требуются. Каждый следующий цикл проверки использует
новый request ID. Ни replay, ни новое разрешение не дают права повторить уже
выполненный HTTP-вызов: один permit — один непосредственный вызов после лимитеров.
Истёкшая попытка может оставаться внешне неоднозначной; риск дубля принят DEC-004.

`ErrNotFound` одинаков для чужой/отсутствующей подписки; чужой/отсутствующий workflow —
`ErrAdmissionRejected`; неверная котировка/пара/TTL, request ID и переполнение —
`ErrInvalidInput`. Детали SQL скрываются, context cancellation сохраняется.

Контракт для SUB-019: под теми же user/subscription locks находить известную
попытку в `delivery_admissions`. Отрицательный результат может менять каноническую
работу только при совпадении `current_attempt_id` и `admission_fence`, с учётом
terminal и версии привязки; по завершении текущей попытки pointer очищается.
Возврат в active/blocked при новом допуске также очищает pointer. Старый replay
не может восстановить прежний pointer/token. Достоверный поздний успех известной
попытки обрабатывается по DEC-004, включая аудит после отмены; истечение permit
само по себе не отвергает такой успех. Сохранение исходов реализуется в SUB-019.

Проверка: `GOCACHE=/tmp/binance-sub017-build GOMODCACHE=/tmp/binance-go-mod python3 scripts/check_postgres.py`.
`admission_test.go` проверяет реальные SQL-транзакции: одинаковые и разные
конкурентные request ID, истечение/новый fence/старый replay, true/false и
восстановление канала, terminal/другие блокировки, общие locks с настоящей
отменой и поглощением Telegram-кода, rollback INSERT/журнала/commit и потерю
commit-ответа. Runtime и отправка Telegram остаются отдельными задачами.

### Подготовка сетевого допуска — SUB-018

`PrepareAdmission(ctx, db, command)` использует тот же порядок locks и восстановление
ответа, что `AdmitDelivery`. Без цены может сохранить только terminal/busy/blocked.
Если новая цена нужна, возвращает `*AdmissionQuoteRequired{Record, BindingVersion}`
без записей, освобождая транзакцию до сетевого I/O. Сетевой адаптер передаёт
эту версию в `AdmissionCommand.ExpectedBindingVersion`; изменение версии до
допуска возвращает `ErrAdmissionChanged` без записи команды. Нужно повторить
подготовку и чтение последней цены с прежним request ID в пределах deadline.
Сохранённый ответ имеет приоритет над этой проверкой. Старые прямые вызовы
`AdmitDelivery` без подготовки сохраняют контракт SUB-017.

Сетевой интерфейс и правила использования: [admissionrpc](../admissionrpc/README.md).
