# Допуск попытки доставки — SUB-018

`proto/api/v1/admission.proto`: unary `/api.v1.Admission/AdmitDelivery`.
`NewPostgres(pool)` компонует готовую атомарную операцию SUB-017;
`NewServer(store, latest.NewClient(marketConn), permitTTL, clock)` проверяет TTL
конфигурации (от 1 мкс до 1 минуты, с точностью мкс). Runtime выбирает TTL,
сертификаты, URI сервисов и адреса. Бюджет клиента и сервера — 3 с, включая
подготовку, чтение market-data с его пределом 1 с, повторы привязки и commit.
Это начальный лимит операции, не измеренный SLA.

Устанавливать все `ServerOptions` вместе с регистрацией сервиса. Они дают доступ
только точному доверенному URI notifications по mTLS. Matcher/API и публичный
Bearer не разрешают этот RPC. Если runtime объединит несколько API RPC на одном
gRPC-сервере, он должен собрать единую политику разрешённых методов; отдельные
наборы unary interceptor нельзя независимо накладывать друг на друга.

Запрос содержит owner/subscription/workflow/request ID. Только API читает свои
таблицы и проверяет соответствие workflow; сервисные credentials не заменяют
эту проверку. В запросе нет котировки события, chat, TTL или порога.

1. `PrepareAdmission` под user/subscription locks восстанавливает сохранённый
   ответ или сохраняет terminal/busy/blocked без чтения market-data. Новая цена
   нужна только при доступном канале и возможности новой попытки. Подготовка,
   требующая цены, возвращает каноническую запись и версию канала без изменений.
2. После завершения транзакции API читает MKT-006. Проверяются пара, точная цена,
   ревизия, времена и пригодность ответа; stale/unconfirmed/gap не запрещают
   отправку. Возраст вычисляется по исходному времени сделки, не времени чтения.
3. `AdmitDelivery` повторно проверяет состояние, workflow, текущую попытку и
   привязку. Изменившаяся версия канала требует новой подготовки и новой цены
   в пределах того же deadline/request ID. Отмена до допуска запрещает попытку.
   Сетевого I/O под SQL locks нет.

Доменные ответы: `admitted`, `wait_condition`, `attempt_busy`, `terminal`,
`blocked`. `admitted` содержит attempt ID/fence, неизменяемый deadline,
актуальные chat/версию канала и полную проверенную котировку с исходными
временами и диагностикой потока. `blocked` содержит причину и версию блокировки.
`attempt_busy` означает, что другая попытка ещё действует; отправка не разрешена.

NotFound одинаков для отсутствующего/чужого owner/subscription; несоответствие
workflow — FailedPrecondition; неправильная форма запроса — InvalidArgument.
Ошибки SQL/цены — Unavailable, отмена/deadline сохраняют gRPC-код. Ни ошибка
чтения привязки, ни недоступная цена не считаются отсутствием канала и не теряют
работу. При недоступной цене ответ команды не сохраняется: тот же ID допускает
повторную проверку после восстановления зависимости.

`NewClient(conn)` использует принадлежащее вызывающему mTLS-соединение и не
добавляет автоматических повторов. При timeout/неопределённом commit повторять
**тот же request ID**: ответ сохраняется транзакционно и восстанавливается без
цены, включая после expiry/отмены/перепривязки. Replay — исторический ответ:
он не продлевает срок, не выдаёт новую попытку и не разрешает повтор уже
выполненного HTTP-вызова. Каждый новый цикл проверки требует нового request ID.
Один permit — один непосредственный вызов Telegram после лимитеров до expires_at.

Проверки: `go test -race ./internal/api/admissionrpc ./internal/api/deliveryrpc`
(нужен loopback); `python3 scripts/check_postgres.py` — реальный disposable
PostgreSQL, обе mTLS-связи API/market-data, гонки и потеря ответа после commit.
Сохранение исходов готово в SUB-019, защищённый RPC —
[SUB-020](../resultrpc/README.md). Runtime, Telegram worker и лимитеры — отдельно.
