# Relay журнала подписок — SUB-007

`New(pool, kafka.Config, topic)` создаёт relay одной фиксированной очереди API.
`Step(ctx)` пытается отправить один **целый** SQL-пакет; `Run(ctx, observe)`
опрашивает очередь до отмены, с паузой 250 мс и backoff до 5 с при ошибках.
Наблюдатель синхронный и должен быстро возвращаться. Runtime подключается отдельно.

Все реплики одной среды обязаны использовать один стабильный transactional.id,
например `local-api-subscription-relay-0`, и её `subscription-changes` topic с
**одной партицией** по SET-005. ID не содержит PID/случайного суффикса.
`ErrFenced` или `ErrLeaseLost` завершают Run: старый владелец не перехватывает producer обратно.
После такого результата Step вызывающий тоже обязан остановить владельца.

Миграция `008_subscription_relay.sql` создаёт отдельную singleton-строку:
последний опубликованный C (исходно 0), монотонный token и `lease_until`.
Атомарный UPDATE забирает свободную/истёкшую lease на 30 с по часам PostgreSQL;
одна Step ограничена 5 с, включая SQL, инициализацию producer и Kafka commit.
Сетевых вызовов внутри SQL-транзакций или под блокировками строк нет.

Шаг читает следующий полный пакет после cursor, проверяет непрерывность C,
границы пакета и соответствие сохранённого конверта SQL-столбцам. Один пакет —
одна Kafka-транзакция, записи идут по position, ключ — исходный ordering_key
(subscription_id), Value — исходный bytea без повторной сериализации.
Несколько пакетов не объединяются; следующие C до успеха текущего не отправляются.
В памяти находится один полный пакет. Ограничение размера бизнес-транзакций
и admission относится к будущим ограничителям; произвольный пакет не режется
ради лимита числа записей клиента. Нагрузочная вместимость не квалифицирована.

На каждой попытке создаётся новый producer с тем же ID: `kafka.New` получает
новую эпоху и выполняет fencing до отправки. После инициализации lease проверяется
повторно: запоздалый initializer с устаревшим token не публикует. Если новый
владелец появился после этой проверки, его Kafka initialization отсекает старого
producer перед новой публикацией. Старый SQL-ack дополнительно запрещён token/CAS.
Поздняя инициализация может вызвать fencing нового владельца и его остановку;
она не разрешает публикацию старого C. Назначение нового процесса после fencing
остаётся обязанностью runtime/supervisor, которого здесь ещё нет.

Только `nil` от Kafka Publish разрешает UPDATE cursor на конец пакета с проверкой
исходного cursor, token и живой lease. При ошибке/потере EndTxn-ответа cursor не
меняется; при падении после commit Kafka до SQL-ack допустим дубль с прежними
байтами/event_id/C. Условное освобождение lease не затрагивает нового владельца;
после аварии восстановление ждёт её истечения. Ошибка SQL-ack с неизвестным исходом
повторно разрешается чтением durable cursor. Run повторяет ошибки брокера/SQL,
но останавливается при fencing/потере lease, ошибке конфигурации или повреждённом журнале.

Журнал не обновляется/не удаляется, batches/counter не меняются. Отметка publish
не снимает replay-pin и не разрешает retention. SQL replay остаётся доступным
после отправки; pins и cleaner реализуются отдельными задачами.

Проверки:

```sh
# Реальный PostgreSQL + контролируемые границы ошибок:
GOCACHE=/tmp/binance-go-build python3 scripts/check_postgres.py
# Оба disposable стенда, lost EndTxn response, fencing, read_committed,
# сбой SQL-ack, точные повторы/порядок; удаление обоих тестовых volumes:
KAFKA_RUN_POSTGRES=1 GOCACHE=/tmp/binance-go-build bash infra/kafka/verify-go.sh
```

Без POSTGRES_TEST PostgreSQL-тесты пропускаются; KafkaRecovery требует также
KAFKA_INTEGRATION=1 и параметры disposable Kafka. Обычный go test сам по себе
не подтверждает интеграцию. Ни рабочая БД, ни рабочие topics runner не используются.
