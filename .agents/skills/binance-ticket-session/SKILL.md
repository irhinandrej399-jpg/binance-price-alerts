# Сессия по тикету Binance Price Alerts

Работай из корня репозитория с `AGENTS.md`, `scripts/backlog.py` и `docs/backlog/tickets/`. Все команды и пути ниже указаны от корня. Правила проекта находятся в [AGENTS.md](../../../AGENTS.md); не копируй в skill весь бэклог и изменяемые назначения моделей.

## Вход и выбор режима

1. Прочитай [STATE](../../../docs/STATE.md) и [WORKING](../../../docs/WORKING.md). Сверь сводку с `git status --short` и относящимся к запросу diff, включая staging. Сохрани существующую работу пользователя.
2. Определи поручение: выполнение, продолжение, подготовка/выбор модели или ревью. Просьба посмотреть карточку или подобрать модель разрешает чтение, но сама по себе не запускает реализацию и не меняет статусы.
3. Возьми ровно один названный пользователем ID. Если поручено выбрать следующий, выполни `python3 scripts/backlog.py next` и учитывай показанную начатую работу по правилам [ORDER](../../../docs/backlog/ORDER.md). При нескольких неоднозначных ID уточни один; без ID или поручения выбрать следующий не начинай продуктовый тикет. Консультация и обслуживание процесса выполняются без выдуманного ID.
4. Выполни `python3 scripts/backlog.py show <ID>` и прочитай полную `docs/backlog/tickets/<ID>.md`, включая «Ход работы» и «Передача следующей сессии», если они есть. Не подменяй чтение карточки выводом очереди. Контейнер `split` целиком не выполняй; покажи дочерние задачи для выбора. Для уже `done` сначала проверь результат: повторно открывать реализацию без соответствующего поручения не нужно.

## Контекст и модель до реализации

Прочитай [workflow](../../../docs/backlog/workflow.md) и [MODELS](../../../docs/backlog/MODELS.md). Из карточки возьми конкретную рекомендуемую модель, reasoning и причину. Кратко сообщи пользователю ID, результат сессии, рекомендуемую пару и готовность зависимостей. Если запрос только на подготовку, передай эту информацию и стартовый запрос без изменения карточек.

Модель пользователь выбирает в селекторе клиента до запуска. Не заявляй, что skill сменил модель или подтвердил фактическую модель сессии. При недоступной паре используй рекомендации замены из MODELS; иной выбор пользователя не блокирует уже порученную работу. Не меняй глобальную конфигурацию и не повышай модель вместо разделения задачи.

Далее читай относящиеся к критериям разделы [requirements](../../../docs/requirements.md), принятые ADR, карточки прямых зависимостей и их артефакты/интерфейсы, нужные код и тесты. Контекстные ссылки из карточки открывай по необходимости; весь бэклог не загружай. Сверяй `done` зависимостей с их результатом, а старые записи о тестах — с текущими файлами.

## Проверка и выполнение

- Проведи сессионную проверку из workflow: готовые зависимости, согласованные контракты, один проверяемый результат и имеющиеся средства проверки. Если предпосылка не готова, зафиксируй препятствие и точный нужный ID; не выполняй зависимость скрытно внутри этой сессии.
- Для разрешённой реализации только после проверки переведи `planned` → `ready` → `in-progress`, синхронизируй индекс и активный ID в STATE. При продолжении восстанови оставшиеся критерии по diff, карточке и проверкам.
- Для `decision` исследуй факты и варианты. Открытое продуктовое решение согласуй с пользователем; до согласования оставь `decision`. Затем запиши ADR и связанные изменения требований. Не добавляй реализацию приложения в DEC.
- Поведение разрабатывай через Red → Green → Refactor с проверенной причиной падения. Документы и инфраструктуру проверяй подходящими командами без искусственных unit-тестов. Команды и фактические результаты сохраняй в карточке.
- При ревью проверяй критерии, артефакты и относящийся diff; передавай замечания со ссылками. Не превращай ревью в реализацию без поручения.
- Выросший объём сначала раздели по правилам проекта. При изменении карточек/зависимостей синхронизируй ORDER и назначь модели новым активным карточкам по MODELS.

## Передача и завершение

Следуй разделу завершения AGENTS и [GIT](../../../docs/GIT.md). Обнови «Ход работы» и «Передача следующей сессии» в карточке, статус в индексе и краткую навигацию STATE. Недоступная проверка не считается успешной; незавершённую работу не помечай `done`. Отдельное ревью требуется только когда оно согласовано.

Выполни `python3 scripts/backlog.py check`. Для завершённого тикета создай уже разрешённый локальный commit через `scripts/git_ticket.py`, с явным списком файлов, карточкой, индексом и STATE, сообщением `type(ID): описание` и разделами изменений и проверок. Проверь `git status --short` и `git show --stat HEAD`. Сообщи ID, статус, SHA, результат, проверки и ограничения; собственный SHA обратно в этот commit не записывай. Push автоматически не выполняй. Следующий тикет не начинай.
